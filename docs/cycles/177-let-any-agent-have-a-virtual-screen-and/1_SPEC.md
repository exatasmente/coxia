# Let any agent have a virtual screen, and watch it from the conversation it works in

Gate 1: **approved on 2026-10-09** (answers at the end). Gate 2 waived by the maintainer; the plan (`2_PLAN.md`) follows.

Marks used below: **decided** is a maintainer decision taken in chat on 2026-10-09 (not reopened here); **proposed — confirm at gate 1** is a product choice this spec makes and the maintainer may change; **verified 2026-10-09** is a fact read in the code on `release/0.9.0` (`9c13311b`, schema 20), nothing was run; **requirement for the plan** is something the spec fixes as an outcome and leaves the mechanism to the plan; **not verified** is said in the last section. Names of fields, channels and tools are suggestions: the plan fixes them.

## What is asked

The issue, in its own words:

> Only a QA stage gets a virtual screen, and only that stage's screen can be watched (#157). A person who asks an agent in a conversation, in the forum or in its direct conversation, to "open the browser and update the spreadsheet" has no way for that agent to get a screen, and no way to watch it work.

What should happen, quoted:

> - **Any agent can have a virtual screen** when its work needs one: in a stage of any kind, in its direct conversation, in a squad channel or in a run's thread when it is mentioned. Never the person's own screen.
> - **Live screen wherever the agent is talking**: the conversation that started the work shows the same viewer as the stage card (watch on the phone, take control on the computer), and the recording is kept as evidence of that conversation's work.
> - **Network, per agent**: an agent in the sandbox reaches only the hosts the person allows for it, through the existing proxy; or the agent is set to run on the computer (`shell: host`) and uses the network as the person does. The person chooses per agent.
> - **A logged-in browser, per agent**: the agent's browser profile (cookies, local storage) is kept between uses in the app's data folder, mode 0600, never in a worktree and never in what the model reads. Settings show which sites hold a session for each agent, and the person can revoke one or all.
> - **Authorisation**: the person's request in the conversation authorises the task; before an irreversible step (send, save to an external service, delete, publish, pay) the agent stops and asks; everything it does on the screen is recorded and audited.

The issue also says that this touches the rule that the only door to an external effect is the approval in Actions, and that the refinement "must say how the stop-before-irreversible rule is enforced and audited, not only asked of the model". Rules 33 to 41 answer that, and rule 40 states the new rule in full.

## What changes for the person

- In Settings, on the computer, an agent gets a **Virtual screen** switch (it gives the agent the app's browser and a screen to watch), a list of **sites it may reach** (sandbox only), and a **Keep a logged-in browser** switch. A **Sessions** panel per agent lists the sites that hold a session and revokes one or all. An agent may have the screen and no shell at all, which is the recommended setting for work on sites.
- A person who asks such an agent, in its direct conversation, in a squad channel, in a general thread or in a run's thread, to "open the browser and update a spreadsheet in an online office suite" sees the agent's live line show a **Watch** button. It opens the viewer of the stage card: on the computer with **Take control**, on the phone watch only.
- The screen **stays open between messages** and says when it will close. A strip above the message box lists the open screens of the conversation, each with **Watch** and **Close**. The live line of a running answer gets **Stop**. Closing the viewer does not stop the agent.
- The agent works the page through the app's browser tools. When it is about to **submit a form or press a control named like send, save, delete, publish, pay or confirm**, the app holds the step and asks: a card in the conversation and a notification show what is about to happen, in the app's words read from the page. The step does not happen until the person says yes. For a step the app cannot classify, the same card says so.
- For a step taken outside those tools (the agent's own script), the agent has the **confirmation tool**, which asks the same way, but nothing forces the agent to call it.
- When the screen closes, the recording appears in the conversation as an attachment that plays in place.
- The agent's browser logs in once and stays logged in the next time, until the person revokes the site, the agent is removed or the profile is deleted.
- A QA stage looks and behaves as today unless the person turned the new switches on for its agent.

## Rules

### 1. Which agents and stages get a display and a browser

1. **A per-agent switch decides.** (proposed — confirm at gate 1) A new optional field on the agent, absent meaning off, gives the agent a virtual screen and the app's browser tools (rule 5). A session also gets a display, as today, when its stage is a QA stage. The workspace switch `runner.sandbox.display` stays the master: with it off, no agent has a display, and the platform must be Linux. The switch does **not** require a shell: an agent with `shell: none` can have it, and then the screen and the browser are the app's alone.
2. **Every place the agent works.** The switch applies to the agent in a stage of any kind, in an agent a stage calls, in an agent mentioned in a run's thread, and in a direct conversation, a squad channel (including the `squads` channel) and a general thread. A ceremony (the voice ceremonies) has no screen.
3. **Never the person's own screen.** (decided, carried over from #157) The display is always a virtual one the app started.
4. **A QA stage does not change.** A QA stage still gets its shell-path display with no agent switch, loopback-only network and a fresh profile unless the agent's new switches are on. Its prompt is byte-identical to today's; the goldens that do not involve the new switches do not move.

### 2. The app-owned browser (the main path)

5. **`coxia_browser`, built on the Playwright MCP.** (decided 9 and 11) The agent's browser work goes through an app-owned tool server named `coxia_browser`, served the way the existing ones are (an in-process MCP server for the Claude SDK, `ToolImpl`s from the same request for the open engine, with the same behaviour in both). Behind it, the app starts **one Playwright MCP server (`@playwright/mcp`, Apache-2.0) per agent browser session** and sits between the agent and that server as an **intermediary**: the agent never talks to the Playwright MCP, and every tool call passes through the app before it is forwarded. The intermediary exposes an **allowlist** of the Playwright MCP's tools, not whatever the pinned version offers: the page reads and the actions of a browser (navigate and back, snapshot, click, type, press a key, select, hover, wait, tabs, dialogs, and a screenshot only where the agent can look at images). A tool that runs script in the page or in the browser (an evaluate or run-code tool), uploads or downloads a file, reads or writes cookies or storage, lists network requests, installs a browser or closes the browser is **not exposed**, because each would let the agent step around what the app classifies and records; the app owns the browser's life. A tool the allowlist does not know, because an upgrade added it, is not exposed either (the contract test of acceptance criterion 2). The exact tool names are those of the pinned version (the maintainer named `browser_navigate`, `browser_snapshot`, `browser_click`, `browser_type` and `browser_press_key`); the plan reads them from that version. The confirmation tool (rule 37) is offered next to them, in this server or in a sibling (decided 10).
6. **How the app starts the server.** (decided 11) For each agent browser session the app starts the Playwright MCP with: the agent's profile as `--user-data-dir` when the profile switch is on, or `--isolated` (an in-memory profile) when it is off; `--proxy-server` pointing at the app's CONNECT proxy, carrying that agent's allowed hosts (rule 7); the agent's virtual display in `DISPLAY`, headed (the display the live screen shows and the recording films; when the agent also has a shell session it is that session's display, and when it has none the app starts one); and an output folder for traces and session files that belongs to the app (see below). The server's other documented options are used or left alone on purpose, as this table says (the options are those the maintainer cited from the Playwright MCP configuration docs; this step did not read the package):

    | Option | What the spec does with it |
    |---|---|
    | `--user-data-dir` | The agent's persistent profile (rule 27). |
    | `--isolated` | The fresh, throwaway profile when the profile switch is off, and for a second session of an agent whose profile is in use (rule 29). |
    | `--storage-state` | Not used. A state file would be another place holding cookies for the app to guard. |
    | `--proxy-server` | The network boundary of the app's browser (rule 7). |
    | `--allowed-origins` / `--blocked-origins` | May be set from the agent's host list so that a refusal reads clearly, and never relied on: Playwright's own docs say `--allowed-origins` is **not** a security boundary. The proxy is the boundary. |
    | `--secrets` | The server's mechanism for keeping values away from the model (a dotenv file; the docs say secrets prevent LLMs from accessing sensitive data). A candidate for #178's hand-off mask, which the plan proves against the app's own masking in the intermediary (rule 8). Not used by #177. |
    | `--init-script` | A candidate for letting the intermediary learn what a snapshot does not say (whether a field is inside a form, for rule 34). The plan decides; nothing the agent can see or call. |
    | `--caps vision,pdf` | Not enabled. `vision` brings tools that act at screen coordinates, which the app cannot classify (rule 35); enabling it for a canvas-based application is open question 20. |
    | `--cdp-endpoint` | Not used by default. It is the way to attach the server to a browser started elsewhere, a candidate for the plan's question of where the browser runs (open question 19). |
    | `--save-video` | Not used: the app records the whole display (rule 18). |
    | `--save-trace`, `--save-session` | An output folder the app owns, outside any worktree and outside what the model reads (the guard of rule 28), never exported. A trace holds page content and the network's requests, cookies included, so it is treated like the profile: bounded in size, deleted with the agent's profile on removal, and off unless the plan finds a use for it. |

7. **Network and confinement of the app's browser.** *Requirement for the plan:* the browser reaches exactly the network the agent's sandbox would have under rule 25 (the agent's host list through the app's proxy; the shared network only for an agent on `shell: host`; nothing when the agent has no list), with the same refusals and the same summary (rule 26). There is no route around the proxy: the browser must not reach the person's loopback services, local network, other hosts, or anything through a side channel the proxy does not see (DNS, UDP, QUIC, real-time connections). The proxy today listens on a socket in the stage folder and speaks to a forwarder inside a sandbox; a browser's `--proxy-server` needs an address, so a browser outside a network namespace needs a loopback listener of the app, which must be per session, closed with the session, and not usable as a free tunnel by another process of the computer (credentials the app sets for the session, or an equivalent). The browser is also confined as the agent's sandbox is: for an agent not on `shell: host` it reads nothing of the person's home beyond its profile and its output folder. Whether the server runs inside the agent's sandbox, where a network namespace forces the proxy, or in the app's own process tree, where the flags and the listener do, is the plan's question (open question 19); the spec requires the outcome and a test that a host outside the list, and a service on the computer's loopback, are unreachable.
8. **What the intermediary does to a call.** Every call is handled in one place, in this order: it is **classified** (rule 34, from the tool name and arguments and from the page the app itself passed through); if irreversible or unclassifiable it is **held** until the person answers (rules 34 to 36); it is **forwarded** to the Playwright MCP; its **result is masked and fenced**: page text is untrusted, so it comes back to the agent as data inside a fence, redacted with the app's `redact`, and cut to a size cap, and a mask can be applied to it. #178 uses that mask to remove from every snapshot what the person typed during a hand-off; this spec builds the place and not the mask. The call is **audited** (rule 38) and its **step is recorded** (rule 9). Navigating refuses addresses that are not HTTP(S), and says plainly when a host is outside the agent's list.
9. **Every step is recorded as material for the procedure memory.** (decided 9; #179 specifies the memory) The app keeps, per screen session, a structured log of the steps it forwarded: the tool, the role and name of the target the app read from the page, the site, the path without query and fragment, the outcome, whether it was held and what the person answered, and the time. It never holds a typed value, the page's text beyond a control's name, a cookie, or a query string. This spec fixes that the log exists, what it never holds, and that #179 consumes it; where it is kept and how it becomes memory are #179's. The Playwright MCP's own session file (`--save-session`) is not that log and is not given to #179.
10. **The shell path stays, with fewer guarantees.** (decided 9) An agent that has a shell can still run Playwright from it (for example to test the app under development, which is what a QA stage does). That path keeps the recording of the display, the agent's host list and the confirmation tool; it lacks the hold of rule 34, the mask of rule 8 and the step log of rule 9. The prompt says so and tells the agent to use the app's browser for any external site (rule 45). Rule 33 states what the authorisation means on each path. *Requirement for the plan:* the control channel of the app's browser (the server's stdio or its debugging connection) is not reachable from the agent's commands, so an agent with a shell cannot drive the app's browser around the hold; where the plan cannot guarantee it, rule 39 is softened accordingly.
11. **Dependencies and no driver.** `@playwright/mcp` is added as a dependency at an **exact version** (not a range), allowed in the public package, with its licence in the third-party notices; `playwright-core`, today a development dependency at 1.62.1, becomes a production one if the plan needs it, at the version the server expects. The app browses with the browsers the person configured (the browsers folder). When they are missing or do not match the server, the tools answer once with a plain reason, the thread says it, and the agent goes on without a browser; Settings shows it on the sandbox status line. The app downloads and ships no browser.

### 3. A screen in a conversation

12. **One screen per agent and conversation.** A conversation screen is identified by the activity call without its message sequence: the agent and the thread (`call:<thread>:<agent>`). The sequence is left out because the screen outlives the message that opened it (decision 6). A stage's screen keeps its run key (`run:<id>`). The hub's registry, `SCREEN_EVENT` and the conversation notes take this key instead of a run id. A run can then have its stage's screen and a mentioned agent's screen at the same time. (proposed — confirm at gate 1: the key's shape)
13. **The screen and browser live between messages.** (decided 6) The first message that calls an agent with the switch on opens its display and, if it has a shell, its session, with its profile and its proxy. The following messages of the same conversation reuse them: the open page, the tabs, the display and the processes an agent's shell started are still there. Today the session is opened per answer.
14. **It closes after about 10 minutes idle.** (decided 6) The value is a constant of the code. A screen is idle when no answer of that agent is running in the conversation, no browser step or command of its is running or waiting for the person, no held step or confirmation is pending and the person has not used the screen with Take control. Watching does not keep it open: a viewer left open on a phone does not pin it. A screen also closes at the first of: the person closes it (rule 16); 2 hours since it opened (the workspace's existing `runner.stageMaxMs`); the agent is removed, its switch or its `shell` changes, or the workspace display switch goes off; the app quits; the thread is deleted; for a run's thread, the run's stage moves on or the run ends. (the 2 hours and the run's thread are proposed — confirm at gate 1)
15. **A conversation without a repository still gets a screen.** (proposed — confirm at gate 1) An agent with the switch and `shell: none` needs no working folder at all. An agent with the switch and a shell, in a place with no repository on disk, works in an empty throwaway folder instead of the `noShell` line.
16. **How the person stops it.** (proposed — confirm at gate 1) Today a mention cannot be cancelled. Two controls, in the desktop app and in a paired browser (a stop only takes capability away, like `runs:cancel`, which is open to a paired browser):
    - **Stop**, on the live line of an answer that is running: aborts that call only. The screen stays and starts its idle clock. It applies to every mention call, with or without a screen.
    - **Close**, in the viewer and in the strip of open screens: ends the screen. A running answer is aborted, the browser, the agent's processes and the display are killed, the recording is kept (rule 18), the profile is released (rule 29), a held step or pending confirmation counts as declined, and the thread gets one line saying the person closed it.
17. **Many screens.** At most 4 conversation screens are open in a workspace at once (a constant). A fifth agent works without a display and the thread says why. (proposed — confirm at gate 1; see the open questions)

### 4. Recording a conversation screen

18. **Recorded from open to close.** The conversation screen is recorded as #157 records a stage (change-only, about 1 frame a second, the same caps of 24 MiB and 60 min, a cap stops the recording and says so), and kept when the screen closes, before the browser and session are closed, whatever the end (idle, the person, a failure, a stop). Marks for the person's use of the screen are kept. A conversation screen is idle most of the time, so the recording relies on #176 (decision 8) to skip an empty screen and shorten idle gaps; see Risks.
19. **Where it is kept.** (decided 6; the shape is proposed — confirm at gate 1)
    - In a conversation that is not a run's thread, the recording is **an attachment of the conversation**: the app posts one message of its own (a system-kind post, so it is not pasted into any prompt) titled with the agent and the time span, carrying the WebM file in the conversation's attachment folder.
    - The attachment store has **no video kind** today and its limits (5 MiB an image, 1 MiB the rest, 10 MiB a message) do not fit a 24 MiB video. So a new kind, `video` (WebM), is added with these properties: it is accepted only through the app's own door, never from a person's upload (a WebM a person attaches is still refused); it has its own cap (the recording's 24 MiB) outside the 10 MiB of a message; the model's attachment tool neither lists nor reads it (the frames of a logged-in session are not for the model); deleting the post deletes the file; it joins the `screens` retention group, so the workspace's retention days apply and the post keeps a "removed by retention" note.
    - In a run's thread, the recording is a piece of the run's evidence, exactly as a stage's recording is (the store, the player, the retention and the model-exclusion already exist).
20. **A failure to keep it is said**, in the conversation, with the reason, and never fails the answer (as #157 rule 19).

### 5. Watching and taking control

21. **Frames stay out of `screen:`.** (proposed — confirm at gate 1) The frame read stays the existing `runs:screen`, whose first argument is now the screen key (`run:<id>`, `call:<thread>:<agent>`; a bare run id is accepted as the stage's). It is already a read open to a paired browser and already pinned by `runs-policy.test.ts`, so the policy does not change, and no frame is ever served under `screen:` (denied to the web by a pattern). New `runs:` channels (list the open screens of a thread; close a screen; stop a call; answer a held step or a confirmation) are classified in `test/runs-policy.test.ts`. No `forum:` channel is added, so the pinned list of `test/forum-policy.test.ts` does not move. A channel named outside `screen:` that moved input would be allowed by default to a paired browser: input stays on `screen:control` and `screen:input` (now taking the key), and a test pins that no input-like channel exists elsewhere.
22. **The same viewer in the conversation.** The viewer takes a key instead of a `Run`. It opens from the live line of a call (`CallLine`) and from the strip of open screens, in the forum conversation screens, in a run's thread and in the Settings agent assistant's thread. The signal that a screen exists rides the activity entry while the call runs and the new list read (refreshed by `SCREEN_EVENT`, which carries no pixels) between messages.
23. **The phone may watch.** (proposed — confirm at gate 1; open question 3) A paired browser sees the list, the frames at the smaller size, Stop and Close, and never Take control. Answering a held step or a confirmation from the phone needs the external-effects switch, like `runs:command`. The desktop has Take control exactly as in #157; what the person does is not a step of the agent and is recorded as a mark.

### 6. Network per agent

24. **A per-agent host list.** (decided 4; the field is proposed — confirm at gate 1) A new optional field on the agent holds the hosts the person allows for it: exact lowercase names, HTTPS port 443, at most 20, no wildcard and no port, the same validation as `registryHosts`. It is edited on the computer only. It applies to the agent's app-owned browser (rule 7) **and** to every sandbox session of that agent, in a stage, a call and a conversation, with or without a display.
25. **How it meets the workspace's setting.** (proposed — confirm at gate 1)
    - Workspace `off`, agent list empty: nothing changes (no network).
    - Workspace `off`, agent list set: the agent's network is the proxy with exactly the agent's hosts, as a plugin's is.
    - Workspace `registry`: the agent's list is added to the workspace's package-registry hosts for that agent.
    - Workspace `open`, agent list set: the agent's list **narrows** the network to the proxy with only its hosts, because the per-agent choice is what the person allows for that agent. Agent list empty: open, as today.
    - `shell: host`: the list is not used (there is no proxy on the computer); the editor says so. The app's browser of a host agent uses the computer's network as the person does. The person's choice per agent is either the sandbox with a list or `shell: host`, and nothing mixes them.
    - An agent with the screen and no shell follows the same table, as if it had a sandbox.
    - The agent's prompt says which hosts it may reach (rule 45).
26. **The proxy's decisions are summarised, not flooded.** A conversation session and the app's browser get the proxy's log, which a conversation lacks today. A page opens dozens of tunnels, so the thread gets one line the first time a host is refused in a session (so the person sees why a page broke) and one summary line at close; `auditoria.jsonl` gets one summary per session (rule 38), not one line per tunnel. The limits that fit installing packages (16 tunnels, 60 s idle, 20 hosts) may not fit a browser; the plan measures and sets them.

### 7. A logged-in browser per agent

27. **One persistent profile per agent, used by the app's browser.** (decided 3; the switch is proposed — confirm at gate 1) With the agent's browser-profile switch on, the app's browser (rule 6) starts on that agent's profile folder (`--user-data-dir`). With it off, it starts isolated (`--isolated`), on a fresh profile, as today. **The profile is not mounted into the agent's sandbox**: the agent's own shell, whose Playwright keeps a fresh profile (rule 10), cannot read the folder.
28. **Where it lives and how it is protected.** (decided 3; the exact location is open question 2)
    - In the app's data folder (the recommendation is `<workspace>/browser/<agent id>/`), created by the app with mode 0700; the files the browser creates are 0600 where the browser allows it, and the 0700 folder is what keeps other users out whatever its files do.
    - Never inside a worktree or the throwaway copy, never a link, never reachable through a folder bind the person configured; the real path is checked before the browser starts on it.
    - **Outside what the model reads.** The engines' own Read, Grep and Glob refuse any path inside a profile folder, for every engine, including an agent with no shell whose working folder is the workspace folder. This is a new guard, not a naming trick: the profile files' names match none of today's secret globs.
    - The app never parses the profile's files in its own process; the browser it launches is the only program that reads them (rule 30). The profile is never exported with the config, never copied to a worktree, never put in a log, never in an age-based retention group, and it is listed with the credentials in `rules/secrets.md` as a sibling of `secrets.json`.
29. **One session at a time per agent.** (proposed — confirm at gate 1) A browser locks its profile, and nothing serialises an agent's sessions today (a stage and a conversation, two runs, a nested call). The app holds a lock per agent. The first session to start holds the profile; any other session of the same agent at the same time gets an isolated, fresh profile and the thread and the tool's answer say the logged-in browser is in use and where. The lock is released when the session closes, and a stale browser lock file left by a dead process does not block the next session. A held-open conversation screen holds the lock for its whole life, idle included, which is why Close exists.
30. **Settings show the sites and revoke them.** (decided 3) On the computer only, per agent: the sites that hold a session; **Revoke** one site; **Revoke all**. Revoke all deletes the profile folder (a new empty one is made at the next use) and always works. Listing and revoking one site are done by the app's own browser, started on the closed profile with no network, using the browser's own account of what it holds (cookies and site storage per site); the app parses no database and shows the sites, never a value. Both are refused with "close the agent's screen first" while the agent's profile is in use. Whether the browser can clear all the storage of one site, not only cookies, is the plan's spike; if it cannot, rule 30 falls back as open question 9 says.
31. **When the agent goes away.** (proposed — confirm at gate 1) Removing an agent from the config (the editor, an import, a template) closes its screens and **deletes its profile at once**, not into a trash; a profile folder whose agent is not in the config is deleted at the next start. A new agent created later with the same id does not inherit anyone's cookies. Deleting a workspace deletes its profiles before the folder is moved to the trash, so cookies never sit in the trash (which nothing purges today).
32. **A named risk: what the agent can reach in its own profile.** On the app's browser path the agent has no tool that returns a cookie or the storage (rule 5) and the folder is not in its sandbox (rule 27), so it cannot read them. It does see everything the logged-in page shows, which is the point, and what it reads is redacted and fenced (rule 8). The remaining ways: an agent on **`shell: host`** runs as the person and can open the profile folder directly, and 0600 protects only against other users; an agent that logs in through its own shell-path browser puts that session in a fresh profile it can read, and what bounds where that can be sent is the host list in the sandbox and nothing on the host. The viewer and Settings say so on the host switch.

### 8. Authorising, holding and asking

33. **The authorisation rule, per path.** (decided 1 for the MCP path; the shell-path rule is proposed — confirm at gate 1, for the maintainer to approve)
    - **App's browser path.** The person's request in the conversation authorises the task it names, and for a stage, the person's starting the run does. The app then enforces what it can: it holds classified irreversible steps until the person confirms (rule 34), it bounds where the browser can go (rule 7), it records every step (rule 9) and audits the session (rule 38). The audit line that opens a screen names the message that asked.
    - **Shell path.** The same request authorises the same task in the person's words, but the app does not enforce the authorisation on this path: it keeps the recording of the display, the agent's host list (sandbox) and the confirmation tool, which is voluntary; it does not hold, mask or log steps. So: an agent may use the shell path on a site only within its host list (or `shell: host`, where nothing bounds it), the prompt tells it to ask with the confirmation tool before an irreversible step and to use the app's browser for any external site, and the recording and the audit are how a step taken without asking is found. Using the shell path for the app under test (the loopback) needs nothing more than today.
34. **The structural hold.** (decided 9 and 11; the classification is proposed — confirm at gate 1) The intermediary (rule 8) sees every call before the Playwright MCP does, and holds it if it is **irreversible**. It decides from the tool and its arguments, and from the target as the **page** describes it (the role and name the app read from the snapshot it passed through itself), never from what the agent said about it. In code, not configurable: (a) a **submit**: a type call that asks to submit after typing, a press of Enter (or the equivalent key) while the focus is in a field of a form, or a click on a submit control; (b) a click, or a key on a focused control, whose accessible name, visible text, value or title names an irreversible act (words such as send, save, submit, delete, remove, publish, post, pay, buy, order, confirm, transfer, approve, share, sign, apply, unsubscribe, in English and Brazilian Portuguese, the app's two languages); (c) a keyboard shortcut that saves or sends (Control or Command with S or Enter); (d) accepting a page dialog (a "are you sure" box). Typing into a field, filling a form without submitting, selecting an option, hovering, navigating (a GET), going back, scrolling, waiting, reading and tab changes are not held. A snapshot gives roles and names but may not say whether a field is inside a form; where it does not, the app reads that itself (the plan's choice, for example the server's init-script option or its own read, never a tool the agent can call). A held step does not execute until the person says yes; a no, no answer or Close makes it not execute and tells the agent. The classification is by name and form, a heuristic: a control named "Go" that deletes, or a word in a language the list lacks, is **not** caught, and the spec says so (rule 39).
35. **A step the app cannot classify.** (proposed — confirm at gate 1; open question 5) When the app cannot read what the target is (a click at coordinates, a canvas, a control with no accessible name, a frame from another site, a drag, a shortcut with a modifier it does not know, or a tool or argument the classification has no row for), it **holds it too** (fail closed, as the rest of the app does). To keep a spreadsheet in a canvas usable, the person can answer **Yes for the rest of this screen on this site**, which lets unclassifiable steps on that site through until the screen closes. That pass never applies to a step the app classified as irreversible, which asks every time. The step log (rule 9) marks unclassifiable steps and the passes.
36. **How a held step asks.** One card in the conversation (or the run's thread) with the agent, the step in the app's words read from the page ("click 'Send', a submit button, on example.com"), why it was held (submit, a name, a shortcut, unclassifiable), the agent's own one-line reason (marked as the agent's words) and a **Watch** button; a notification that opens the conversation; the pending ask in the viewer. It is answered from the desktop; from a paired browser only with the external-effects switch (the same class as `runs:command`). The agent's clocks and the screen's idle clock stand still while it waits. No answer in 15 minutes counts as declined (fail closed), as the conversation command store already does.
37. **The confirmation tool.** (decided 2; the details are proposed — confirm at gate 1) `screen_confirm`, an app-owned tool offered to every session that has a virtual display or the app's browser, and to every session of an agent with a host list or on `shell: host`. Called with the step in a sentence (and the site, and a kind: send, save, delete, publish, pay, other), it asks the person like rule 36 and **waits**; the model gets back approved, declined (with the note) or "no answer". It exists for what the app cannot see: a step taken through the shell path, and anything the app's browser did not classify but the agent knows is irreversible. **It is voluntary for the model, and the spec says so plainly**: the app does not see the request a site receives from an agent's own script, cannot tell a click that sends from one that does not there, and does not intercept TLS. Nothing stops an agent that takes an irreversible step on the shell path without calling it.
38. **What is audited.** In `auditoria.jsonl`, with the log's own scrubbing, as new kinds of the closed list (the plan names them, and the audit screen shows them in both languages): a screen opening and closing (agent, place, mode sandbox or host, which path was used, whether the profile was used, duration, number of steps by tool, whether the recording was kept, the message that asked); the hosts allowed and refused with counts, once per session; every held step and every confirmation (the step as the app described it or as the agent wrote it, the site, why it was held, who answered and through what: the window or a paired browser; the answer); the intervals in which the person used the screen (from and to only); and the commands of a conversation's shell session, as a stage's already are (`exec`, with `via`). The audit never holds a keystroke, a typed value, a cookie, a page's text or a URL path.
39. **What "recorded and audited" means here, and what it does not.** The record is the recording (pixels), the step log (rule 9) and these audit lines. On the app's browser path the steps are complete, because every one passes the app. On the shell path there is **no per-click record**: the app does not drive that browser, so it has none to keep, and a script's body is not logged (a command line is clipped at 300 characters, as today). The structural hold bounds only the app's browser: an agent with a shell can start its own, which is why rule 10 asks that the app's browser cannot be driven from the shell, and why the shell path's guarantees are listed in rule 10 and not hidden.
40. **The rule in `external-effects.md` changes.** (proposed text, for the maintainer to approve at gate 1) Today the rule says that anything leaving the machine becomes a proposed action, is confirmed by the person and audited, and that `approveAction` is the only door. That stays true for what the app itself sends to a code host or to any service it speaks to. It is already not the whole truth (`shell: host` commands and `network: open` are other doors), and an agent working a site through a virtual screen is a third that never reaches `approveAction`. The rule becomes:
    > **Two doors.** (1) What the app sends itself (a comment, a label, a status, a push, a pull request, a plugin's write) is proposed, confirmed by the person and audited; `approveAction` is the only door for these. (2) What an agent does on a site through a virtual screen is not a proposal in Actions. For it, the rule depends on the path. **Through the app's browser** (`coxia_browser`, built on the Playwright MCP) every action passes the app: the person's request authorises the task; the app holds a step it classifies as irreversible (a submit, a control named like send, save, delete, publish, pay or confirm) and asks the person before it executes, holds a step it cannot classify unless the person gave a pass for that site, bounds where the browser can go to the hosts listed for that agent, and records every step and the screen. **Through the agent's own shell** (its own Playwright, a script) the app does not see the actions: it keeps the recording, the host list in the sandbox and the confirmation tool, which the agent is asked to call before an irreversible step and which is voluntary; on `shell: host` nothing bounds where. In both, the session, the hosts reached, the person's use of the screen and every hold and confirmation are audited; the recording and the audit are how a step taken without asking is found afterwards.
    The same text goes into `docs/runner.md`. `rules/secrets.md` gets the sibling paragraph of rule 28, `rules/test-workspace.md` gets rule 41, `rules/agent-roles.md` gets the three fields and `rules/paired-phone.md` the new channels.
41. **A test workspace.** (proposed — confirm at gate 1; open question 4) Today a sandbox with network and a `shell: host` session run unchanged in a test workspace, which makes the guard a promise it does not keep for a browser. #177 adds capabilities that reach real sites, and a test workspace refuses them, with a thread line saying why: the agent's host list (the agent keeps the workspace's own network), the persistent profile (a fresh one is used), and the app's browser for an agent on `shell: host` (it would reach the person's network). The app's browser for a sandboxed or shell-less agent with no host list, a QA stage with a display, a sandbox display on the loopback and the confirmation tool work in a test workspace. The check fails closed like the rest of the guard (an unreadable registry counts as a test workspace). This does not stop a `shell: host` agent from using the person's network by its commands, which the person already approves one by one.

### 9. Configuration

42. **Three optional fields on the agent, all raises.** (proposed — confirm at gate 1; names are the plan's) A virtual-screen switch (it gives the app's browser and the screen), a host list and a browser-profile switch, absent meaning off and empty, so no existing agent gains anything. The schema goes from 20 to 21 with a step in `STEPS` even though absent means off, as `rules/config-schema.md` asks and as #170 did for an optional field. The agent editor, `docs/configuration.md` and both `ui-team` catalogs change.
43. **A paired browser may lower them, never raise them.** `agents.team` is editable from a paired browser, so `raisedPermissions` refuses by name an agent whose switch goes on, whose host list gains a host, or whose profile switch goes on, including a new agent created from the browser (it may only be made with all three off). Templates strip all three, import warns about them as it does for `host`, and the agent assistant's output never sets them.
44. **The merge order is a risk, not a decision here.** The schema number is whatever is next when the change merges: today 21, but the unmerged branch for #170 is already at 21 and edits the same functions (`openStageSandbox`, `open`, `openHost`, `createRegistryProxy`). Whichever merges second renumbers its step and resolves those files. The plan names the order after checking the branches again.

### 10. The prompt

45. **The texts that contradict the feature are updated** in both catalogs (`main.en.json` and `main.pt-BR.json`). `rules.gui` ("There is no network: never open an external address ... a fresh profile in /tmp"), `rules.gui.host` ("never drive a browser to an external one ... a fresh profile inside {out}") and `rules.shell.registry` ("install packages, nothing else") get variants that read the agent's own settings: the hosts it may reach and that anything else is refused; that the app's browser tools are the way to work on any external site and that its own Playwright is for the app under test; that the app holds some steps and asks the person; whether its profile is the logged-in one or "the logged-in browser is in use, you have a fresh one"; run its own browser headed when it has a display; call `screen_confirm` before an irreversible step taken any other way and that its calls are audited. A mention call, which has no GUI text today, gets the same sections. An agent with none of the new switches gets today's text, byte for byte. `docs/runner.md:381` loses "only that one; never a mention".

## Out of scope

- The **hand-off** of the screen to the person for a login or a confidential input (#178, decision 5): the awaiting tool (`screen_handoff`), the notice, the best-effort handling of the person's keystrokes and frames, the plain warning in the viewer, and the mask itself (this spec builds only the place where a mask is applied, rule 8). Until it exists, a password typed with Take control is on the screen, in the recording and kept in the profile, as #157 already warned.
- The **GUI memory** (#179, decision 7 and 10): records per site, `coxia_procedures`, who reads and edits them. This spec only produces the step log (rule 9).
- TLS interception, a browser extension, or a debugging-protocol filter on the agent's own browser to enforce **what** the agent does on the shell path. Only **where** is enforced there (the host list). Saying "irreversible" on that path is the model's call.
- Tools that run script in the page, read cookies or storage, upload or download files, or fill a payment form from stored data. Not in the allowlist of rule 5.
- Wildcard host names, ports other than 443, and a one-click "allow this host" from a refusal.
- More than one profile per agent, profiles shared between agents, and moving a profile between workspaces.
- Controlling a conversation screen from the phone, and several people at once.
- Operating systems other than Linux; the person's own screen; audio.
- A screen for a ceremony, and for a request or question that is passed down the chain with no session.
- Changing how the recording starts, skips empty screens or shortens idle gaps (#176).
- A setting for the idle time, the number of open screens, the word list of the classification or the confirmation timeout (constants first).
- Backing up or exporting the data folder: the app has none, so cookies leave the machine only through the person's own backup.

## Acceptance criteria

Verifiable on screen or by test.

1. **Which sessions get a display.** A table test covers the decision for: a QA stage with no switch, a non-QA stage with the switch, a called agent, an agent mentioned in a run's thread, a direct conversation, a squad channel, a general thread, a ceremony, each with the workspace switch on and off and `shell` `none`, `allowlist`, `sandbox` and `host`. An agent with the switch and `shell: none` gets the screen and the browser tools. A QA stage with no new switch behaves as today and its prompt is byte-identical (the existing goldens do not change).
2. **The tool set, and the contract with the pinned server.** The tools `coxia_browser` exposes are exactly the allowlist of rule 5, served the same way to the Claude SDK (MCP) and to the open engine (`ToolImpl`), by one test run against both. A contract test starts the pinned Playwright MCP, lists its tools, and fails if any name is neither on the allowlist nor on an explicit list of tools the app refuses to expose (script, upload and download, cookies and storage, network requests, install, close), so an upgrade that adds or renames a tool cannot go unnoticed; at run time a tool not on the allowlist is not exposed. No exposed tool can run script in the page, read cookies or storage, or move a file.
3. **Classification.** A table test over recorded snapshots and calls (the tool name, its arguments, and the target as the snapshot describes it) gives: a type call that asks to submit, a press of Enter in a form field, a click on a submit control, on a button named "Send", "Delete" or "Pay" and on their Brazilian Portuguese names ("Enviar", "Excluir", "Pagar"), Control+S, and accepting a dialog, all **irreversible**; a click on a link named "Next", typing, filling a form without submitting, a tab change, a scroll and a GET navigation all **not held**; a click at coordinates, on a canvas, on a control with no accessible name, inside a frame from another site, a drag, and a call whose tool or argument has no row in the classification all **unclassifiable**. The class comes from the page, never from the agent's own words: a click the agent describes as "harmless" on a "Delete" button is still held. The names and arguments in the table are those of the pinned version.
4. **The hold.** A held step does not execute until answered; Yes executes it exactly once; No, no answer in 15 minutes and Close each leave the page unchanged and tell the agent; a held step stops the agent's and the screen's idle clocks; the pass "for the rest of this screen on this site" lets an unclassifiable step through and never an irreversible one, and ends when the screen closes.
5. **Results.** Every result of a call returns its text inside the data fence, redacted and cut to the cap; a page whose text tries to give the agent instructions arrives inside the fence; the mask hook is called on every result that carries page text (a stub mask is applied in the test); navigating to a non-HTTP(S) address or a host outside the list answers with a plain reason. Every call, held or not, appears once in the audit summary count and once in the step log.
6. **The step log.** One entry per executed step with the fields of rule 9; no entry holds a typed value, a query string, a cookie or page text beyond a control's name; held and passed steps are marked.
7. **Network of the app's browser.** A browser started for an agent with a list reaches the listed host through the proxy and nothing else: with fake servers, a host outside the list, a service on the computer's loopback and a local-network address are all unreachable, and so is a direct UDP or DNS attempt; the decisions are summarised (200 CONNECTs make at most a few thread lines and one audit summary). On screen, with a real network and a list of one example host: the page loads and another host is refused.
8. **Keys.** The hub accepts two screens in the same run (the stage's and a mentioned agent's), refuses a second screen with the same key, and the stage's screen works as before through `run:<id>` and through a bare run id. `SCREEN_EVENT` carries the key and no pixels.
9. **Lifetime.** With a fake clock: the second message of a conversation reuses the browser and display (one opened, the page still open); they close 10 minutes after the last answer ended; a running answer, a browser step in progress, a held step or confirmation, a command waiting for the person, and the person's input on the screen each keep it open; a viewer alone does not; it closes at 2 hours, on agent removal, on the switch or `shell` changing, on thread deletion and, in a run's thread, when the run's stage changes. The recording is kept on each of these ends.
10. **Stopping.** Stop aborts the running call and leaves the screen; Close aborts a running answer, kills the browser, the session's processes and the display, keeps the recording, releases the profile lock, declines a held step and writes one thread line. Both work from a paired browser; `runs-policy` lists the new channels as allowed; a channel made up under `screen:` is still denied.
11. **Channels.** `runs:screen` answers a frame for a conversation key, `none` for an unknown key and never throws; no frame channel is served under `screen:` (`screen-policy` extended); `screen:control` and `screen:input` take the key and stay denied to a paired browser; the answer channel for a held step or a confirmation is classified as an external effect (refused to a paired browser without the switch); the forum policy's pinned list is unchanged.
12. **The viewer.** On a Linux machine with Xvfb and the browsers folder: ask an agent in its direct conversation to open a page; its live line shows Watch; the viewer opens with Take control on the desktop and without it in a paired browser; after the answer the strip lists the screen with Watch and Close; it disappears after Close.
13. **The recording as an attachment.** The app's post carries one `video` attachment of the conversation; a person's WebM upload is refused; 24 MiB is accepted for the app's recording and does not count against the message's 10 MiB; the model's attachment tool neither lists nor reads it and the post is not in any prompt; deleting the post removes the file; the retention sweep lists it in the screen-recordings group and removes only that file, leaving the post marked; it plays in place in the desktop and in a paired browser. In a run's thread the recording is run evidence and plays in the evidence block.
14. **Network per agent.** A table test of the effective network: workspace `off`, `registry` and `open`, each with an empty and a non-empty agent list, and `sandbox`, `host` and no shell, gives exactly the modes of rule 25. The list is validated (lowercase, exact, 443 only, at most 20, no wildcard, no port). With a fake upstream, a CONNECT to an agent host is allowed and any other host is refused in a stage and in a conversation session.
15. **The profile.** The folder is mode 0700 under the data folder, not inside a worktree, and a link is refused; it is **not** among the binds of the agent's sandbox; two sessions of one agent at once give the second a fresh profile with a thread line and the tool's answer saying so; the lock is released at close and after a crash, and a stale browser lock file does not block the next session. The engines' Read, Grep and Glob refuse a path inside a profile folder, for both engines, for an agent with no shell whose working folder is the workspace folder. The profile is not in the config export, in no retention group, and not in a worktree.
16. **Removal.** Removing an agent (editor, import, template) closes its screens and deletes its profile; a profile of an agent not in the config is deleted at start; deleting a workspace deletes its profiles before the trash.
17. **Settings.** On the computer: the Sessions panel lists the sites of an agent that has logged in, with no network and no value shown; Revoke removes one and the agent is logged out of it at the next use; Revoke all empties the folder; both are refused with the message while the agent's screen is open; the channels are denied to a paired browser by a pattern, and a channel added later under the same prefix is denied too.
18. **The confirmation tool and the shell path.** `screen_confirm` is offered exactly to the sessions of rule 37. A call shows the card, sends the notification and waits with the clocks paused; the desktop answers it; a paired browser is refused without the external-effects switch and allowed with it; no answer in 15 minutes returns "no answer" and counts as declined. A session whose agent runs its own Playwright from the shell and never calls the tool produces no hold and no confirmation line, and a test names this plainly as the voluntary, shell-path case; the same session still has its recording, its host list and its audited session line, and has no step log and no mask.
19. **The audit.** One line for a screen opening and one for its closing; one summary of the hosts per session; one line per held step and per confirmation naming who answered and through what; one line per interval of the person's use; `exec` lines for a conversation's shell commands. No line holds a keystroke, a typed value, a cookie, a URL path or the page's text. The audit screen shows the new kinds in both languages.
20. **Permissions.** From a paired browser, turning on the switch, adding a host, turning on the profile or creating an agent with any of them is refused by name; lowering them is allowed. A template strips them, an import warns, and the agent assistant's output cannot carry them.
21. **Migration.** A config of schema 20 migrates to 21 with the fields absent, a config of a newer schema is refused, and the schema accepts the new fields with the validation of rule 24.
22. **Test workspace.** In a workspace with `test: true` (and with an unreadable registry), the agent's host list, the persistent profile and the app's browser for a `shell: host` agent are refused with a thread line; a QA stage with a display and a sandbox display on the loopback still work.
23. **Prompts.** The new variants exist in both catalogs, an agent with none of the new switches gets today's text byte for byte, an agent with the screen is told to use the app's browser for external sites and its own Playwright for the app under test, an agent with a host list gets the list, and the goldens that involve the changed keys are updated. A mention call includes the GUI sections.
24. **The server and its dependencies.** The app starts one Playwright MCP per agent browser session with the options of rule 6 (a test on the argument list: the profile folder or `--isolated`, the proxy address with that agent's hosts, `DISPLAY`, the output folder; no `--cdp-endpoint`, no `vision` capability, and `--allowed-origins` never the only restriction); `@playwright/mcp` is pinned to an exact version and listed in the third-party notices; the main bundle builds with it (`electron-vite build`; `npm run dist` is never run) and `npm run dist:public` includes it; with no browsers folder or a mismatched one, the tools answer once with a reason, the thread says so, and Settings shows it.
25. **Gates.** `npm run i18n:lint`, `node scripts/theme-audit.mjs` (the viewer's strip, the cards and the Settings panel use tokens) and `node scripts/public-audit.mjs` pass; the fixtures use `example.com` only.
26. **Docs.** `docs/runner.md`, `docs/configuration.md` and the rule files named in rule 40 carry the new text, and `docs/runner.md:381` no longer says "never a mention".

## Risks

- **The classification is a heuristic.** The hold is structural (the app sees the step) but the judgement is by form and by name. A button named "Go" that deletes, a link that changes something by a GET, a word in a language the list lacks, and a canvas the app cannot read all slip through or fall to the unclassifiable rule. Too many holds make the feature tiresome; too few make it look safer than it is. The word list is in code and cannot be tuned by the person yet.
- **A version pin and a moving upstream.** The hold, the mask and the step log depend on the Playwright MCP's tool names and arguments (`browser_click`, `browser_type`, `browser_press_key`, `browser_navigate`, `browser_snapshot` and the rest), on the shape of its snapshots (the role and name of each target) and on its options. An upstream release can rename a tool, add one that acts (a new way to run script, to read storage or to click), change an argument such as the one that submits after typing, or change a snapshot so the classification reads the wrong target. The mitigations are an exact pin, a contract test that fails on any tool the allowlist does not know (acceptance criterion 2), a classification table pinned to that version, and a deliberate, reviewed upgrade; none removes the work of keeping up.
- **How the intermediary classifies by tool name and arguments.** The classification (rule 34) is only as good as the app's reading of a call and of the snapshot it passed through: a ref the app did not see (a page changed between the snapshot and the click), an argument the app does not model, or a tool added by a capability the person enabled would be held as unclassifiable or, if misread, let through. A per-call row for every exposed tool is part of the plan, and an exposed tool with no row is held.
- **Another party's server in the middle.** The Playwright MCP runs a browser as the process the app starts. Its own options are not all security controls (`--allowed-origins` is explicitly not a boundary; the app's proxy is). Traces and session files it can write hold page content, network requests and cookies, so the output folder is as sensitive as the profile. A flaw in the server or the browser is the app's to answer for, because the app chose them.
- **The structural hold bounds only the app's browser.** An agent that has a shell can start its own browser from the browser binaries in the browsers folder and use the shell path. Rule 6 asks that the app's browser cannot be driven from the shell; nothing stops the agent from using another browser. Giving the agent `shell: none` is the only setting where the shell path does not exist, and the editor recommends it for site work.
- **The shell path is voluntary, by decision.** There, a model that does not call the confirmation tool can send, delete or pay. The host list bounds where, and the recording and the audit show what happened afterwards. Rule 37 is the honest statement.
- **The app's browser is a program the app launches.** If it runs outside the sandbox, a hostile page's browser exploit lands in a process of the person, and a browser outside a network namespace can reach the person's loopback services and local network unless the plan removes every route around the proxy (rule 7). The requirement is firm; the mechanism is untested.
- **`shell: host` has no bound.** No proxy, no allowlist, the agent runs as the person and can read the profile folder. The only gate is the per-command "yes", and a command line says nothing about the clicks inside a script. The app's browser for a host agent uses the person's network.
- **Page text is an injection channel.** The agent reads untrusted pages with a logged-in browser. Fencing and redaction help and are not a wall; the hold, the host list and the recording are the bounds.
- **Chromium through the proxy is not demonstrated.** No evidence in the repository that Chromium honours the proxy for the app-launched browser or the sandbox's variables for the agent's. Real sites need many exact host names, the proxy has no wildcard, 16 tunnels and a 60 s idle cut, and QUIC cannot leave a sandbox without network. The plan starts with a throwaway measurement, and the result may change rules 7, 25 and 26.
- **New and promoted dependencies.** `@playwright/mcp` is new, and `playwright-core` (1.62.1) is a development dependency today that may have to ship, at the version the server expects. They grow the package and the audit of third-party notices, and the browsers in the folder the person configured must match the version the server drives: a folder holding other revisions may not work. Apache-2.0 and allowed in the public package by the maintainer's decision. Not verified (see below). `npm run dist` is never run and the public build is checked by the plan.
- **A conversation session outlives the answer.** Every limit today assumes one call: the watchdog, the working-folder copy, the cleanup in `finally`, the order "keep the recording, then close". A held browser and display are a new lifecycle with a lock, a timer, a registry and several ways to end; a leak means an Xvfb and a Chromium for as long as the app runs. The app quitting, a crash and the next start's purge must end it.
- **Idle is most of a conversation screen's life.** The recording's 60-minute cap can be eaten by idle time if #176 has not merged; the plan orders the two.
- **Per-agent lock.** The app has no per-agent serialisation today. A held conversation screen can keep the profile from a stage of the same agent; the thread says so and the person can Close. A crash must not leave a profile locked for ever.
- **Phone exposure.** `runs:screen` and every `forum:` read are open to a paired browser, so a conversation screen with a logged-in session can be watched by every paired browser. Control, the host list, the profile and the revocation are not; answering a held step needs the external-effects switch.
- **The recording shows what is on the screen.** A logged-in page can show private data, and with Take control the person's own typing is in it; frames are not paused during control (#157 decision). #178 refines this.
- **The test workspace guard is bypassed today** by any sandbox with network and any host session. Rule 41 closes what #177 adds, not what already exists.
- **The attachment store is the person's channel.** A new `video` kind touches the recogniser, the retention listing, the model's attachment tool and the deletion path; each must keep the app-only door.
- **A larger issue.** The app-owned browser, the hold, the conversation lifecycle, the profile and the network are separable. The plan may order them in commits so each can be reviewed and reverted on its own.
- **Resource limits for browsing are unmeasured.** A 512 MiB `/tmp` and `/dev/shm`, a 256 MiB file-size limit and a 256-process limit (threads count) may fit a heavy page badly in the sandbox.
- **Merge order with #170** (schema 21, same functions) and with #176 (recording behaviour). See rule 44.
- **Public repository.** Fixtures and docs use `example.com` and "a spreadsheet in an online office suite"; no real site, account or person.

## What this step did not verify

- No code ran: no `tsc`, no test, no app, no browser. Every `file:line` above was read on this tree on 2026-10-09; test names were read, not executed.
- That Chromium or Playwright, launched by the app or inside the sandbox, honours a proxy, which hosts a real page needs, and whether a large provider's sign-in refuses an automated browser (it would be the #178 case).
- That the Playwright MCP exists at a version whose tools, arguments and options are as the maintainer cited them: this step did not read the package, its configuration docs or its tool list, so the option table of rule 6 and the tool names are the maintainer's, not checked. Nor which `playwright` it depends on and whether that matches `playwright-core` 1.62.1 and the browsers folder, whether it can be started as a child of the Electron main process or must run under a separate Node, and how an intermediary reaches it (as an MCP client over its stdio, or as a library).
- Whether a snapshot says which field is inside a form, and whether the server's snapshot marks the focused element.
- That the browser can list and clear one site's cookies and storage on a closed profile (the spike of rule 30).
- Whether the control channel of an app-launched browser can be made unreachable from the sandbox's commands (rule 6), and how a classified step is read from a page without running script the page can see.
- The file modes Chromium gives its profile files; whether a timed-out command's whole process group dies; which X client tools exist in `/usr`.
- Behaviour of Chromium under the sandbox's `/dev/shm`, file-size and process limits.
- Whether another branch besides #170 bumps the schema; the check was of the remote branches known on 2026-10-09.

## Open questions

Each with the recommended answer, for the maintainer at gate 1.

1. **The idle time.** Decision 6 says "about 10 minutes". **Recommended:** a constant of 10 minutes, not a setting; watching does not count as use, taking control does.
2. **Where the profile lives.** Options: the workspace folder (`<workspace>/browser/<agent id>/`, next to `memory/` and `evidence/`, one place per workspace, goes with the workspace) or the data root (`<data root>/browser/<workspace>/<agent id>/`, next to `secrets.json`). **Recommended:** the workspace folder, with rule 31 (deletion on agent removal, a start sweep of orphans, and deletion before the workspace goes to the trash), plus the read guard of rule 28, which either location needs because the agent with no shell reads from the workspace folder.
3. **May a paired phone watch conversation screens?** The open question of the issue. **Recommended:** yes, watch, Stop and Close, as #157 decided for runs; never control; answering a held step or a confirmation only with the external-effects switch. The cost is that every paired browser can watch a logged-in session.
4. **What a test workspace allows.** **Recommended:** rule 41: refuse the host list, the persistent profile and the app's browser for a host agent; allow the loopback screen, the app's browser with no network and the confirmation tool. The alternative, refusing every GUI session in a test workspace, would also stop the QA stages that run there today.
5. **A step the app cannot classify: hold or let through?** Rule 35 holds it, with a per-site pass for the rest of the screen. The alternative is to let it through and only mark it in the step log, which keeps a canvas-based spreadsheet usable with no friction and weakens the structural claim to the classifiable part. **Recommended:** hold, with the pass: it matches the app's fail-closed habit and the pass removes the friction after one answer.
6. **Does the host list reach the agent's shell or only the app's browser?** Decision 4 says per agent, and rule 24 applies it to both. A stricter option keeps the shell at the workspace's network and gives the list to the app's browser alone, which would make the app's browser the only way to an external site. **Recommended:** both, as decision 4 reads; revisit if the shell path is used for external sites in practice.
7. **Open the screen at the first message or when the agent asks for it?** Opening at every answer of an agent with the switch costs a display and holds the profile for 10 minutes after a message that did not need a browser. A tool the agent calls to open the screen would avoid that and give a precise audit line, at the price of another tool and a changed prompt. **Recommended:** open at the first message in this issue, because the idle close bounds the cost; revisit if the cost shows.
8. **One switch or two?** Whether the profile should be a separate switch from the screen. **Recommended:** separate (rule 27): keeping logins is the sensitive part, and a person may want a screen agent that fills a public form with nothing persisted.
9. **If the per-site list cannot be done safely.** **Recommended:** do not ship Revoke-one-site by editing the browser's database; if the spike finds no safe way for the browser to clear a site, ship Revoke all and a list of the sites the agent's sessions reached (from the proxy), labelled as that, and tell the maintainer before building.
10. **How many conversation screens at once.** **Recommended:** 4 per workspace, a constant.
11. **Wildcards in the host list.** Real sites use many names. **Recommended:** none in this issue; the summary of refused hosts (rule 26) is how the person finds the names to add.
12. **A workspace in `open` mode and an agent with a host list.** **Recommended:** the list narrows (rule 25), because the person set a list for that agent. The alternative, ignoring the list in `open` mode, would silently widen what the person asked for.
13. **Does starting a run authorise a stage's work on a site?** Decision 1 speaks of the conversation. **Recommended:** yes, with the same switches, host list, hold and confirmation tool in stages (rule 33).
14. **The hold and confirmation timeout.** **Recommended:** 15 minutes, then declined, matching the conversation command store; a stage that waits for ever on an answer is worse than one that asks again.
15. **A run's thread: a held screen or one per call?** **Recommended:** held, like the other conversations, closed when the run's stage changes (rule 14); the recording is the run's evidence.
16. **The MCP server layout.** One server (`coxia_browser` with `screen_confirm` and later `screen_handoff` inside) or two (`coxia_browser` and `coxia_screen`), decision 10. **Recommended:** the plan decides after seeing how #178 needs to reach the viewer; this spec does not depend on it.
17. **Merge order with #170.** **Recommended:** merge the one that is ready first and renumber the other's step; the plan re-checks the branches the day it is written.
18. **Who can drive a browser when the person has no browsers folder.** **Recommended:** nothing is shipped or downloaded by the app; the tools and Settings say plainly that there is none (rule 11). Bundling a browser is a separate issue.
19. **Where the Playwright MCP runs, and how its network reaches only the agent's hosts.** (for the plan, decision 11) Inside the agent's sandbox, the server and its browser sit in a network namespace that only the app's proxy can leave, which forces the host list; the cost is binding the server's package and a Node into the sandbox, and that an agent's shell in the same sandbox shares the process space with the server (it could signal it). In the app's own process tree, the server is out of reach of the agent's commands, and the network is enforced by `--proxy-server` and a loopback listener the app opens per session, with the flags needed to stop non-proxied UDP, DNS and QUIC; the cost is that the enforcement is the flags, not a namespace, and the browser reaches the person's loopback unless the plan closes it. A third shape starts the browser in the sandbox and attaches the server with `--cdp-endpoint`. **Recommended:** the plan decides after a throwaway measurement, with the requirements of rules 7 and 10 as the test; prefer the shape that makes "no route around the proxy" a property of the system, not of a list of flags.
20. **Vision for canvas-based applications.** Enabling the server's `vision` capability gives tools that click at coordinates; each of those is unclassifiable and therefore held (rule 35). **Recommended:** not enabled in this issue; a canvas-based application is served by keyboard and snapshot where it offers them, and the pass of rule 35 makes the rest bearable. A per-agent vision switch is a later issue.
21. **The hand-off mask: the server's `--secrets` or the intermediary's own.** (for #178 and the plan) `--secrets` is the server's own way to keep values from the model; masking in the intermediary also covers values the server does not know. **Recommended:** the plan proves both in a spike for #178; #177 only builds the place where a mask is applied (rule 8).
22. **Reading "inside a form" and the focus.** Rule 34 holds Enter in a form field; a snapshot may not say which fields are in a form. **Recommended:** if the snapshot does not, the app reads it through the server's init-script or its own read, never a tool the agent can call; if neither is reliable, hold every Enter in a text field and let the person's per-site pass of rule 35 cover search boxes.
