# Implementation notes: the persona's tools, origin, audit and stop

What was built against `2_PLAN.md`, commit by commit, and every place it differs from the plan. The plan stays as approved; this file is where the differences are recorded.

## Commit 1: a persona origin on the call wrapper and one helper that names the door

Built as planned: `Through` in `src/shared/auditoria.ts`; `callOrigin()` with three values and `viaOf()` in `src/main/rpc.ts`; `invokePersona`; `src/main/persona/act.ts` (the leaf module of the act scope); the six comparisons turned into `viaOf()` (`turnAsks.ts`, `runner/module.ts` twice, `memory/module.ts`, `persona/assist.ts` twice); `AnsweredThrough`, `TurnAnswerer`, `MemoryAuditInput.via`, `ChannelDeps.via` and `rpcContext` widened; `test/persona-origin.test.ts`; `test/runs-policy.test.ts` and `test/errorlog-rpc.test.ts` updated.

Deviations and decisions:

- **`Act` has no `basis` yet.** The plan's interface lists `basis: ActBasis`; the type for it (`AuditBasis`) is introduced by commit 2 with the audit, so the field is added there. Everything else of the interface is as written.
- **`invokePersona` refuses a call made outside an open act.** The plan only says it runs the handler under the persona origin. Because `callOrigin()` answers `persona` only while an act is open (rule 13), a call with no open act would have read as the window, the person's own door, which is the failure this whole issue exists to prevent; it throws instead. Tests drive it through a local helper that does what the door will do (open the act, call, close it when the promise settles).
- **`openAct()` is added next to `currentAct()` in `act.ts`** (the act, only while it is open), which is what `callOrigin()` and the audit stamp consult; `currentAct()` returns a closed act too, for a caller that needs to know the scope existed.
- **No file but `rpc.ts` may name `callOrigin`**, comments included (the scan is by word), so the comment of `act.ts` says "the call origin".
- **The `by` of the memory audit line** (`o.by ?? 'person'`, `memory/audit.ts`) is left for commit 2, with the rest of the audit, as the plan has it.
- **`persona/assist.ts` keeps `through()`** as a one-line alias of `viaOf()` typed `Through`; its scope check is `viaOf() === 'paired'`, so a persona is never held to a device's scope (unreachable today, since `invokePersona` refuses `persona:` channels, and pinned by a source scan).

## Commit 2: the audit says who, and records the person's own configuration, secret and plugin changes

Built as planned: `Through`-style fields on `AuditEntry` (`actor`, `door`, `id`, `said`, `basis`, `proposedBy`), `AuditBasis` and `BASIS_LIMITS`, the four kinds (`config`, `secret`, `plugin-decision`, `act`) in `AuditKind`; the stamp and the bound and mask of `basis` in `recordWrite` (`src/main/auditoria.ts`); `Act.basis`; `src/main/configAudit.ts`; the config, secret and plugin lines in `configModule.ts` and `plugins/module.ts`; the memory audit's `by`; the Audit screen's Who filter, badge, door, reason, folded basis, "approved its own proposal" and scroll to an act (`Auditoria.tsx`, `auditModel.ts`, `Screen` member `auditoria` with `id`), both catalogs, the CHANGELOG line; `test/persona-audit.test.ts`, `test/audit-model.test.ts`.

Deviations and decisions:

- **`decisionAudit.ts` holds the secret and plugin-decision entries.** The plan puts the lines in the channel lambdas; the pure builders (`secretAuditEntry`, `pluginDecisionEntry`) are in their own file beside `configAudit.ts`, and the lambdas call them through `recordedSecret` (configModule) and `decided` (plugins). A field value that is not a reference or a plain word is dropped, so a path, a command or a value has no field to arrive in.
- **The `config` line walks lists of identified objects by id.** `changedPaths` (the phone's scope check) treats an array as one path, so every change of the team would read `agents.team`. `configAudit.ts` has its own walk that goes into an array whose elements all carry a distinct string `id` and names the element as `agents.team[me].shell` (the grammar of the settings tool of commit 6); any other array is one path. The scope check and `changedPaths` are untouched; `same` is exported from `configScope.ts`.
- **The line's fields are the paths themselves.** `fields` is `{ changed: "<count>", raised?: "<names>", "<path>": "<old> → <new>" ... }` for the first twenty paths, which the existing Audit screen draws as `key = value` lines with nothing new to learn. A value is shown only for a boolean, a number or a lowercase word of at most 24 characters whose path does not end in a name that holds text (`instructions`, `job`, `name`, `userName`, `text`, `body`, `description`, `title`, `prompt`, `command(s)`, `args`, `note`, `message`); anything else is `len=<n>`.
- **`raised` is the plan's Q2 default**: the four checks plus the workspace autonomy block going on (`runner.autonomy.<field>`) and a new entry in an agent's `allowedCommands`. It is written for the person's own saves too, since it is a function of the diff. The phone's refusal is unchanged (`configScope.ts` still refuses by the original four).
- **A save that changes nothing writes no line**, as one the validation refused writes none.
- **A handler cannot claim the stamp's fields.** While an act is open `recordWrite` drops `actor`, `door`, `id`, `said` and `basis` from the entry before it applies the act's own; outside an act they pass through as written (nobody writes them there).
- **The act's mask applies to the whole line**, not only to `said` and `basis`: `target`, every field and `result` pass through the exact-value mask, then the app's redaction (`redact`), then the log's `scrub`, while an act is open. The person's lines are untouched.
- **The `act` kind and `proposedBy` have no writer yet.** The door that writes `act` is commit 4; `audited()` filling `proposedBy` is commit 5. The type, the screen's label and the "approved its own proposal" sentence are here.
- **Plugin lines are written after the decision** (and as `ok: false` with the reason `refused` when the service threw), with the plugin, need and action read before it, since an answered request is gone afterwards.
- **`config:import-apply` writes its line only when it applied to the running workspace**, comparing the configuration before with the one it reloaded.
- **Not seen:** the Audit screen's layout (the select next to the issue box, the folded basis, the highlighted entry); it compiles and its decisions are tested as plain functions.

## Commit 3: the stop of the persona, a latch outside the configuration and the channels that use it

Built as planned: `src/main/persona/latch.ts` (the file, read once, fail closed, memory is the truth), `stop.ts` (the service over ports: `stop`, `resume`, `hold`, `holds`, `unansweredSince`), `inflight.ts` (the registry the door will fill), the singleton `personaStop()` and `setLatchEmitter` in `persona/runtime.ts`; `src/shared/personaStop.ts` (the event, the state, the channel names); `persona:stop`, `persona:resume` and `persona:state` in `personaModule`, added to `PERSONA_CHANNELS`; the held list and the latch check in `mentions/module.ts`; `answer.ts` writing no per-answer stop line when the latch is the cause; the control (`StopControl.tsx`), the banner (`StoppedBanner` in `ChatScreen.tsx`), the indicator (`PersonaIndicator.tsx` in `App.tsx`), the state in Settings › Persona, `personaStopModel.ts`, `personaStopApi.ts`, the catalogs, the CHANGELOG line; `test/persona-stop.test.ts`, `test/persona-stop-model.test.ts`, `test/persona-policy.test.ts` (the three channels).

Deviations and decisions:

- **The stop lines are four codes per door, not one with a `door` parameter.** `persona.stopped.window|paired`, `persona.stoppedInflight.window|paired`, `persona.resumed.window|paired`, plus `persona.notAnswered` (`_one`/`_other`). A parameter cannot be worded at display time in the viewer's language, and the door is part of what the line says; the in-flight acts go in as the `inflight` parameter (masked, at most 300 characters).
- **The stopped line does not carry a count of ended answers.** The plan's `count` is dropped: the text says the answer and the agents it called were ended, which is what was done whatever the number.
- **`persona:stop`, `resume` and `state` return the new `PersonaState`** (`stopped`, `since`, `door`, `waiting`), so the control takes the answer in without a second read; the module event carries the same shape.
- **A held message keeps its call line, `queued`.** The plan says the line is made as queued; on Resume the chain starts the answer and `made.queued` turns the line to started, as for any message that waited behind another. A message that was queued behind the stopped answer is held from inside the chain, at the moment its answer would begin; held messages are sorted by `seq` on Resume, because that one reaches the list after one written while stopped.
- **Clear and Delete refuse while a message waits**, as the plan's test says ("count a held message as waiting"). Nothing is left to drop when they run, so the plan's `drop` is not built.
- **`MentionDeps.latched`** is the one new dependency of `answerMentions` (does this thread belong to a stopped persona): the answer that the Stop ended keeps what it had written and writes no `runner.mention.stopped*` line. It applies to every answer in the persona's thread, the agents it called included.
- **The indicator is a fixed pill at the bottom left**, lifted over the bottom bar on a phone, not seen on a screen; `JobsDock` is at the bottom right. Not rendered by any test.
- **Not built here, as the plan has it for later commits:** the refusal of a tool call that is already on its way (the door, commit 4) and the line "a persona that asks to resume is told it cannot" (the door's unknown-operation answer, commit 4), the test that no tool operation names the three channels (the table test, commit 4). The service takes the in-flight acts from `inflight.ts`, which has no writer until the door.

## Commit 4: the door, its pinned table and the footer for the code host

Built as planned: `src/main/persona/door.ts` (the run of one call, the stop checked in the synchronous stretch before the handler, the act's scope, the stamp, the `act` and `config` lines, the line in the conversation, the thirty-line cap and its count line, the in-flight record, the ring of reads), `doorTable.ts` (the 190 operations, the four door-only, the 111 exclusions with their reasons), `args.ts`, `configPath.ts`, `footer.ts`, `session.ts`; the fallback texts (`main.forum.code.persona.act`, `.act.more`), the door's own texts (`main.persona.door.*`) and the footer (`main.persona.footer`) in both catalogs; `test/persona-door-table.test.ts`, `persona-door.test.ts`, `persona-args.test.ts`, `persona-footer.test.ts`, `persona-secrets.test.ts`, `persona-acts-chat.test.ts`, `persona-test-workspace.test.ts`. No tool is offered: the tests drive the door directly.

The table was produced from a scan of the registered names and checked against the plan: 190 + 111 = 301 channels, and the groups of the exclusion list add up as the plan's lists do (the parenthetical order of the plan's group counts is off by a few places, the lists are right: bytes 5, pairing 11, workspace 2, guard 3, scope 1, own 12).

Deviations and decisions:

- **The table is data and the hooks are in another file.** `doorTable.ts` imports nothing from the app, so the pinned-table test reads it with no module of the main process; what each operation builds, says and runs is in `doorOps.ts` (`HOOKS`, keyed `Tool.op`). The plan's `subject.ts` is folded into `doorOps.ts` (the subject is a hook like the others), and `session.ts` (the answer's session) is new, since the door and the module that answers both need its type.
- **Arguments are written in a short form** (`'run:s@!'`: name, type, `@` the target of the call, `!` required, `*` a secret value, `[a,b]` the values of an enum) and parsed by `args.ts`. A test pins that one argument name has one type inside a tool, so the flat schema of commit 6 can describe it once; where the same word meant two things the names differ (`Asks`: `decision` for a hold, `choice` for a turn limit, `verdict` for a ceremony's command).
- **A generic renderer instead of a `render` per operation.** A result is compact JSON with strings cut at 2,000 characters, lists at 60 and bytes as a size, then masked and cut at 12,000. The operations whose result is not worth giving whole have a `shape`: `Settings.get`, `getApp` and `schema` give the slice at a path and never the document (nor the secrets of the view), `Conversations.attachmentGet` gives the size and not the bytes, `Overview.audit` the newest sixty lines. Per-operation renders can be added to `HOOKS` later with no change to the door.
- **`Secrets.list` leaves out the `detail` of a secret** (the command line or the variable behind it): names, sources and whether each is available. `Secrets.read` writes its own `secret` line in its hook, inside the act, so the stamp is the act's.
- **A value given to set is masked as soon as it is validated.** An argument marked `*` (`Secrets.set`'s `value`, `Plugins.setSecret`'s) joins the answer's mask before anything runs, so a reason that quotes it, a refusal that repeats it and the lines of the act hold the masked form.
- **A handler that answers `{ ok: false, reason }` is a refusal**, as one that throws is: the same tool error, the same `act` line with `ok: false` when the handler wrote none, the same line in the conversation. The plan counted only a thrown error.
- **`Board.proposePriority`** is the door's own run over `priorityDecision` and the store's `proposePriority` (now exported, with its `Written` type), after `assertExternalWrite`; an unknown priority or a decision that cannot be written comes back as the decision's own words (`dest`). `Actions.*` subjects come from `actionSubject` (new, in `actions.ts`): the summary and the method and endpoint of the command, read from the proposal the app holds.
- **`gitlabQuick:propose` carries no footer.** The plan said its fields would be read at this commit: `QuickRequest` has no text field (a reviewer, an undraft, a job to play, a transition), so only `Board.create|update|comment` (`body`) and `Ceremonies.discussionsReply` (`body`) are host text, and a test pins that list.
- **`Board.update` and `Board.create` sign the body they are given**, also for a card that is never sent to the host (the plan accepts this).
- **`Conversations.post` still runs `forum:post`, which authors the message as the person.** The persona's authorship, with `mentions: []` so it calls nobody, is commit 5 (`Who`); until then the operation exists in the table and no tool offers it.
- **The registration scan** (`persona-door-table.test.ts`) reads `handle(` and `handleDevice(` with a regular expression, accepts a literal, the four known constant forms and the three calls that are not registrations (by file), and fails for any other first argument; it was checked by hand against a file that registers a constant and a new literal (both fail).
- **The door writes its lines inside the act**, by running them again under `runAct` after the handler settles (the async store of the handler's own work does not carry over the `await`), then closes the act and ends the in-flight record in a `finally`. The `act` line is written only when the handler wrote nothing, the `config` line only when the configuration changed and the handler wrote none; for a change the door writes the `raised` names it also puts in the chat line.
- **Not exercised by any test:** the arguments of most of the 190 operations (their order was read from the handlers' signatures and is pinned by nothing but the operations the door tests call), `Board.proposePriority` past the test-workspace refusal, and the door over the real `answerMentions` (commit 6). The `Ceremonies` and `Settings` operations that take a structured object (`minutes`, `mr`, `options`, `docs`) pass the model's JSON to the handler, which is the one that validates its shape.

### The real checks (the plan's "The real checks")

Run outside the suite, before this commit, with a throwaway script in `scratch/` (git-ignored, deleted afterwards), `env -i HOME=... PATH=...`, empty `CERIMONIAS_DATA_DIR` and `CERIMONIAS_SPECS_DIR`, on `@anthropic-ai/claude-agent-sdk` 0.3.292 in `node_modules`, with the Claude login of this machine and the model `claude-haiku-4-5`. An in-process server named `runner` with loose fields (`z.unknown().describe(...)`), the same form `runnerMcpServer` builds:

1. **The PreToolUse hook fires for a sub-agent's call, with `agent_id` set, and a deny is honoured.** A principal's call: `HOOK PreToolUse mcp__runner__Probe agent_id= undefined`, then `HANDLER ran with {"op":"principal","why":"check"}`. A sub-agent (`Agent` tool, definition `helper`) calling the same tool: `HOOK PreToolUse mcp__runner__Probe agent_id= a41d1625bd455bf22 agent_type= helper`; the hook returned `permissionDecision: deny`; the sub-agent got `tool_result ... "PreToolUse:mcp__runner__Probe hook error: sub-agents may not use this tool" IS_ERROR`; the handler did **not** run (`handlerRuns after 1b (0 expected if deny honoured) 0`). So the guard holds and the fallback (open engine only) is **not** needed.
2. **A query aborted while an in-process handler is pending: the handler keeps running to its end.** `SLOW handler started; aborting the query 1.2 s from now`, `ABORTING now`, the model got `tool_result ... "The tool call was interrupted before a result was received. It may or may not have completed on the server..." IS_ERROR`, the generator threw `Claude Code process aborted by user`, `slow finished 8 s later: 1`. The plan's assumption stands: the Stop cannot cancel a handler already running (the act is in flight and finishes, and the stopped line names it); the door carries the latch for the calls not yet started.
3. **Declared shape.** A property declared `z.enum(['alpha','beta'])`: the SDK validates it itself and refuses `zzz` with `MCP error -32602: Input validation error: Invalid arguments for tool Strict` (the handler does not run). A property declared `z.unknown().describe('alpha or beta')`: `LOOSE handler ran with {"op":"zzz"}`, nothing enforced. So `.describe` is accepted on a loose field, and the enum and the required fields are the door's to check on this path, as the plan has it. (The SDK also defers the tools behind its own `ToolSearch` step when it is given many, which the model does by itself.)

### Deviations and decisions

- **The words of 194 operations are a file of their own** (`toolDocs.ts`), one line per operation, checked by a test against the table in both directions. They were written from the names, the arguments and the handlers' comments; a few lines say less than a reader would want (`Overview.errors`, `Ceremonies.effectsCheck`) because the channel's own comment says no more. Not read by a person who knows these screens yet.
- **The size of the eleven tools is about 44,000 characters, about 11,000 tokens** at four characters to a token (descriptions 23,100 plus schemas 20,900 characters; `Runs` 6,800, `Ceremonies` 6,800 and `Settings` 6,700 are the largest). It is in the prompt of every answer of the persona, on both engines. A schema property carries "Used by: ..." (the first six operations), which is a third of the schemas; dropping it would take about 3,000 tokens off. Left in for the first real session. A decision for the maintainer if the cost matters.
- **On the open engine the schema is checked by the engine before the door sees a call** (`[tool error] Invalid arguments: $.op: must be one of [...]`, the list of operations without `resume`), so the door's own sentence about the stop ("stopping and resuming are the person's") is what a model of the Claude path reads, where the fields are loose. Both tell the model it cannot.
- **The guard is generic.** `principalOnlyGuard` matches every runner tool marked `principalOnly`, so `OpenScreen` is now held on the Claude path too; the memory's own guard is untouched.
- **The session is made in the mentions module for the persona's thread**, before the line of the call, so the activity's `mask` and the answer share it (the plan says so); `answerMentions` makes one itself when a caller gives none (a test, a ceremony never). The door a message came by is `viaOf()` read in the forum's listener, which runs inside the post's own call, and travels with the held message.
- **`MentionDeps.persona` gained `door`.** Without it the real persona has the button and nothing else, and its prompt says it changes nothing; `persona.cannot` is that sentence, used for the test copy and for a caller with no door. The prompt's old third paragraph ("you change nothing") is gone from `persona.system` (both languages). No golden covers a persona prompt; the goldens are unchanged.
- **The live text and the activity take a mask** (`live.begin(..., mask)`, `beginCallActivity({ mask })`), applied before the redaction, so a secret the persona read is hidden in the bubble, in the partial a Stop posts and in every line of the call's node and the nodes under it. The error log's context is not given the answer's mask: a failure of an act reaches it through the door's `reasonOf`, which masks.
- **Not exercised:** the tools against a real model of either engine, the quality of the descriptions for weaker models (plan risk 11), the Claude path end to end through the door (the SDK is a script in the suite and the real SDK was checked by hand as above).
