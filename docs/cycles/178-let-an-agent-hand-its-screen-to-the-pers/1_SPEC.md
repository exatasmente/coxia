# Let an agent hand its screen to the person for a login or a confidential input, and go on after

Gate 1: **waiting for the maintainer.** Nothing here is built; the plan (`2_PLAN.md`) is written only after this is approved.

Marks used below: **decided** is a maintainer decision taken in chat on 2026-10-09 (decision numbers are those of that chat); **assumed from #177** is something the spec of #177, written in parallel, is expected to deliver, and this spec only references it; **proposed — confirm at gate 1** is a product choice this spec makes and the maintainer may change; **read 2026-10-09** is a fact checked that day by reading the code on `release/0.9.0` at `040d0db5` (no test, no `tsc`, no app run).

## What is asked

The issue, in its own words:

> An agent working a site on its virtual screen will meet a login, a second factor, a payment form or any field the person should fill and the model should never see. Today it can only guess, give up, or ask for the secret in the conversation, where it would be written and read by the model.

What should happen, quoted:

> - **The agent hands the screen over**: it stops, says what it needs ("log in to this site", "type the code that reached your phone"), and the viewer asks the person to take control of the screen, on the computer.
> - **The person fills it and gives it back**; the agent continues from there. A notice on the phone says the agent is waiting for the person on the computer.
> - **What the person typed is never the agent's**: no keystroke reaches the model, the conversation or the audit log (only "the person used the screen from … to …"), and the frames of that interval are kept out of what the model sees (the recording keeps them marked, or blurs them: the refinement decides).
> - **A wait, not a failure**: the hand-off is a question to the person, with the same waiting and answering the runner already has; a stage or a conversation that waits too long says so.

Notes of the issue that this spec answers: it depends on #177 (a screen for any agent) and builds on Take control of #157; whether the agent may read the screen while the person controls it, and whether it is told what changed, is for the refinement (rules 12 and 13).

Decisions of the maintainer on 2026-10-09 that bind this issue, **decided**:

- **D5. Best effort.** The person's keystrokes and the frames of the hand-off interval are kept out of everything the **app** gives the model. The agent's processes are **not** frozen: the agent could still capture its own screen or read the page. The viewer says this plainly to the person before they type (for example "the agent's programs keep running and could read this screen"). The behaviour is the same in the sandbox and on `shell: host`.
- **D1 and D2** (of #177): the person's request authorises the task; before an irreversible step the agent asks through an app-owned confirmation tool, which is voluntary for the model, so the audit and the recording are the check. The hand-off tool of this issue is the same kind of tool and has the same limit (rule 3).
- **D3** (of #177): one persistent browser profile per agent. A login made in a hand-off is kept there, so the agent that continues is logged in, and so is a later attempt after a restart (rule 21).
- **D6** (of #177): in a conversation the agent's screen lives between messages and closes after about 10 minutes idle; the recording is an attachment of the conversation.
- **D9 (later the same day).** The agent's browser goes, as the **main path**, through an app-owned MCP server, `coxia_browser` (#177): the app drives Playwright on the agent's virtual display with the agent's profile and returns page reads to the agent. Because the app sees every action, **the values the person typed during a hand-off are masked in every page read returned to the agent**; the app knows the exact values because it holds the input events, and the keystrokes never reach the agent through the app. Playwright from the agent's own shell stays available, **without** these guarantees; there D5 stands: best effort, no frozen processes.
- **D10.** The hand-off tool is app-owned like the confirmation tool and lives in an app-owned MCP (`coxia_screen`, or inside `coxia_browser`; the plan decides). Its name here is `screen_handoff`; the MCP server's name is the plan's.

- **D11.** `coxia_browser` is built on Microsoft's Playwright MCP (`@playwright/mcp`, Apache-2.0). The app starts one per agent session and sits between the agent and it, so every tool call passes through the app. That server documents a `--secrets` option: "path to a file containing secrets in the dotenv format. Secrets prevent LLMs from accessing sensitive data."

So the promise has **two paths** and the spec keeps them apart: the **MCP path** (the agent works the page through `coxia_browser`) and the **shell path** (the agent runs its own programs in the sandbox or on the host, for example Playwright from `Shell`). A session may offer both.

## What changes for the person

- When an agent that has a screen needs a login, a code or a confidential field, it calls the **hand-off** tool, `screen_handoff`. The person gets a card where the agent works (the run, or the conversation) and, if they are away from the computer, a notice on the phone that says the agent is waiting for them **on the computer**.
- On the computer, **Take the screen** opens the live viewer with a plain warning that the agent's programs keep running and could read the screen. After one click on the warning the person types; what they type goes to the agent's screen and nowhere else. **Give back** ends the hand-off and the agent goes on.
- Nothing about what the person typed, and no picture of the screen while they had it, goes to the agent, the conversation, the audit log or the recording. On the app's browser path the app also **masks what the person typed** in every page the agent reads afterwards. The conversation says only that the person used the screen from a time to a time.
- The warning says which of these guarantees holds on which path, in plain words (rule 19).
- A hand-off that nobody takes, or that the person declines, ends with a short result for the agent; the stage or the conversation does not fail.

## Rules

### 1. The request

1. **An app-owned tool.** The agent has a tool, `screen_handoff` (D10), served by an app-owned MCP server the plan places (`coxia_screen`, or inside `coxia_browser`). It is the same tool on both paths, for both engines, and it is the one place the promise starts: the agent that works through `coxia_browser` and the agent that runs its own Playwright from the shell call the same tool and get the same card, notice, warning and withheld frames (they differ in what is masked, rule 12 and rule 28). It is offered **only** to an agent that has a live screen (the display is on and registered, as #177 defines) and is never offered to a documentation run, to a session without a display, or on a platform without Xvfb. A model that has no screen does not learn that the tool exists. (proposed — confirm at gate 1)
2. **What it carries.** Two short texts: `what` (required, what the person is asked to do: "log in to this site", "type the code that reached your phone") and `why` (optional, one sentence). Both are clipped to 300 characters, go through `redact`, and are shown as plain text, never as markup. They are the agent's words; the app adds nothing to them.
3. **It is voluntary for the model, and the spec says so.** Nothing stops an agent from not calling the tool and asking for a secret in the conversation, or from typing something itself. What the app does is make the tool the way to get the person to type, say so in the agent's prompt (rule 22), refuse the agent's browser calls and commands while the person has the screen (rule 12), mask what was typed on the app's browser path (rule 28), and make the audit line (rule 16) and the recording the check, as D2 says for the confirmation tool.
4. **What the agent gets back.** The call returns when the hand-off ends, with one fixed sentence, in English like the other tool texts: `done` ("the person finished and gave the screen back"), `declined` ("the person did not want to hand the screen over"), `expired` ("the person did not respond within N minutes"), or `unavailable` ("the screen is not available" — the display was lost, or a hand-off is already open). **The result carries no content**: no text the person typed, no picture, no description of what changed on the screen, and no timing.
5. **One at a time.** A screen has at most one hand-off open. A request while another is open, or after the person declined or the wait expired in the same stage attempt or conversation answer, is refused with `unavailable`, so a model cannot loop on the person. A request after a `done` is accepted (a second site, a second code). (proposed — confirm at gate 1)

### 2. The wait, in a stage and in a conversation

6. **In a stage: a pending record next to the pending command.** The hand-off is held like `Run.command`: a record per run, never written to the run file, handed out with the run (a new optional field, filled when the runner returns the run), resolved by the person's action and removed when the stage's signal aborts. The stage's clocks stand still while it is open, through the same `clock.pause()` the host command uses (`src/main/runner/executor.ts:451-458`). A pending command and a pending hand-off are separate records: one does not queue behind the other (today's single `asking` chain at `service.ts:430-439` is for commands only). (proposed — confirm at gate 1)
7. **Why not a question.** A question ends the stage attempt, and with it the sandbox and the virtual display (`executor.ts:955-966`): the page the agent stopped at would be gone. A conversation has no run to hold a question at all. The hand-off therefore awaits inside the tool call and keeps the screen up. (read 2026-10-09)
8. **In a conversation: the same wait through the conversation's store.** The call's clocks are paused as the host command's are (`answer.ts:344-352`). The card appears on the call's line in the thread, where #177 puts the viewer. The screen's idle close (D6, about 10 minutes) does not run while a hand-off is open or taken: the call is not idle.
9. **Clocks.** The time spent waiting is never charged to the stage's idle or total limit, and the clocks resume with their remaining time when the hand-off ends, whatever way it ends.
10. **Wait limits.** Two, fixed in code, with no setting (so no schema change). (proposed — confirm at gate 1; see open question 3)
    - **To take the screen:** 15 minutes from the request, like the conversation's command store (`ceremonyCommands-core.ts:45`).
    - **Once taken:** the hand-off ends as `expired` after 30 minutes without any input of the person reaching the screen (each delivered event restarts it). A person who is typing is never cut off; a person who walked away is.
11. **When the limit passes.** The agent gets `expired`, control is turned off, held keys are released, the interval closes (rule 14), the card and the notice disappear, and the thread says once that the wait ended without the person. The stage or the conversation **goes on**: the app fails nothing. The prompt (rule 22) tells the agent to stop and say in its answer what it could not do, which in a stage can end as a question to the person (the existing path, which waits without a limit); in a conversation it ends as an ordinary answer.
12. **While the person has the screen, the agent's calls are refused.** From the moment the person takes the screen until it is given back (or the hand-off ends), a new call of the agent is not started and not queued, and its result is a fixed refusal ("the person has the screen; wait for the hand-off result"). This covers every `coxia_browser` call (a page read, a click, a picture: the app drives the page and simply does not act while the person does) and every shell command (the gate sits in front of the serial queue of both sessions, `session.ts:314`, `host.ts:182`; on `shell: host` the refused command is not put to the person as an approval). This answers the issue's note: during the interval the agent has **no way through the app** to read the screen or run anything, and is **not told** what changed. What it already started with its own shell (a script, a browser automation) is not stopped (D5; rule 29). (proposed — confirm at gate 1)
13. **After the give-back the agent reads the page itself.** It was told only that the person finished. On the browser path the page it reads has the typed values masked (rule 28); whatever else the page shows (the account page after a login) is the agent's to see, as any page it works on.
14. **The interval.** The **hand-off interval** runs from the moment the person takes the screen (after the warning, rule 19) to the moment the hand-off ends: give-back, expiry, the stage or the call ending, the screen being lost. Closing the viewer, or the exit chord, turns control off but does **not** end the interval: the screen stays withheld (rule 18) until the person gives back or the limit passes, because the page may still show what is not for the agent's tools.
15. **Cancel and end.** The stage being cancelled, failing or being aborted, a conversation's call being aborted, or the app closing removes the pending hand-off without a result (nobody is left to read it), closes the interval, releases held keys, and the hub's `finish` builds the recording without the interval (rule 19).
16. **Audit and thread.** Each hand-off leaves, and only leaves:
    - system lines in the run's thread or the conversation's thread (catalog codes in both `main` catalogs): asked (with `what`), taken, given back, declined, expired. They are system lines, so they do not reach a model's prompt (`prompt.ts:111`).
    - **one** line "the person used the screen of {agent} from {from} to {to}" for the whole interval. The per-burst lines of Take control (`hub.ts:142-151`) are **not** written during a hand-off: a line per burst would show the rhythm of the typing, and the interval is what the issue asks to record.
    - one audit line through the GUI audit kind that #177 adds (assumed from #177): agent, `what` (clipped), the outcome, the interval, `sandbox` or `host`. No text of the person, no picture. If #177 has no such kind when this is built, the plan adds it.
    - **the step record of the browser path.** D9 has `coxia_browser` record every step it performs automatically, as material for the procedure memory (#179). The hand-off is **one step** there ("handed the screen over: {what}", and the outcome); the keys and the typed values of the interval are not steps and are never offered to the procedure memory. The person's typing is not an action of the agent.

### 3. The person's side

17. **A card where the agent works.** In a stage: next to the pending command's card at the top of the run (`RunScreen.tsx:180`), in the desktop app and in the paired browser. In a conversation: on the call's line. It shows the agent, `what`, `why`, since when it waits, and the buttons below. It is read from the hand-off record, not from the thread, so it is gone when the record is gone (restart, rule 21).
    - Desktop: **Take the screen** and **Decline**; after the screen is taken, **Give back**.
    - Paired browser: the text "The agent is waiting for you on the computer." and **Decline** (open question 4). It has no Take the screen and no Give back: they are on the `screen:` family, denied to the web by pattern.
18. **A notice.** When the hand-off starts, `notify` shows the desktop notification and pushes it to the paired phones (`index.ts:78-80`), respecting the person's notifications setting as the command notice does (`service.ts:455-459`). The notice says that the agent is waiting for the person **on the computer**. **Its text is fixed from the catalog** (agent name and, for a run, the issue reference and title, like the command notice): the agent's `what` is not put in a notice, since a push goes through a push service outside the app. The click opens the run, or the conversation (the plan finds the target; today's command notice opens a list, not the conversation, `ceremonyCommands.ts:27-30`).
19. **The warning before anything is typed.** *Take the screen* opens the live viewer with a warning in place of the control, and nothing is sent to the screen until the person clicks *I understand, take the screen*. The text, in both catalogs, says in plain words **which guarantee applies on which path**. It is built from what this agent has, and says:
    - *always:* the app keeps your typing and the pictures of this screen away from the agent's conversation, the log and the recording, and the agent is not told what you did;
    - *when the agent has the app's browser:* what you type is masked in the pages the app returns to the agent through that browser, as long as the agent has them (a masked value shows as a placeholder); the app does not return a picture of a page that shows it;
    - *when the agent can run programs (a shell, in the sandbox or on the computer):* those programs keep running while you use this screen and could capture it or read the page themselves, including what you type; the app does not freeze them and cannot see them. This guarantee is weaker than the one above;
    - *always, last:* use the screen only for what you accept those programs might see.
    For an agent on `shell: host` the text adds that the agent runs on your computer with your permissions, not in the sandbox (rule 26). If the agent has no shell at all (the browser path alone, if #177 allows one), the third line is not shown and the text says no program of the agent runs next to this screen. The warning is shown **every** hand-off, with no "do not show again", since D5 asks that it be said plainly. (proposed — confirm at gate 1)
20. **While the screen is taken.** Control is on (no separate switch), and the viewer's banner says that the person has the screen, that nothing typed goes to the agent, and that the agent's programs are still running. Clicks, wheel and keys work as in Take control (`LiveScreen.tsx:253-273`, same limits on events); the exit chord **Ctrl+Alt+Shift+Esc** (never sent) turns control off, and the person turns it on again without the warning, within the same hand-off. **Give back** is always visible in the viewer and on the card.
21. **Restart.** Neither wait survives an app restart, and the spec does not make them. In a stage the run starts the stage over by the existing rule (`transitions.ts:660-669`): the hand-off record, the control state and the connection to the display are gone, the thread already says "stage restarted", and the new attempt may ask again; if the person had logged in before the restart, the persistent profile (D3) may still hold the session. In a conversation the answer that was waiting is lost as any interrupted answer is today, and the person writes again. The card and the notice disappear because they are read from the record. Nothing of the interval was ever on disk (rule 19). (read 2026-10-09 for the stage; for the conversation see "What this step did not verify")
22. **The agent's prompt.** A text in both catalogs of the prompt, added when the tool is offered: use the tool for a login, a code, a payment field or anything the person should type; never ask for or accept a secret in the conversation or in the text of a tool; after `done`, read the page again and go on (what the person typed shows as a placeholder, which is correct); after `declined` or `expired`, stop and say what you could not do; do not call it again after those. The stage goldens that include the screen text are updated. It also says, for an agent that has both paths, to prefer the app's browser for a page that needs a hand-off. This is the instruction; the app does not enforce it (rule 3).

### 4. What is kept out of the model (best effort)

23. **No keystroke leaves the desktop window and the screen.** The input channel is the `screen:` family, denied to a paired browser (`webPolicy.ts:72,75`), and the hub keeps the events only for the call (`hub.ts:322-347`). During a hand-off nothing of them is written to: the thread, the activity record, the audit log, the run file, the error log, the recording and its marks' metadata, the tool result, or the GUI memory of #179. The only record is the interval (rule 16). The plan checks that no layer between the viewer and the hub logs the arguments of a call (see "What this step did not verify").
24. **Frames of the interval are withheld from every reader the app serves.** From the moment the interval opens, the frame read for a paired browser (`runs:screen`) answers a state of its own ("held": no picture, a short text) instead of a frame, and the frame cache and the encoded pictures are dropped (`hub.ts:214-240`), so nothing of the interval is served later. The desktop viewer of the person who has the screen gets its pictures through a read on the desktop-only `screen:` family (the plan names it), so the web policy pattern covers it from the day it exists. The order is: **withhold first, control on after**, so a phone that polls twice a second never sees a frame typed into. The cache is dropped again at give-back, so the first picture after it is read fresh.
25. **Nothing the app hands the model can carry a frame of the interval.** Today none does (the table above), and this issue adds no such path: the tool's result has none; no tool the app offers returns the live frames or the recording; the recording is not among what the agent may cite. A page read or a picture that `coxia_browser` returns **after** the interval is a read of the page as it is then, not a frame of the interval, and is treated by rule 28. This is pinned by a test (criterion 9) so a future path fails it.
26. **`shell: host`: same behaviour, weaker guarantees.** The rules above apply unchanged to an agent set to `shell: host` (D5, D9): the same card, warning, give-back, withheld frames, refused calls and masking. The browser path masks the same way on the host, since the app holds the page and the input events there too. The guarantee that is weaker is the shell path, and the viewer's warning says so (rule 19): the agent's programs run as the person, the display's socket is in the host's `/tmp/.X11-unix` and reachable by every process of that user (`host.ts:44,66`), and the environment the agent is given only has `WAYLAND_DISPLAY` and `XAUTHORITY` removed (`host.ts:75-76`), which is a convention and not a boundary. In the sandbox the display is also reachable by the agent's processes (`policy.ts:83,107`), but they are confined to the sandbox's files and network. The app does not claim more than that for either.
27. **The recording of the interval (proposal, open question 1).** **Recommended: skip.** While the interval is open the recorder is not fed new pictures: the last picture before the person took the screen stays on the video for the whole interval (the recorder already keeps the time between pictures and plays an idle stretch as a still, #157 rule 16), and the interval is marked on the timeline, so the video says "the person used the screen here". The first picture after the give-back resumes the recording. The change is in the recording's timer, which does not hand a picture to the recorder while the interval is open (`hub.ts:243-251`). Nothing of the interval is then ever encoded, written, shown by the player to a phone, or kept past a crash. The options:

    | Option | What it keeps | Cost |
    |---|---|---|
    | **Skip (recommended)** | The still of the screen before the person typed, and the mark | The video no longer shows what the person did. That is the point; the interval line, the audit line and the mark say that it was the person |
    | Keep and mark (what #157 decided for Take control, decision 6) | The full interval | A card number, a code or a password shown in clear text is on disk for as long as the evidence is kept (retention is off by default) and can be opened from a paired browser. Contradicts the issue's own wish |
    | Blur | The shape of the screen | Needs an image processing step the app does not have; large digits stay readable; a promise it cannot keep |

    Take control **outside** a hand-off is unchanged: #157's rule still keeps and marks.
28. **Masking what the person typed (decided on the browser path, proposed on the shell path).**
    - **The values.** The hub builds the typed text from the printable keys it delivered during the interval, with Backspace taken into account (Take control has no paste, #157 rule 25). It keeps it **in memory only** and drops it when the stage attempt or the conversation answer ends (and the screen with it). The app is the only party that knows it. Its forms are the typed text as it is, URL-encoded and JSON-escaped, for 4 characters or more, longest first, then `redact`, the shape of `stageMasker` on #170's branch.
    - **On the browser path (decided, D9b).** **Every page read `coxia_browser` returns to the agent after the interval is masked** with those values: the text of the page, the fields' values, the title and the address. A masked value shows as a fixed placeholder. This holds until the attempt or answer ends, not only for the first read. The same applies to anything else the app returns to the agent about a page (a list of links, a step's result). Because the app drives the page, this is not a request to the model: it cannot be skipped.
    - **A picture cannot be masked.** If the app is asked for a picture of a page that, read as text, shows a typed value (a revealed password, a code that stays on screen), it refuses the picture with a fixed sentence ("the page shows what the person typed; read it as text instead") and the text read comes back masked. (proposed — confirm at gate 1; see open question 2)
    - **How: two mechanisms, the plan must prove which one works (proposed — confirm at gate 1).**
      - **A. The server's `--secrets`.** The app writes the values the person typed into a **per-session dotenv file**, mode 0600, outside any worktree and outside what the model's Read/Grep/Glob reach (the place D3 gives the profile), and the server keeps them out of what it returns. The file exists only for the session and is **deleted at the session's end** (and swept at app start if a crash left one). The server reads the file when it starts, so how a value typed *later* reaches it (a restart of that server, which would lose the page; a reload of the file; or not at all) is part of what the plan must prove.
      - **B. The app's own masking in the intermediary.** Every tool result passes through the app (D11), so the app masks the typed values in the result itself, before the agent gets it, with the forms above. No file; the values stay in memory. It is under the app's control and testable with a fake server, but it masks only what the app knows to look at (text of the result), and the app must read the server's results in a form it can walk.
      - **Recommended: B as the guarantee, A as an extra if it proves to work.** B needs nothing unverified about a third-party option and keeps the typed text off disk. If A is used too, it is a second layer and the file's life is as short as rule 28 says. The plan builds a throwaway check of both against the real server and records which holds; if neither holds for a kind of read, that kind is refused after a hand-off rather than returned unmasked.
    - **Not recorded as steps.** The steps recorded for the procedure memory (#179) and the audit never hold a typed value (rule 16).
    - **On the shell path (proposed, open question 2).** The output of the agent's own commands (`session.ts:288`, `host.ts:152`) and, with #179, what it writes to the GUI memory go through the same masker. This is a second layer and is described as one: it catches a script that prints the typed text, and does **not** catch a picture, a split or encoded value, a value shorter than 4 characters, or what the agent's program does without printing it. The guarantee on this path stays best effort (D5).
    - How the masker lands next to #170 (not merged) is in open question 2.
29. **What the app cannot do, said once.** On the **shell path** the agent's processes are not frozen (D5). A program the agent started before the hand-off can capture the screen (`xwd`-style tools or its own X client), poll the keyboard state, read the page by the browser's debug port, or log the browser's fields, and write the result to its own files. The app does not stop it and cannot see it. The hand-off keeps the app's own paths clean, refuses new calls and commands, masks what the app returns on the browser path, and tells the person. Playwright started from the agent's shell is also outside the other guarantees of #177 (D9): what it keeps is the recording, the hosts the proxy lets through and the voluntary confirmation; the hand-off's masking does not reach a page that the agent reads with its own program. A person who wants more than that should not use a hand-off for that secret, or should use an agent that has the browser path alone.
    The browser path closes that gap only for the agent that uses it: **if the agent has a shell session as well, the shell path exists beside it**, and the warning says so.

### 5. What stays the same

30. A stage or conversation with no screen is unchanged: no tool, no card.
31. Take control, the viewer, the recording, the marks and the retention of #157 work as built, outside a hand-off.
32. The agent's `ViewImage`, `SaveEvidence` and the evidence rules are unchanged.
33. `coxia_browser`'s own rules (the hold on a submit-like action, the confirmation, the recording of steps) work as #177 specifies. The hand-off only adds the refusal while the person has the screen (rule 12), the masking (rule 28) and the one step record (rule 16).
34. The hand-off is not an external effect and not a proposal in Actions (nothing leaves the machine through the app); it is audited as rule 16 says. A test workspace does not change it.

## Out of scope

- **Freezing, stopping or killing the agent's processes** during the interval, in the sandbox or on the host (D5).
- **A hand-off started by the person** without the agent asking (typing a secret into an agent's screen on their own initiative).
- **Typing from the phone**, or giving the screen back from it: the phone is told and may decline.
- **Paste, files and clipboard** between the viewer and the screen (as in #157).
- **Telling the agent what changed** during the interval, or letting it read the screen then.
- **Changing what the confirmation tool of #177 does**, the profile, the network, the allowlist or the GUI memory.
- **Masking secrets in anything but the text the app hands the model**: pictures, the page, the agent's own files.
- **A setting for the wait limits**, the warning or the masker.
- **Operating systems other than Linux.**

## Risks

- **Two paths, two strengths.** On the browser path the app drives the page, refuses calls during the interval and masks what it returns, so the guarantee is the app's to keep. On the shell path it is best effort: the agent's processes read the same display (`policy.ts:83`), and on the host they run as the person. A person can read the warning and still type something that an already running agent script captures. An agent with both paths has the weaker one available. The warning and this spec say so; nothing else is promised (rule 29).
- **The values exist on disk briefly with `--secrets` (A).** A per-session dotenv file holds what the person typed from the moment it is written until the session ends. Mode 0600 and a place the model's tools cannot reach limit it, but the agent's shell on the host runs as the person, and a crash can leave the file until the next start's sweep. This is the reason B (memory only) is recommended as the guarantee.
- **Neither mechanism covers the agent capturing the screen through its own shell.** The server and the intermediary only see what goes through `coxia_browser`. A program the agent runs from `Shell` can still capture the display or read the page; D5 stands: best effort, processes not frozen, and the warning says so (rule 19).
- **A third-party option's behaviour is not ours.** `@playwright/mcp` may change `--secrets` between versions, may replace only in some outputs, and is a dependency the app starts per session; B does not depend on it.
- **Masking is exact-match.** A typed value that the page shows reformatted (spaces in a card number, a code split in digits, a value cut in a field) is not matched; a short value (under 4 characters) is not matched at all; a picture cannot be masked, which is why rule 28 refuses a picture of a page that shows a typed value. A false positive masks a harmless word that equals a short typed value.
- **Reconstructing the typed text from keys can be wrong.** The keys are what the viewer sent; a layout, a dead key or an autofill the page applied differs from them. The app masks what it reconstructs, not what the page ended with.
- **The step record could leak.** `coxia_browser` records every step for the procedure memory (D9c); a typed value must never reach it (criterion 11). This spec leans on #177 and #179 for that record's shape.
- **The tool is voluntary.** An agent can type a login itself (through `coxia_browser` or its own program) or ask for the secret in the conversation. The prompt discourages it and the audit and the recording show it; the app does not block it (rule 3).
- **The still in the recording can mislead.** A video that holds one picture for twenty minutes with a mark looks like an idle agent; the mark and the interval line explain it. After the give-back the recording shows whatever the page shows (the account page, a code still on screen).
- **The login becomes a cookie the agent can use.** That is the purpose, and under D3 the profile is where the agent's shell can reach it; where the agent may send it is the allowlist of #177, and on `shell: host` nothing limits it.
- **A phone that has the page open** may show one frame typed into if the order of rule 24 is wrong; criterion 7 pins it.
- **The wait limits are guesses.** 15 and 30 minutes are the maintainer's to change (open question 3). A shorter first limit fails a person who is away; a longer one holds the agent and, in a conversation, a screen and a browser.
- **Merge order with #170.** The masker lands next to an unmerged branch that bumps the config schema; this issue asks for no setting, so it does not bump it.
- **Notice target.** A conversation's notice must open the conversation; today's command notice opens a list (`ceremonyCommands.ts:27-30`). The plan checks the target exists.
- **Typed text in the masker is a secret in memory.** It lives in the main process for the attempt or answer and is never written (rule 28). It also means the browser path's guarantee ends with the attempt or answer: a later attempt on the same profile reads a logged-in page with nothing to mask (the values are not the agent's, but the cookie is, which is the purpose).
- **Phone exposure of the card.** The card's `what` and `why` are read by every paired browser, like the run's other text.
- **Public repo.** Fixtures and tests use neutral hosts (`example.com`) and a marker string, never a real credential.

## What this step did not verify

- The app, the real sandbox and the test suite were not run; nothing here was tried on a display.
- Whether a layer between the viewer and the hub (the web RPC, the error log, the IPC wrapper) logs the arguments of a failed call. The input channel throws only for a call that is not formed (`screen/module.ts:15-24`), but the plan must confirm no argument is logged.
- What a conversation's call line shows after an app restart, and whether an interrupted answer is cleaned up (the activity record). The claim in rule 21 is that it is not resumed, which is how mentions work today; the code of the activity record was not read for stale entries.
- Which screen target a conversation's notice can open.
- Whether the engines let a model call two tools at the same time (so that a command could race the start of the interval). The gate of rule 12 does not depend on it, since it is on the queue, but the order of withhold-then-control does.
- How #177 names the screen's key, the confirmation tool's record and the audit kind, and the exact shape of `coxia_browser`'s page reads (whether it returns pictures, links or other reads besides a snapshot); this spec uses only their roles and masks every read it returns. The server's name and whether `screen_handoff` sits in it are the plan's.
- The behaviour of the server's `--secrets` option: whether it replaces values in page snapshots, in text the agent asks it to type, in console and network output, in error messages and in screenshots' text; whether it matches the encoded forms; whether values can be added after the server started; and what the dotenv format does with a value that has spaces, quotes, `#` or a newline. Only the one-line description in D11 was read; the package was not run.
- Whether the app can walk every kind of result `@playwright/mcp` returns well enough to mask it (text snapshots, structured content, images, file paths), which B needs.
- Whether an agent can have the browser path with no shell session (the warning's last variant depends on it).
- That a still held for the whole interval is accepted by the recorder and the player as a long gap (the recorder keeps the time between pictures by design, `3_SPIKE.md` of #157; not tried for tens of minutes).

## Open questions

Each with the recommended answer, for the maintainer at gate 1.

1. **The recording of the interval.** Keep and mark (as #157 decided for Take control), skip, or blur. **Recommended: skip** (rule 27): the still plus the mark. It is the only option in which nothing of the interval is ever stored, and the line, the audit entry and the mark already say it was the person. Keep and mark only if you want the recording to show what the person did, and then the warning must say that the recording has it.
2. **Masking, now that the browser path is decided (D9b).** The masker on the browser path is **decided** and is in this issue (rule 28). What is open: (a) **the shell path.** **Recommended: apply the same masker to the output of the agent's commands and to GUI memory writes**, as a second layer that is cheap once the browser path has it, and keep saying best effort. The alternative is to leave the shell path unmasked and say so in the warning. (b) **Pictures.** **Recommended: refuse a picture of a page that shows a typed value** (rule 28). Alternatives: return the picture anyway (the value is then visible to the model), or never return a picture after a hand-off for the rest of the attempt. (c) **Which mechanism masks the browser path** (rule 28): **recommended B**, the app's own masking in the intermediary, with `--secrets` as an optional second layer if the plan proves it works; the alternative is `--secrets` alone, which puts the typed values in a file on disk for the session and rests on a third-party option nobody has run here. (d) **Landing next to #170.** Do not wait for it: write the collector of typed text in the hub, and for the masking take the two small functions of `maskExact.ts` (copied, same names and signatures) if #170 is not in the base when the plan starts, and reuse the file if it is, so whichever lands second has a trivial conflict.
3. **The wait limits.** **Recommended:** 15 minutes to take the screen and 30 minutes without input once taken, fixed in code (rules 10, 11). Alternatives: a setting (a schema bump), a single 15-minute limit, or a long limit in a stage with none in a conversation.
4. **May the phone decline?** **Recommended: yes.** Declining gives the agent nothing and takes no screen, and a person away from the computer would otherwise leave the agent waiting for 15 minutes. Taking the screen and giving it back stay on the desktop. The alternative is a phone that only reads.
5. **Agent calls while the person has the screen.** **Recommended: refuse both browser calls and shell commands** (rule 12), the strongest thing the app can do without freezing. Alternatives: queue them until the give-back (the agent's script then runs right after, on the logged-in page; it hides nothing but delays), or allow them (then the hand-off has no app-side guarantee during the interval at all).
6. **One hand-off after a decline or an expiry.** **Recommended: refuse a second request in the same attempt or answer** (rule 5), so a model cannot keep asking. The alternative is a cap, such as three requests per attempt.
7. **The warning every time.** **Recommended: every hand-off, no "do not show again"** (rule 19), since D5 asks for it to be said plainly and the cost is one click. The alternative is to remember the acknowledgement per agent.
8. **Where the tool lives.** `screen_handoff` in its own app MCP (`coxia_screen`, with the confirmation) or inside `coxia_browser` (D10: the plan decides). **Recommended: `coxia_screen`**, so an agent on the shell path alone (no `coxia_browser`) has the hand-off and the confirmation too, and the promise is the same tool everywhere (rule 1). Not a product question; listed so the plan does not drop it.
9. **A hand-off started by the person** (typing a secret into the agent's page on their own initiative, with the same withholding). **Recommended: later**, not here: it needs a place in the viewer and a decision on who may start it.
