# O runner / The runner

[Português](#português) | [English](#english)

---

## Português

O runner leva uma issue pelo [ciclo de agentes](cycles.md) (`agent-flow`): cria uma branch e um worktree do repositório da issue, copia a issue para a pasta do ciclo e roda, uma etapa de cada vez, o agente de cada etapa, até um gate, uma pergunta, uma falha ou o fim. O que ele faz fica no worktree e na conversa da execução; o que vai para o **host de código** (um comentário por etapa na issue, a revisão nas linhas do pull request, o push e o pull request) segue [uma regra só](#o-que-fica-no-host-de-código): ou o agente é autônomo e a escrita sai sozinha, registrada, ou espera o seu "sim" em Ações; o push e o pull request esperam um "sim" a menos que o bloco de autonomia da execução os libere (e nunca numa execução de release). Configuração: a seção `runner` em [`configuration.md`](configuration.md) e os modelos de comentário em `devCycle.comments` ([`cycles.md`](cycles.md)).

### Começar uma execução

`runs:start(ref)` (a referência do cartão, como `app#101` ou só `101`). Uma execução começa sempre por uma issue lida do host: um cartão que existe só no **quadro do próprio workspace** nunca inicia uma execução, porque o quadro não é o tracker; um cartão que virou issue no host é uma issue que o host lista, e inicia uma execução como qualquer outra. O app lê a issue e os comentários pelo provedor, só leitura, e então:

1. Escolhe o repositório: o único de `projects.repos` com o `projectPath` do projeto de issues (ou o único que existe, ou o que a chamada nomear); sem cópia local ele procura uma pela origem.
2. Busca a branch padrão da origem (uma leitura) e cria o worktree em `<worktreesDir>/<repo>/<n>-<título>` numa branch nova `cycle/<n>-<título>`. Uma branch ou uma pasta que já existe é recusada, nunca reaproveitada.
3. Escreve `docs/cycles/<n>-<título>/0_ISSUE.md` (título, endereço, rótulos, descrição e comentários humanos, com o que parece credencial mascarado) e faz o commit `feat: add the issue record #<n>`.
4. Liga ao worktree as pastas de dependências do seu clone (veja [Dependências do clone](#dependências-do-clone)), abre a conversa da execução e entra na primeira etapa. Quem inicia a execução inicia também a primeira etapa.

Só há uma execução por issue por vez, e só em um workspace cujo ciclo é o ciclo de agentes. Se qualquer passo falha depois de o worktree existir, o worktree e a branch que esta chamada criou são removidos: é a única coisa que o runner apaga.

### Dependências do clone

Um worktree nasce sem `node_modules` nem `.venv`, e sem eles os comandos que o app roda antes da QA e o `npm test` de um agente que escreve falham com `vitest: not found` (código 127). O clone da pessoa costuma tê-los instalados, então o app **liga** o que falta: para cada pasta de dependências que o clone tem e o worktree não (`node_modules` e `.venv` na raiz, uma pasta abaixo, como `sidecar/.venv`, e sob `packages`, `apps`, `libs` e `services`, como `packages/a/node_modules`; no máximo 30), cria no worktree um link simbólico para a pasta do clone. Isso acontece quando a execução começa e de novo antes de toda etapa que roda comandos (um agente com permissão `worktree` e os comandos do app antes da QA), então uma execução criada antes disto, ou devolvida para uma etapa, recebe os links na próxima etapa assim.

- **Só onde o repositório ignora a pasta** (`git check-ignore`, antes de criar o link), para o app nunca a commitar. Como um link não é uma pasta para o git, `node_modules/` no `.gitignore` não cobre o link: o `git add -A` e a conferência de mudanças do app deixam `node_modules` e `.venv` de fora pelo nome.
- **Nunca por cima de algo que já existe**, e só dentro de uma pasta do worktree que é de verdade (não um link).
- A conversa diz uma vez quais pastas foram ligadas, ou que o clone não tem nenhuma (a QA pode não conseguir rodar os testes; instale no clone e a próxima etapa que roda comandos liga).
- **Os comandos rodam com as dependências do clone**, que é o objetivo: um `npm test` ou `npm run typecheck` usa e pode mudar o que está lá (um `npm install` dentro do worktree escreveria no clone). Um agente, por outro lado, **não escreve** por esse link: o guarda recusa um caminho que sai do worktree por um link simbólico, e isso vale para `node_modules` ligado também.
- Desligue com `runner.linkDependencies: false` (padrão: ligado; um config guardado sem o campo vale ligado). Está na aba do runner, também no navegador pareado.

### Uma etapa

Para a etapa atual, o agente dela recebe um prompt montado pelo app: o trabalho e as instruções do agente, os documentos que a etapa precisa produzir, o conteúdo da pasta do ciclo até agora (a issue e os documentos anteriores), as últimas mensagens da conversa, o recado que outra etapa deixou para ele e a resposta da pessoa a uma pergunta dele. Tudo que veio de fora (issue, comentários, conversa, arquivos, diff) entra entre marcas `<data>` e o texto de sistema diz que é material, não instrução. Os textos estão no catálogo como `prompt.<família>.runner.*`.

**Os documentos não repetem o cabeçalho da issue.** O prompt pede que cada documento abra com um título só dele, sem a referência, o título ou o endereço da issue (a pasta e o nome do arquivo dizem de que issue é), e que o título da nota de lançamento diga o que mudou, sem a referência interna (`app#101`). O app também arruma o que vier assim ao gravar: tira a referência e o título da issue do título do documento e, logo abaixo, as linhas de endereço, estado, rótulos e autor que o registro da issue já tem; uma lista que seja outra coisa (tipo, prioridade) fica.

**Só se afirma o que foi verificado.** O texto de sistema de todo agente do runner manda dizer só o que a etapa verificou (leu, rodou ou viu funcionando) e marcar o resto como não verificado; a regra do comentário repete isso, e a orientação das seções dos modelos de comentário do ciclo de agentes também (como foi conferido na implementação e no PR, o que só foi lido na QA, o que ficou sem verificar). É texto para um modelo: o app não confere se a afirmação é verdadeira. As regras de leitura e de escrita também mandam olhar em volta com as ferramentas Read, Glob e Grep, e não com `ls`, `find` ou `pwd`, que não estão na lista e são recusados.

**A QA não roda nada, mas recebe resultados.** Antes da etapa de QA o **app** roda, no worktree da execução e sobre o código entregue, os comandos que o workspace permite (`runner.commands`; sem lista, os scripts de teste e typecheck do repositório): cada um como um comando simples, sem shell, com o ambiente limpo de tudo que parece credencial, até 5 minutos, a saída cortada no fim (onde um teste diz o que falhou) e mascarada. A QA lê os resultados (comando, código de saída e o fim da saída) no prompt, junto do que leu no código; o agente continua só lendo, a menos que esteja com `shell: sandbox`: aí o app roda esses comandos dentro da sandbox dele e o agente roda os seus ([abaixo](#o-que-um-agente-pode-ler-e-rodar)). Os códigos de saída ficam em `Run.qa[].commands` (a saída não), e a conversa diz o que rodou. Sem comandos configurados o prompt diz que o comportamento não foi exercitado, só lido. Cada cenário da QA traz uma **gravidade** (`blocking` ou `non-blocking`): só uma falha que bloqueia devolve o trabalho; a que não bloqueia vai para o comentário e a conversa. **Comando que não pôde rodar não é resultado do código:** `ENOENT`, `EACCES` e os códigos 126 e 127 do shell (a ferramenta que o script usa não foi achada) ficam em `Run.qa[].commands` com `notRun: true`, a conversa diz quais comandos não rodaram e por quê (`npm não foi encontrado pelo app` ou o que o shell disse, como `vitest: not found`), e o prompt da QA marca esses comandos e manda **não aprovar cenário que dependa deles**: marcar `not-run` e dizer por quê. Os comandos do app (os da QA, os que os agentes que escrevem podem rodar, o `runner.commands`, a verificação dos conflitos e as CLIs do host de código) começam com o **`PATH` do shell de login** da pessoa na frente do `PATH` do app (lido uma vez, no início do app, com `$SHELL -ilc` e um tempo limite; as pastas do próprio AppImage ficam de fora): um app aberto pelo menu da área de trabalho não herda o `PATH` do terminal, e é nele que o nvm e os gerenciadores de versão põem o `npm`. A limpeza de credenciais não muda. `COXIA_NO_LOGIN_SHELL=1` desliga a leitura (os testes a usam).

A resposta é estruturada: `summary` (o que fez, para a conversa), `commit` (o assunto do commit do código: em inglês, no imperativo, em minúsculas, sem prefixo de tipo nem número de issue; o app tira o prefixo e a referência que vierem, e usa o texto da própria etapa quando o resumo não parece inglês, fica vazio, ou a etapa só escreve documentos ou terminou a passada sem mudar código), `artifacts` (nome e conteúdo completo de cada documento), `handoff` (o que a próxima etapa deve fazer), `question` (algo sem o qual não dá para seguir: pausa a etapa e vai ao agente a quem o autor recorre, depois à pessoa), `needsPerson` (a pergunta é uma decisão só da pessoa: vai direto a ela; se o agente marca isso e não escreve a pergunta, o app faz a pergunta com o que ele disse no resumo, em vez de dar a etapa por terminada), `reporterQuestion` (na **primeira** etapa do fluxo: algo que só quem abriu a issue sabe), `priority` e `milestone` (só na etapa que é dona da prioridade, a última etapa de trabalho do `backlog` que tem agente, como o refinamento do Product Owner, quando o workspace tem rótulos de prioridade graváveis: uma proposta; as etapas de backlog antes dela, como a triagem, recebem os níveis e só sugerem um no documento, e um valor que viesse mesmo assim é dito na conversa como não proposto; a chave da proposta leva a etapa e a tentativa, e quando nenhuma proposta nasce — repetida, sem host, host sem escrita de rótulo, rótulo que não se grava — a conversa diz por quê) e, quando o ciclo tem modelo de comentário para a etapa, `comment` (um texto por seção do modelo, mais `technical`; a etapa que termina com o push traz também `pr`, o título e as seções da descrição do pull request), `memory` (a versão nova da memória do ciclo, que a etapa que conclui reescreve; vazia quando a etapa pausa numa pergunta — veja [A memória do ciclo](#a-memória-do-ciclo)). A etapa de revisão acrescenta `verdict` e `findings` (cada um com `path`, `line`, `endLine`, `side`, `severity` `blocking` ou `suggestion`, `body` e `suggestion`, a troca exata das linhas comentadas, só quando completa); a de QA acrescenta `scenarios` (`name`, `result` `pass`, `fail` ou `not-run`, `detail`). Quem escreve os documentos e faz o commit é o **app**, nunca o agente: um agente que só lê produz os documentos da mesma forma, e um documento que a etapa não lista é ignorado (e dito na conversa). Um documento é nomeado só pelo nome do arquivo; um nome que vem com a pasta é lido pelo nome do arquivo, e um nome que não se pode gravar (oculto, com `..`, vazio) é deixado de fora e dito na conversa. Uma resposta que conclui a etapa e deixa de fora um documento que ela produz (e que não está na pasta do ciclo) é pedida **uma vez** a esse documento, na mesma sessão do agente, antes de a etapa falhar; só os documentos que faltavam são tirados dessa rodada, e o resto da resposta fica como veio.

Depois da resposta o app aplica a transição, **pelos campos da etapa** (não por uma ordem do código): uma pergunta pausa a execução (e anda pela cadeia de agentes, abaixo); uma pergunta a quem abriu a issue deixa a etapa esperando a resposta na issue; `blocking` (ou `verdict: changes`) devolve o trabalho à etapa que o `returnsTo` da revisão diz, com os achados como recado, e conta uma devolução para essa etapa (ao chegar no `roundLimit` da etapa que devolve a execução para e pergunta); um cenário de QA que falha devolve do mesmo jeito, na mesma conta; qualquer outro caso é a etapa concluída e a execução vai ao `next` dela (ou termina, se não há). Os achados de cada rodada e os cenários de cada passada de QA ficam na execução (`Run.reviews`, `Run.qa`), do jeito que foram dados: é de onde os comentários de linha serão montados.

### A memória do ciclo

A pasta do ciclo guarda, além dos documentos das etapas, um arquivo de nome fixo: **`MEMORY.md`**. É a memória da execução, e existe para que uma execução longa não perca uma decisão nem para o orçamento de leitura da pasta nem para a janela de 40 mensagens que a etapa recebe da conversa (veja [Uma etapa](#uma-etapa) e [`cycles.md`](cycles.md#a-memória-do-ciclo)). Toda etapa a lê inteira, antes dos documentos, e a etapa que conclui a reescreve a partir da resposta.

- **Forma fixa.** O título e as seções na ordem **Decisões**, **Restrições**, **Tentado e descartado**, **Perguntas abertas** e **Onde o trabalho está** (no idioma do workspace). O que a etapa devolve é normalizado à forma do arquivo: uma seção que faltou volta vazia, uma inventada é descartada e os espaços em branco se juntam. A etapa que pausa numa pergunta não escreve nada.
- **O que entra sozinho.** Antes de montar o texto, o app acrescenta à memória cada resposta da pessoa e cada passagem da conversa, cada uma numa linha marcada com o número da mensagem (`<!-- answer:3 -->`, `<!-- handoff:5 -->`): reescrever não duplica nada, e o que a pessoa decidiu e o que uma etapa passou à seguinte sobrevivem mesmo depois de a conversa passar da janela. A etapa que conclui reescreve o resto, e os marcadores são reaplicados por cima do que ela devolveu.
- **O tamanho.** O teto é uma constante de código, `MEMORY_MAX` (`10.000` caracteres): não é configuração e não há migração de config. Passando do teto, o arquivo continua sendo lido inteiro e o prompt diz à etapa o limite e manda encurtá-lo.
- **A pessoa pode corrigir.** Na tela da execução a memória abre para edição (só ela): `runs:memory(id, texto)`. O app grava a versão da pessoa, commita com a identidade do workspace (a mensagem do commit diz "update the cycle memory") e registra no histórico (`memory-edited`, `by: person`) e na conversa (`runner.memory.edited`) que a edição foi da pessoa, não de um agente; a etapa seguinte lê a versão corrigida. A edição é recusada enquanto um agente trabalha na pasta (`memory-busy`) — a pessoa nunca disputa o arquivo com um agente.
- **Sem host de código.** A memória vive no worktree e vai nos commits da execução, como os documentos: nada dela sai para o tracker por si, e editá-la não passa por `Actions`.

### O registro das atividades

Além da memória de uma execução há um registro de **todas as atividades do espaço de trabalho**, para que um agente chamado em qualquer lugar — a conversa de uma execução, o canal de um squad, a conversa geral, a conversa direta de um agente — saiba responder o que está em andamento, e para que um reinício não perca onde cada atividade parou. Não é um documento que um agente reescreve: é um índice que o app projeta do estado que já guarda (o store de execuções), e o agente recebe um **recorte** dele, nunca o arquivo.

- **Onde mora.** `<workspace>/memory/activities.json`, na pasta do espaço de trabalho que o app já possui (a mesma de `historico/`, `atividade/`, `qa/`; `ATAS` em `env.ts`). Fica fora de todo worktree, então nunca entra num pull request nem num commit da atividade. Nada dele passa por `Actions`: ele nunca alcança o host de código.
- **Uma frente por atividade.** A chave é a referência que a execução escreve (`app#101`; `release:X.Y.Z` e `docs:<repo>` nos assuntos sintetizados). Uma segunda execução da mesma issue atualiza a mesma frente; nunca são duas. A frente traz a referência e o título, onde a atividade está agora (a etapa do ciclo, ou que está entre etapas, ou que terminou), o agente que a trabalha e o último agente a mexer nela, as decisões e as perguntas em aberto, onde o trabalho parou e o instante da última atualização, mais o que a pessoa escreveu por cima.
- **O app é o único escritor.** Todo movimento de uma execução passa pelo store, e é lá que ele mantém a frente da atividade em dia: um escritor, mescla por chave, escrita atômica. Um movimento que não conseguiu gravar é registrado no log e engolido — um movimento de execução nunca falha por causa deste arquivo — e o leitor reprojeta aquela frente do store de execuções, então a perda se recupera sozinha. Duas atividades avançando no mesmo instante são duas chaves.
- **Ela nasce antes da primeira execução.** O início grava a referência quando a identidade e o repositório já são conhecidos e antes de o worktree ser feito, então um início interrompido ali deixa um registro da atividade ("conhecida, nunca iniciada") em vez de nada. Um início recusado antes desse ponto não registra nada.
- **O que uma chamada vê.** Uma mensagem que nomeia uma atividade (a referência ou o número que ela carrega) ou um agente recebe a frente inteira do que nomeou; sem nada nomeado, uma linha por atividade em andamento, mais uma linha dizendo que se pode nomear uma para vê-la inteira. Toda etapa recebe a frente da própria atividade inteira, mais a lista curta das outras. A seção é própria, entre `<data>`, com uma linha dizendo que é material do app e não instrução; o registro nunca entra em ferramentas, em `allowedTools` nem nas raízes de confinamento, então a única saída dele é texto no prompt.
- **O antigo não vira mentira.** Nada é apagado, e uma frente cuja última atualização passa de `STALE_AFTER_MS` (30 dias) é renderizada como provavelmente encerrada, junto do que ela registra. A resposta de uma chamada é limitada (`SELECT_MAX`), e uma frente que não couber é nomeada numa linha, nunca cortada no meio.
- **A pessoa vê e corrige, sem chamada de modelo.** A tela de execuções lista as atividades (`runs:activities`), uma linha por atividade com referência, título, etapa, agente e onde parou, e uma abre para edição; a correção é gravada por `runs:activitySave`, mascarada e com teto, marcada como da pessoa, e vale até a atividade voltar a andar. Os dois canais são abertos ao navegador emparelhado como todo `runs:*` de leitura e movimento, e nenhum modelo é chamado no caminho.

### Autonomia, escalonador e reinício

- Agente **autônomo**: a etapa começa quando a execução chega nela e o resultado segue adiante sem esperar. Agente que **espera**: a etapa fica em `to-start` até a pessoa iniciar (`runs:startStage`), e o resultado fica em `to-accept` até a pessoa aceitar (`runs:accept`) ou devolver com um recado (`runs:return`). Mudar a chave (`runs:setAutonomous`) vale a partir da próxima etapa, nunca no meio de uma. Os gates não mudam.
- Uma execução guarda a **cópia do fluxo** com que começou e a segue depois de o ciclo ser editado (`runs:migrateFlow` a passa para o fluxo atual quando a etapa dela ainda existe lá e é do mesmo tipo). Antes de iniciar, o runner roda a verificação do fluxo e se recusa se houver erro. As etapas `wait` seguram a execução (`waiting`) até o evento (`pr-merged`, `reporter-reply`, `label`, `time`; `linked-done`: o runner a resolve sozinho, veja [Squads](#squads)): a mesma passada de 5 minutos olha o host (`runs:skipWait` deixa a pessoa seguir sem esperar, com motivo; só anda para a frente: para devolver o trabalho a um agente há `runs:sendBack`). Uma etapa com `trackerStatus` põe o rótulo na issue ao entrar e o tira ao sair, pela autonomia do agente (a de um gate ou de uma espera espera um "sim").
- Com `runner.enabled`, um trabalho a cada 5 minutos lista as issues abertas atribuídas à pessoa que levam o rótulo `runner.triggerLabel` e inicia execuções até `runner.maxConcurrentRuns` execuções **trabalhando** ao mesmo tempo (uma execução parada em um gate não conta). Uma issue que já teve uma execução, em qualquer estado, não é iniciada de novo sozinha: sem isso uma execução cancelada voltaria a cada passada. Uma issue que o app não consegue iniciar (sem cópia local, sem identidade) é tentada uma vez por sessão. O mesmo trabalho olha, na mesma passada, o que as execuções que esperam aguardam (pull request mergeado, resposta, rótulo, o tempo) e posta as revisões que esperavam o pull request. A passada **nunca espera uma etapa terminar** (as etapas rodam por conta própria, e uma que demora não atrasa as esperas das outras), e uma passada que ainda está andando não é iniciada de novo; se uma das três olhadas falha (o host caiu), as outras acontecem e a falha é registrada.
- Ao abrir o app, uma execução que estava no meio de um agente recomeça aquela etapa (nova tentativa); as que esperavam a pessoa continuam esperando. Uma etapa é interrompida (e a execução fica `failed`) por dois limites: `runner.stageIdleMs`, o **silêncio** do agente (nenhum sinal do modelo, nem texto, nem ferramenta, nem relato de uso, por esse tempo; quem trabalha sem parar nunca chega a ele, por mais que demore), e `runner.stageMaxMs`, um teto de **relógio** generoso para a etapa que não termina mesmo falando. A mensagem diz qual dos dois foi. A execução fica `failed`, com tentar de novo (`runs:retry`) ou cancelar (`runs:cancel`). Cancelar interrompe o agente e não apaga nada: o worktree, a branch e a conversa ficam até a pessoa removê-los.
- **Pedido de plugin** (`wait.kind: 'plugin'`). Um plugin que precisa de rede ou de escrita sem ter permissão abre um pedido em Ações; enquanto um pedido da execução espera, a execução não começa a etapa seguinte e fica `waiting` com `plugin` e `detail` (o que ele pede) no `wait`. Responder (uma vez, nesta sessão, sempre ou recusar, em Ações, no computador) a solta quando não sobra pedido dela; uma recusa vai para a conversa e a execução segue. `runs:skipWait` também segue sem responder (o pedido fica em Ações). Veja [`plugins/`](plugins/README.md).
- **Orçamento da chave esgotado** (`wait.kind: 'budget'`). Quando o provedor recusa a chamada porque o orçamento da chave dele acabou (HTTP 402; um 403 cujo corpo fala de limite, cota, crédito ou saldo; um 429 que não passa), a etapa **não falha**: ela espera, com o motivo em palavras simples nomeando o provedor, e a execução fica `waiting` com `provider` e `detail` no `wait`. O retry não é oferecido (a ação é "seguir sem esperar o provedor", `runs:skipWait`, ou devolver para uma etapa). O texto que o provedor devolveu — mascarado como o resto do texto de fora — também vai à falha genérica quando a chamada termina sem saída estruturada, em vez de só o subtipo do SDK. Enquanto houver um provedor sem orçamento, nada novo começa nele: a próxima etapa de uma execução que esperava, uma execução nova (`scan`) e uma menção (`@agente`) ficam seguradas, e a conversa diz por quê. A passada de 5 minutos faz **uma** chamada de sondagem por provedor (nunca uma por execução); quando ela passa, todas as execuções que esperavam por aquele provedor seguem de onde pararam (`waitDone`).

### Devolver para uma etapa

- `runs:sendBack(id, etapa, nota)` é a decisão da pessoa de mandar o trabalho de volta a um agente: de uma **espera**, de um **gate**, de uma etapa a iniciar ou a aceitar, de uma falha, de uma pergunta (menos a do squad) e **do fim** (a execução é reaberta: volta a `working`, e o histórico registra `reopened` e `sent-back` com quem e por quê). Uma execução cancelada não volta, e uma execução parada porque um agente trabalha, também não. Reabrir uma execução terminada é recusado enquanto outra execução da mesma issue estiver em andamento.
- O destino é qualquer etapa de **trabalho** anterior do fluxo da execução que tenha agente. Sem etapa, vale o padrão: o `returnsTo` da etapa atual, a menos que ele só verifique (revisão ou QA: devolver para lá não refaria nada); então a etapa anterior mais próxima cujo agente altera o worktree (a implementação).
- A nota vira um **recado da pessoa** para o agente da etapa, junto do que a revisão e a QA deixaram em aberto desde que a etapa começou pela última vez: os achados da última rodada de revisão (os que bloqueiam e as sugestões) e os cenários da QA que não passaram ou não puderam ser conferidos, com os comandos que não rodaram. Sem nota, o que está em aberto é a instrução; sem uma coisa nem outra a devolução é recusada. Com nota, a nota vem primeiro e o que ficou em aberto vem depois, marcado como contexto do pedido, não como trabalho novo: uma nota que estreita o trabalho ("refaça só as evidências") não é desfeita pela lista.
- **Toda etapa que roda de novo sabe por quê.** Devolvida pela pessoa, devolvida pela revisão ou pela QA, repetida depois de uma falha ou retomada depois de o app reiniciar (lido do histórico da execução), o prompt abre com o motivo, o pedido desta tentativa dito uma vez (fora da janela da conversa e sem a seção de recado no fim), os documentos da etapa que já estão na pasta do ciclo, as comprovações que ela já guardou e o último relato dela. O agente é instruído a fazer o que foi pedido e só isso, a deixar fora de `artifacts` o documento que não muda (o app mantém o que está na pasta) e a devolver `memory` vazia para manter a memória; a QA repete como o plano de testes registra os cenários que não confere de novo. Uma etapa retomada por uma resposta continua com a seção da resposta, sem esse bloco.
- A etapa recomeça de uma vez, como **nova tentativa**, mesmo que o agente espere a pessoa. **Não gasta** as rodadas da revisão nem da QA (é decisão da pessoa, não um achado). As etapas seguintes rodam de novo na ordem: a revisão vê a rodada N+1 com as anteriores, como sempre. A etapa que se deixa fica como estava ao terminar (uma espera vira `skipped`; o que esperava a pessoa vira `rejected`).
- O que vai ao tracker: o comentário de cada etapa que roda de novo é **editado no lugar**, como sempre. O comentário da etapa final que já foi postado não é postado de novo, a menos que ela rode de novo (então é editado; se foi desfeito, é postado outra vez).
- Na tela (`Devolver para uma etapa`): o seletor de etapa com o padrão marcado, a caixa do que pedir e um clique. A ação do estado de espera se chama **`Seguir sem esperar o merge`** (ou `… a resposta`, `… a label`, `… a issue ligada`, `… o prazo`) e diz para onde segue (`Segue para frente, para a etapa …`): ela só anda para a frente. Se o motivo digitado nela cita um agente com `@` ou lê como um pedido de devolução (`volte`, `devolva`, `refaça`, `go back`, `send back`, `return`…), a tela não segue: oferece devolver (com `Seguir mesmo assim` à mão). Uma mensagem da pessoa na conversa da execução que cita um agente continua chamando o agente só para ler; com a execução esperando ou encerrada, a caixa avisa que isso não devolve o trabalho e leva à ação de devolver.

### Perguntas e menções

Uma pergunta do agente pausa a etapa, avisa pelas notificações do app e é respondida por `runs:answer` ou por uma mensagem da pessoa na conversa da execução (a mensagem vira a resposta, e a etapa recomeça com a pergunta e a resposta no prompt). Uma mensagem que cita um agente (`@developer ...`) não é resposta: chama aquele agente, que responde na conversa **sem nunca escrever na execução**, qualquer que seja a permissão dele (a chamada não tem Edit nem Write). Um agente com comandos (`shell: sandbox` ou `host`) recebe a sessão dele sobre uma **cópia descartável** do código, para reproduzir o que perguntaram (em `host`, cada comando espera o seu sim, como numa etapa); onde a sandbox não pode ser feita, ele responde sem comandos e a conversa diz por quê. Um agente que lê o host de código (`tracker: read`) pode **propor uma issue** junto da resposta (título, corpo e rótulos): ela vira uma proposta em Ações, sempre esperando o seu sim (nunca é criada sozinha, nem com o agente autônomo), e a conversa recebe o link quando a issue é criada. Só a mensagem de uma pessoa chama alguém.

**Limite de passos dessas chamadas.** Um agente chamado com `@`, um agente que responde a uma pergunta da cadeia e um agente que responde a um pedido entre squads só leem, e usam o mesmo limite de passos de uma etapa que só lê (`runner.turns.read`, em Configurações › Runner), lido a cada chamada. Se o agente gasta todos os passos sem responder, o app retoma **uma vez** a mesma sessão, **sem nenhuma ferramenta** e com 2 passos, pedindo que responda com o que já leu; a resposta vale como as outras e a conversa avisa que o agente ficou sem passos e que ela pode estar incompleta. Se essa segunda tentativa também falha, ou não há sessão para retomar, vale a mensagem de falha de sempre, com o motivo. Uma etapa não ganha essa segunda chance: ficar sem passos nela continua sendo falha, para que ninguém dê uma etapa por concluída com meia resposta.

**Um agente chama outro numa conversa.** Um agente que responde numa conversa — a conversa direta dele, o canal de um squad, a conversa geral ou a conversa de uma execução — tem a ferramenta `CallAgent`: pergunta a outro agente do time sobre um ponto (o PO ao tech lead ou ao suporte, o desenvolvedor ao tech lead, a QA ao desenvolvedor). A pergunta entra na mesma conversa citando o outro, o outro responde ali **só lendo**, como numa menção, e a resposta volta a quem chamou, que termina a sua. O chamado também pode chamar um terceiro. Uma chamada de volta a um agente que já está na troca é recusada, e uma resposta faz no máximo `runner.conversations.perStage` chamadas. Os relógios de quem chamou param enquanto o outro responde. Numa cerimônia a ferramenta não é oferecida.

**Os agentes conversam antes de perguntar à pessoa.** A pergunta de um agente vai primeiro ao agente a quem ele recorre (`turnsTo`), na conversa da execução; esse agente é chamado **só lendo** e responde em forma estruturada (`answer`, `pass` com um motivo ou `needs-person`). `answer` faz a etapa de quem perguntou seguir com a resposta, sem a pessoa; `pass` leva a pergunta a quem ele mesmo recorre (a pessoa, se a ninguém); `needs-person` e uma decisão marcada `needsPerson` vão direto à pessoa. Cada passo é uma mensagem na conversa (a pergunta de um para o outro, o motivo, a resposta), a execução fica em `question` enquanto a cadeia anda, a pessoa só é avisada (e a pergunta só vai à issue, pela autonomia de quem perguntou) quando ela chega nela, um limite de 4 passos sobe a pergunta à pessoa de qualquer jeito, e uma resposta da pessoa em qualquer ponto encerra a cadeia. Um agente que falha, ou que saiu do time, também sobe a pergunta. Nenhum agente decide um gate.

### Agente que escreve

Um agente com permissão `worktree` roda com a pasta de trabalho no worktree da execução, nos dois motores, com **uma só função de guarda** (`src/main/engine/guard.ts`) na frente de cada escrita: no Claude Agent SDK ela é um hook `PreToolUse` sobre `Edit`/`Write`; no motor aberto são as ferramentas `Write` e `Edit` (que chamam a mesma função de novo, por dentro). As regras:

- Só caminhos dentro do worktree. Recusados: absoluto fora dele, `..` em qualquer lugar do caminho, `~`, um link simbólico no caminho que leve para fora (também para uma pasta e um arquivo novo sob ela), um link que não leva a lugar nenhum, a própria raiz.
- Nada dentro de `.git` (qualquer profundidade, qualquer caixa, nem por um link para ele), nem `.husky`, `.githooks`, `.gitattributes`, `.gitmodules`. Arquivos de segredo (`secretPath`) também não.
- Leitura (`Read`, `Grep`, `Glob`) só no worktree e fora de `.git` e dos segredos.
- Shell só para os comandos de `runner.commands`, **exatamente como escritos**, quando o agente está com `shell: allowlist` (com `none` não há shell; com `sandbox` os comandos vão para a sandbox, abaixo) (a mesma máquina do `shellAllowlist` das cerimônias, com uma lista própria); sem a lista, só `Read`/`Grep`/`Glob`/`Edit`/`Write`. No motor aberto o comando roda sem shell e com o ambiente sem variáveis que parecem credencial; no Claude Agent SDK, cujo processo precisa da chave do provedor, cada comando liberado é reescrito para começar com `env -u NOME` para cada variável que parece credencial (o comando é conferido, caractere por caractere, antes de ser reescrito).
- Sem rede (`WebFetch`, `WebSearch`), sem `git push`, sem MCP; do host de código, só a ferramenta `VcsRead` e só com `tracker: read`.
- Toda recusa vai para a conversa da execução como uma mensagem do app (quem, qual ferramenta, o quê, por quê) e aparece como "bloqueado" na atividade ao vivo.

### Agente que só lê

Um agente que só lê numa execução — uma etapa de leitura (refinamento, revisão, QA, e qualquer etapa cujo agente não tem a permissão `worktree`), um agente chamado com `@` na conversa da execução e um agente que responde a uma pergunta da cadeia — recebe o **mesmo guarda de caminho** que o agente que escreve, pelas mesmas três ferramentas (`Read`, `Grep`, `Glob`), nos dois motores. A raiz é o **worktree da execução** (a pasta do ciclo, dentro dele, inclusive): o que estiver fora deixa de ser lido. As regras de recusa são exatamente as de quem escreve — absoluto fora, `..` em qualquer posição, `~`, um link simbólico que leve para fora, um link que não leva a lugar nenhum, qualquer coisa dentro de `.git` e um arquivo de segredo — e a recusa é dita do mesmo jeito: uma mensagem do app na conversa da execução (o agente, a ferramenta, o alvo e o motivo) e a chamada marcada como bloqueada na atividade ao vivo.

O campo é próprio (`readRoot`, ao lado do `confine` de quem escreve) e não abre nada: um leitor confinado continua **sem `Edit`, sem `Write` e sem shell**. O que já valia por cima continua valendo, porque os hooks **somam**: o filtro de arquivo de segredo, a censura do resultado de busca e a recusa de busca ampla não são substituídos pelo guarda, e sim postos na frente dele e ao lado. As pastas de documentação que a configuração lista fora do worktree (as mesmas que o motor recebe como diretórios adicionais, sem as achadas por auto-detect dentro da pasta de trabalho) continuam alcançáveis: são as raízes extras do guarda. Uma pasta de documentação achada por auto-detect **fora** da pasta de trabalho deixa de ser alcançável pelo leitor.

Fora de uma execução nada muda: um agente chamado num canal, numa conversa geral ou numa cerimônia, e o contato de um squad que lê o repositório do próprio squad, não têm pasta de trabalho para servir de raiz e ficam sem confinamento de leitura. As cerimônias (daily, unblock, retro) leem a pasta de projetos de propósito e continuam de fora.

Depois de uma etapa, o **app** faz o commit no worktree (`git add -A`, sem as pastas de dependências ligadas, e `git commit`) com a identidade de `runner.identity` ou, vazia, a do `.git/config` do próprio repositório (lida, nunca gravada), passada no comando com `-c user.name=… -c user.email=…`; a identidade global do git e as variáveis `GIT_AUTHOR_*`/`GIT_COMMITTER_*` nunca entram, e sem identidade a execução não começa (nem a etapa faz commit), com `-c core.hooksPath=/dev/null` (um hook que o agente tenha mexido não roda), sem assinatura e sem monitor de arquivos, e a mensagem de `runner.commitMessage` (padrão `feat: <resumo> #<n>`, com `{iid}` obrigatório). A mensagem nunca leva atribuição de ferramenta. Os documentos das etapas que só leem também são commitados pelo app. A revisão lê o diff com `--no-ext-diff --no-textconv`, sem a pasta do ciclo.

### O que um agente pode ler e rodar

Duas configurações por agente, em **Configurações › Time**, com padrões por papel (o Product Owner e o Tech Lead leem o host de código; a QA, o desenvolvedor e o Tech Lead rodam comandos numa sandbox). As regras completas, o modelo de ameaças e o que é só promessa: [`docs/cycles/30-agent-permissions/feat/1_SPEC.md`](cycles/30-agent-permissions/feat/1_SPEC.md); os campos estão em [`configuration.md`](configuration.md).

- **Leitura do host de código (`tracker`).** `read` deixa o agente ler issues, comentários, rótulos, o marco, as pull requests ligadas a uma issue e o diff, as conversas de revisão e as checagens delas. Nunca escreve: o que vai para o host continua sendo só o que a [porta](#o-que-fica-no-host-de-código) desta página deixa sair. Todo agente de uma execução lê o host só pela ferramenta `VcsRead` do app (nunca a CLI do host nem o MCP do tracker, que ficam para as cerimônias), e só os projetos do workspace: a issue e os repositórios dele; um workspace que não nomeia nenhum projeto não dá leitura nenhuma. Issues ligadas entre si não estão cobertas: a interface dos provedores não tem essa leitura.
- **Comandos (`shell`).** `none`: nenhum comando. `allowlist`: os comandos de `runner.commands`, como antes (só para quem escreve). `sandbox`: qualquer comando, dentro de uma sandbox que o app monta para a etapa e termina com ela, por uma ferramenta `Shell` (o Bash do próprio motor fica desligado para esse agente). `host`: qualquer comando, **neste computador, como você e fora de qualquer sandbox**, pela mesma ferramenta `Shell`, para o que uma sandbox não alcança (um `docker compose`, um emulador, uma janela, a rede).
- **Comandos no computador (`host`).** Cada comando **espera você permitir** antes de começar: a execução mostra o comando inteiro, avisa (se as notificações estão ligadas) e você responde "Permitir uma vez", "Permitir até o fim da etapa" ou "Não permitir", com um recado opcional que o agente lê. Enquanto espera, os relógios da etapa ficam parados. **A escolha "Comandos no computador sem perguntar" do bloco de autonomia da execução dispensa a pergunta**: com o ciclo autônomo ligado e essa escolha ligada, cada comando roda direto e a conversa diz que rodou sob a autonomia do ciclo; com a escolha desligada, a pergunta continua como sempre (o comando `host` de uma menção pelo celular segue exigindo a chave dos efeitos externos, que o bloco não contorna). O comando roda na pasta da execução (quem só lê roda numa cópia descartável), com o PATH do seu login e o ambiente do app sem o que parece credencial; os arquivos da sua pasta pessoal, a rede e o Docker ficam ao alcance, e é por isso que cada comando pede a sua aprovação. Valem só os limites de tempo da sandbox; um processo deixado em segundo plano fica até o fim da etapa. A conversa e o registro de auditoria dizem que o comando rodou neste computador (`via: host`). Só o computador define `host`: um navegador pareado não sobe um agente para ele, um modelo de ciclo nunca o traz (o agente recebe uma sandbox, ou menos), e permitir um comando pelo celular exige a mesma chave dos efeitos externos que aprovar uma proposta. O pedido vive enquanto a etapa vive: se o app fecha, a etapa recomeça e pergunta de novo. Numa conversa fora de uma execução (um canal, uma conversa geral, a conversa direta de um agente), o agente chamado com `@` roda numa cópia descartável do que o git conhece do repositório (os arquivos rastreados e os novos não ignorados, como estão na pasta; nada do que é gerado ou instalado, como `dist` ou `node_modules`, com as dependências do clone emprestadas só leitura, como num worktree, e o limite de `copyMb`) e o pedido é o mesmo aviso de comando das cerimônias, em qualquer tela e no navegador pareado: "Permitir uma vez", "Sempre permitir" a regra sugerida (que entra na lista do agente em Configurações › Time) ou "Não permitir", com o recado; um comando que essa lista já permite roda sem perguntar, e o pedido sem resposta em 15 minutos é recusado.
- **A sandbox** (Linux com bubblewrap; o Docker não é usado, e macOS e Windows oferecem só `none` e `allowlist`, porque lá nenhum equivalente está ao alcance de um app). Montada para **cada etapa**, ela tem: o worktree gravável (quem só lê recebe uma cópia descartável, e nada do que fizer chega à branch); `/usr` e `/etc` somente leitura e nada mais do sistema: **sem pasta pessoal, sem `/run`, sem `/var`**, logo sem chave, token, socket de agente ou socket de contêiner; `.git` somente leitura (o arquivo que aponta, sobre si mesmo; a pasta do repositório somente leitura, com o `config` trocado por uma cópia só com chaves inofensivas e a pasta `hooks` vazia); um ambiente montado do zero (nenhuma variável do app passa); **sem rede** (só o loopback dela; com a chave do registro, só HTTPS para os endereços listados pelo proxy do app; com a rede **aberta** — `network: open`, só no desktop e desligada por padrão — a sandbox **compartilha a rede do computador inteira**, sem proxy e sem lista de endereços, com a configuração do resolvedor de nomes do sistema montada somente leitura lá dentro; a escolha é de risco e é feita no computador); limites por comando (tempo, memória de dados, tamanho de arquivo) e por etapa (processos, tempo total de comandos). Um processo que um comando inicia (um servidor de desenvolvimento) fica para o comando seguinte e é morto quando a etapa termina; a sandbox termina **antes** de o app fazer o commit do que a etapa mudou. Um comando que passa do limite é interrompido e diz isso. Ela nunca faz push nem escreve no host: não tem credencial nem rota.
- **Testar uma interface na sandbox (#68).** Duas configurações, só no computador (Configurações › Runner › Sandbox), desligadas por padrão. A **pasta de navegadores** (`runner.sandbox.browsersPath`, em geral `~/.cache/ms-playwright`) passa pelas mesmas guardas das pastas só leitura e vai para toda sandbox, só leitura e no próprio caminho, com `PLAYWRIGHT_BROWSERS_PATH` apontando para ela; é a exceção a "sem pasta pessoal", e não entra no `PATH`. A **tela virtual** (`runner.sandbox.display`) faz a sandbox da etapa de QA (só ela; nunca uma menção) subir um Xvfb **dentro** da sandbox (1280×800, sem TCP, com os mesmos limites por processo de um comando, socket no `/tmp` da própria sandbox) e definir `DISPLAY`; o programa vem do `PATH` da sandbox (`/usr/bin` ou o `bin` de uma pasta só leitura), e a tela do computador nunca é usada. Com uma das duas ligadas, a etapa recebe no prompt como testar (servidor de desenvolvimento no `127.0.0.1`, Playwright das dependências do repositório, `--no-sandbox`, capturas em `/coxia/out`, nunca na pasta de trabalho) e a ferramenta **`ViewImage`**, que mostra ao modelo uma imagem salva em `/coxia/out` e em nenhum outro lugar (sem seguir link, sem esperar em pipe, até 4 MB, tipo conferido pelo conteúdo). Uma pasta que sumiu, um Xvfb que não existe ou que não subiu não param a etapa: o fio diz o que falta, o prompt manda marcar os cenários que dependem disso como não executados, e o status em Configurações mostra navegadores e tela em linhas próprias, sem nunca tornar a sandbox indisponível. **O mesmo vale para um agente com `shell: host`.** Os comandos dele enxergam a pasta de navegadores por `PLAYWRIGHT_BROWSERS_PATH` (sem montagem: a pasta é a do próprio computador), e a etapa de QA ganha uma tela só dela: o app sobe um Xvfb (1280×800, sem TCP, num número de tela livre que ele escolhe) antes da etapa e o encerra com ela; `DISPLAY` aponta para essa tela, `WAYLAND_DISPLAY` sai, e, com a tela ligada mas indisponível, `DISPLAY` também sai, para que um app de janela nunca abra na tela da pessoa. O programa é procurado no `bin` das pastas só leitura, no `PATH` do login e em `/usr/bin`. As capturas vão para uma pasta que o app cria para a etapa (`COXIA_OUT`, dita no prompt), o único lugar de onde a `ViewImage` lê. O prompt dessas etapas é o do computador: sem a fronteira da sandbox, uma porta livre para o servidor de desenvolvimento, uma pasta de dados vazia para o app em teste e `--no-sandbox` só se o navegador se recusar a iniciar. Subir a tela é do app, não um comando do agente, então não espera a pessoa; cada comando do agente continua esperando.
- **A tela ao vivo (#157).** Uma etapa de QA com a tela virtual ligada (na sandbox ou de um agente com `shell: host`) mostra um botão **Tela ao vivo** no cartão da etapa, no app e no navegador pareado; ele aparece e some na hora, porque o app avisa quando uma tela abre ou acaba (`SCREEN_EVENT`, sem imagem). O visor pede o último quadro (`runs:screen(id, desde, largura)`, uma leitura aberta ao navegador pareado) cerca de duas vezes por segundo enquanto está aberto, e para quando é fechado, fica oculto ou a etapa acaba; o app lê a tela só quando alguém pede (no máximo uma leitura a cada 400 ms, qualquer que seja o número de visores) e um quadro igual ao que o visor já tem volta sem imagem. O quadro vem da própria conexão X11 do app com a tela (`GetImage`; o app é cliente X, sem programa novo, sem `-fbdir` e sem abrir rede na sandbox, que só ganha uma pasta do `stageDir` montada sobre `/tmp/.X11-unix`); a conexão é feita **antes do primeiro comando do agente** e nunca discada de novo, para o agente não trocar o socket por outro. O computador recebe 1280×800 em JPEG qualidade 75 e o telefone 640 de largura, qualidade 60, como `data:` (a política do desktop não deixa `blob:` em imagem). **Assumir o controle** é só da janela do desktop (o canal `screen:*` é negado ao navegador por um padrão em `webPolicy.ts`): cliques, roda e teclas viram eventos XTEST; o visor diz que o controle está ligado e gravado, e Ctrl+Alt+Shift+Esc devolve o controle (nunca é enviado). O telefone vê uma marca "controlada pelo computador". O que a pessoa faz **não é comando do agente**: não espera atrás dos comandos dele, não gasta o orçamento da etapa e não entra no registro de comandos; a conversa ganha uma linha ao assumir e ao devolver o controle e uma por rajada de uso ("a pessoa usou a tela de … até …"), e a gravação marca o mesmo intervalo. O app **grava** a tela a partir da primeira vez que ela é usada, isto é, quando uma janela aparece nela (e não quando a tela abre), e só enquanto há janela mapeada: o app pergunta ao servidor X pelas janelas filhas da raiz (`QueryTree` e `GetWindowAttributes`, com a resposta lida com tamanho limitado) e, com a tela vazia, não lê nem grava nada. É um vídeo WebM (VP8, codificado por uma janela oculta com WebCodecs e um empacotador do próprio app), a cerca de um quadro por segundo e só quando a imagem muda. Um intervalo parado de mais de 3 segundos entre dois quadros toca como uma pausa de cerca de 1 segundo, e a gravação guarda cada corte (`cuts`: o ponto do vídeo onde a pausa acaba e o tempo da etapa que ficou de fora; no máximo 500): `durationMs` é o tempo do **vídeo**, `realMs` o tempo da etapa, `startedAfterMs` o tempo entre a tela abrir e o primeiro quadro, e as marcas do uso da pessoa ficam no tempo do vídeo, sobre a faixa do player; o player mostra um traço em cada corte, o tempo da etapa ao lado da duração e o tempo da etapa no ponto que toca. Uma etapa cujo agente nunca abriu janela não guarda gravação e diz isso **uma vez** na conversa ("nenhuma janela foi aberta na tela"), sem ser erro. O vídeo tem teto de 24 MiB e 60 minutos de vídeo (o teto para a gravação e diz isso) e é guardado como **uma** comprovação da etapa, feita pelo app, **também quando a etapa falha ou é cancelada**, antes de a pasta da etapa ser removida. O agente não a cita, não a apaga e não a salva (`SaveEvidence` continua recusando vídeo), ela não vai para o host de código nem para a pasta do ciclo. O bloco de comprovação toca o vídeo com as marcas dos intervalos da pessoa, que levam o vídeo até lá; a conversa traz o anexo. Um run que guarda uma gravação é gravado no formato 2, e no formato 3 quando a gravação tem cortes ou `startedAfterMs` (as gravações novas): um app mais antigo o recusa como escrito por um app mais novo (os 0.9.0-beta.4 e beta.5 leem o 2, mas não o 3). A **retenção** ganha o grupo "Gravações de tela das etapas", varrido com os dias do espaço de trabalho (desligada por padrão); só o arquivo some, e o registro fica marcado como removido pela retenção. Com a tela ligada o prompt do QA manda rodar o navegador **com janela** (`headless: false`), porque um navegador headless não desenha em tela nenhuma. Só Linux; a tela da pessoa nunca é mostrada.
- **Entregar a tela à pessoa (#178).** Um agente com tela ao vivo (a etapa que trabalha ou o agente numa conversa, nunca uma execução de documentação) recebe a ferramenta `screen_handoff(what, why?)` para um login, um código que chegou ao celular ou um campo que a pessoa deve digitar e o modelo não deve ver; o prompt manda usá-la e nunca pedir nem aceitar um segredo na conversa ou no texto de uma ferramenta. **A espera:** a chamada fica aguardando dentro da ferramenta (uma pergunta encerraria a tentativa da etapa e, com ela, o display), os relógios da etapa ou da resposta ficam parados e o app mostra **um cartão** onde o agente trabalha (no alto da execução e na conversa) e avisa o celular, com texto fixo do catálogo (nunca o `what`), de que o agente espera a pessoa **no computador**. Ninguém pega a tela em 15 minutos: o resultado é `expired`. **Os quatro resultados** são frases fixas e nada mais (`done`, `declined`, `expired`, `unavailable`: um segundo pedido com outro aberto, ou depois de uma recusa ou expiração na mesma tentativa ou resposta, também é `unavailable`). **A pessoa** assume a tela no computador depois de um aviso montado do que o agente tem (o navegador do app, um shell na sandbox ou no computador, ou nenhum) e que diz que o intervalo **é gravado** e fica com a comprovação; depois do clique, o controle liga sem chave, as imagens chegam por `screen:handoffFrame` e *Devolver* (`screen:handoffGive`) devolve a tela; sem entrada por 30 minutos o intervalo termina como `expired`. Recusar (`runs:handoffDecline`) é aberto ao navegador pareado e não pede a chave de efeito externo, porque não dá nada ao agente; assumir e devolver são só do desktop. **O intervalo:** do clique ao fim, nenhuma imagem da tela vai a um leitor da web (`runs:screen` responde `held`, e o cache é descartado nas duas pontas, antes de o controle ligar); a gravação continua sendo alimentada e o intervalo é **uma** marca do tipo `handoff` (`RecordingMeta.handoff`), então um run com uma gravação assim é gravado no **formato 4** (os formatos 2 e 3 seguem como antes; um app que lê até o 3 o recusa como escrito por um app mais novo; o formato 5 é o de um run em que o registro de uma etapa traz os procedimentos que ela usou, #179, e vale por si, qualquer que seja a gravação); a gravação toca no navegador pareado como qualquer outra. Fechar o visor ou a combinação de saída desliga o controle e **não** encerra o intervalo. **O que o agente não consegue:** durante o intervalo toda chamada do navegador do app, a confirmação e um novo pedido são recusados com uma frase fixa, e um comando do shell (na sandbox ou no computador, sem pedir aprovação) também; ao devolver, o que a pessoa digitou (reconstruído das teclas, só na memória, nunca em disco, na conversa, na auditoria, no registro de passos ou no resultado) aparece como `[secret]` em toda leitura do navegador do app, nas formas pura, codificada para URL e escapada em JSON (4 caracteres ou mais), e a saída dos comandos passa pelo mesmo mascarador; uma imagem de uma página que mostre o valor é recusada. **O que o app não consegue:** programas que o agente já tinha iniciado no shell continuam rodando e podem capturar a tela ou ler a página (o aviso diz isso); a garantia ali é de melhor esforço. A conversa recebe linhas fixas (pedido, assumida, devolvida, recusada, expirada e **uma** linha do intervalo), a auditoria um registro `screen-handoff` (agente, `what`, desfecho, intervalo, `sandbox` ou `host`) e o registro de passos um passo sem conteúdo. Nada disso tem configuração: os limites (15 e 30 minutos) são constantes.
- **O que aparece.** Cada comando, o código de saída e o fim da saída vão para a conversa da execução (uma mensagem cada), para a atividade ao vivo (a chamada e como terminou) e para **Configurações › Registro de auditoria** (tipo "Comando na sandbox", com o agente que rodou). Os comandos que o app roda antes da QA rodam **dentro** da sandbox do agente de QA quando ele tem uma.
- **Dependências do clone.** Os links `node_modules` e `.venv` que o runner faz no worktree seriam pendurados na sandbox: as pastas para onde eles apontam são compartilhadas **somente leitura**, no mesmo caminho, quando o caminho real fica dentro do clone da execução; um link que aponta para outro lugar fica pendurado e a conversa diz que o agente precisa instalar as próprias dependências. Uma ferramenta que grava cache em `node_modules/.cache` falha lá dentro.
- **Onde não há.** Um computador que não consegue criar uma sandbox diz por quê (bubblewrap ausente, user namespaces recusados pelo sistema, falta `prlimit` ou `timeout`), o editor não a oferece, os modelos trazem `allowlist` ou `none` no lugar, e uma execução cujo time tem um agente em `sandbox` é recusada no início, ou a etapa dele falha, com a mensagem. **Nada volta a rodar os comandos fora.**
- **A evidência da QA.** Um agente de QA com sandbox marca cada cenário como `executed` (e cita os números dos comandos que o sustentam, os do app primeiro) ou `read`. O app confere: `executed` só vale se cita um comando da etapa, e um "passou" precisa de um que terminou com código 0; senão é registrado como `read` e **marcado** "dado como executado, nada o sustenta". O comentário da QA diz quantos cenários foram executados. Qualquer outro agente de QA tem todos os cenários registrados como `read`. Mostra que um comando rodou, não que o comportamento está certo: um script pode imprimir o que quiser.
- **Quem muda.** Só o computador sobe `shell` ou `tracker` ou mexe em `runner.sandbox`; um navegador pareado pode baixá-los, o `shell` só para `none`. A migração para o esquema 10 não subiu nada num workspace que já existia: quem escreve manteve os comandos, quem só lê manteve a leitura do host que tinha, ninguém ganhou sandbox; as permissões recomendadas são **oferecidas** no editor do time.

### O que fica no host de código

**Um comentário por etapa, editado no lugar.** Cada etapa de trabalho (e cada gate decidido, e cada pergunta de agente) deixa o seu resultado na tracker, a partir do modelo de `devCycle.comments`: o app monta o comentário (o status na primeira linha, as seções do modelo na ordem, o detalhe técnico por último e recolhido, um marcador escondido no fim com o id da execução e da etapa) e **confere o texto pronto**. O que dá para consertar é consertado em silêncio: segredos mascarados, caminho do worktree vira caminho do repositório, outro caminho absoluto fica só com o último nome, o id da execução sai do texto, uma menção (`@fulano`) vira texto para não avisar ninguém. O que não dá é **apontado**: o nome de um agente, de uma ferramenta ou do fórum, primeira pessoa fora de uma citação, o status que não é a primeira linha, um `<details>` aberto ou que não é o último bloco. Texto apontado **não sai sozinho**, mesmo de agente autônomo: vira proposta em Ações com os problemas no topo.

Antes de postar o app procura o comentário da etapa: a nota que a execução lembra (`Run.comments[etapa].noteId`), senão a que traz o marcador, senão cria. Depois de postar, lê de volta e compara; se o host mudou o texto (tabelas e seções recolhidas são o que quebra) a conversa diz. Quando uma edição muda o que o comentário diz (o status da primeira linha: QA que falhava e passou), um comentário curto, com link, avisa; um gate decidido várias vezes deixa um comentário por decisão (com o motivo e o link do comentário da etapa que ele julgou); cada pergunta de agente é um comentário. Uma etapa sem modelo no ciclo não posta nada, e trocar o modelo muda o próximo comentário.

**Quem decide se sai sozinho.** O valor de `autonomous` do agente na hora em que a etapa terminou (o que o registro da etapa guarda; mudar a chave no meio da etapa não vale para ela): agente **autônomo**: o comentário sai pela porta das Ações (`runner/door.ts`), com uma linha em `auditoria.jsonl` por chamada (`by` o agente, o alvo, o hash do corpo e a resposta do host); agente que **espera**: o comentário vira uma proposta em Ações, com o texto à vista, e o "sim" posta (ou edita) e a execução fica sabendo o id da nota. A decisão de um gate segue o agente cujo trabalho ele julgou. **Workspace de teste:** recusa tudo (o comentário fica `refused`, a conversa diz, nada é lido nem escrito no host); a proposta do push e a do pull request continuam existindo e a confirmação delas é recusada.

**Revisão no pull request.** A etapa de revisão não comenta na issue: a rodada vira **uma revisão** no pull request, `request_changes` quando algum achado bloqueia e `comment` quando não (o app nunca aprova; num pull request que é da própria pessoa os hosts não aceitam pedir alterações, então a revisão vai como comentário e a primeira linha do texto geral diz o resto). O pull request é o que a execução registrou, ou um aberto da branch dela que o app ache pela issue (a pessoa pode tê-lo aberto à mão). Cada achado é posicionado no diff **atual** do pull request: no lugar que ele nomeia, se as linhas estão no diff, no lado certo; senão no arquivo, dizendo qual linha era (nunca numa linha errada); se o arquivo saiu do diff, no texto geral. Cada comentário diz se bloqueia ou é sugestão. O **texto geral** da revisão não repete os achados que já estão nas linhas: traz o que o agente escreveu e não é sobre nenhum achado (o app tira parágrafos e itens que dizem o que um achado diz, ou que citam o lugar dele), os achados de arquivos que saíram do diff e **uma linha** com quantos comentários a revisão deixou no código; as seções do modelo da revisão são "Além das linhas do código" e "O que não foi revisado". A troca que o achado propõe vira o **bloco de sugestão** do host (GitHub `suggestion`; GitLab `suggestion:-N+0`, N calculado pela faixa) só quando o comentário está exatamente onde o achado diz e no lado novo; em qualquer outro caso, e no Bitbucket, é descrita num bloco de código. O mapeamento por provedor está em [`vcs-providers.md`](vcs-providers.md).

A **rodada seguinte** lê as threads que a execução abriu (o marcador de cada comentário diz a rodada e o achado): um achado que continua (as mesmas palavras, o mesmo arquivo; a linha não conta) ganha uma resposta na própria thread; um que foi corrigido, uma resposta de uma linha e a thread resolvida (onde o host resolve thread); só o achado novo abre thread. A rodada inteira (respostas, resoluções e a revisão) é **uma ação**: uma proposta em Ações com um "sim", ou um conjunto de chamadas auditadas sob o mesmo nome. Se o pull request ainda não existe, a revisão espera como rascunho e sai quando ele existir (a última rodada que esperou: as anteriores já foram respondidas pelo trabalho que veio depois).

**O push e o pull request esperam o seu "sim", a menos que o bloco de autonomia os libere.** No fim da última etapa antes da revisão cujo agente muda o worktree (a implementação), o app escreve a descrição do pull request (modelo `pr`: o status, as seções, `Closes #n`, o detalhe técnico) e **propõe o push** da branch (`run-push`): a ação guarda o id da execução, não uma pasta; ao confirmar, o app lê o worktree e a branch da execução, recusa se o worktree está em outra branch ou tem algo que não foi commitado, e faz o `git push --no-verify origin HEAD:refs/heads/<branch>` simples, sem force, auditado. Um push mais novo da mesma execução substitui o que ainda esperava. **Quando o push foi feito**, o app propõe o **pull request** (`createMr`, título e corpo do modelo, para a branch padrão do repositório), que espera o seu próprio "sim"; ao confirmar, a execução registra o pull request (`Run.comments.pr`: o número em `noteId`) e a revisão que esperava sai nele. Cada etapa seguinte cujo agente muda o worktree (um QA que escreve testes, a implementação para a qual a revisão devolveu) propõe um push novo, que só atualiza o pull request; um fluxo sem revisão faz o push uma vez, na última etapa que escreve. **A exceção é o bloco de autonomia da execução**: com **Ciclo autônomo** e **Push sem "sim"** ligados, o push sai pela porta no fim dessa etapa, auditado (uma linha por chamada, com o agente que pediu), e com **Abrir o pull request sem "sim"** ligado o pull request é aberto logo depois, também auditado; com o push ligado e o pull request desligado, o push sai sozinho e o pull request continua esperando o seu "sim". Um espaço de trabalho de teste recusa os dois de qualquer jeito (a escrita é recusada na porta, e a conversa diz por quê), e uma **execução de release** fica fora das duas escolhas: os cortes e os envios dela sempre esperam o "sim" (D18). Fora disso, nada pula o "sim".

**A comprovação de uma etapa.** Um agente com sandbox guarda o que capturou enquanto trabalhava como **comprovação** da etapa: uma ferramenta `SaveEvidence` lê um arquivo que a própria etapa fez na pasta de saída dela (nunca um caminho de outro lugar, nunca um caminho que passe por um link; o tipo é lido **dos bytes**, nunca do nome), recusa o que passa de 8 MiB e o guarda com um id curto e estável na execução, `ev-<algarismos>` (por exemplo `ev-3`), que é o que um cenário de QA e a saída de etapa citam. A comprovação é publicada **na hora** na conversa da execução, como anexo de uma mensagem do agente, e aparece listada na etapa em que foi guardada; a pessoa abre, baixa e apaga (um agente guarda, nunca apaga). Ela some quando a execução é removida. Uma segunda ferramenta, `AnnotateImage`, desenha marcas (retângulo, seta, elipse, rótulo, marcador numerado e a **caixa de borrão**, que esconde o que não deve ser visto) sobre uma imagem e guarda o resultado como uma comprovação **nova**, ligada àquela de que veio, com a original preservada; o desenho é do processo principal, a partir de dados, e nenhum programa do agente roda para desenhar. A `ViewImage` (a mesma ferramenta que mostra uma captura de `/coxia/out`, sempre uma só) também aceita o id de uma comprovação, e deixa o agente olhar para a imagem que produziu e marcar de novo em cima dela. O que é aceito: imagens (PNG, JPEG, GIF, WebP), `text/plain` e PDF; vídeo, áudio, arquivo compactado, executável e qualquer conteúdo que não confirme o que diz é recusado (a única exceção é a gravação da tela que o próprio app faz, descrita em "A tela ao vivo": ela não passa por essa ferramenta). **Onde a comprovação fica** é escolha do espaço de trabalho, em Configurações › Runner: **só nos dados do app** (o padrão: com a execução, nos dados do espaço de trabalho, e nunca num commit) ou **também na pasta do ciclo** (uma cópia vai para `docs/cycles/<n>-<slug>/evidence/` e é levada no commit da etapa). Só o computador muda a escolha. **Levar ao host:** quando um comentário de etapa ou a descrição do pull request cita uma comprovação, a imagem é enviada ao host e sai embutida no texto, pela mesma porta das outras escritas (um agente autônomo publica sozinho e é auditado; qualquer outro espera o "sim" em Ações, com as imagens à vista; um workspace de teste recusa; quando o bloco de autonomia abre o pull request sozinho, as imagens que a descrição cita sobem antes, também sozinhas e auditadas, e a descrição embute os endereços delas). A imagem faz parte da **mesma escrita** que a cita: ela sobe junto com o comentário, na ordem de comandos que o "sim" libera, e nunca antes dele — um comentário que espera em Ações não põe nenhuma imagem no host até a pessoa confirmar. Cada provedor envia do seu jeito (GitHub pela hospedagem de arquivos do próprio host, GitLab pela subida de arquivo do projeto, Bitbucket pela subida de arquivo do repositório); onde embutir não for possível, o comentário diz quantas comprovações existem e que elas estão no app, em vez de omitir ou quebrar. Nenhum host real foi usado neste projeto: o que cada um aceita é o que a documentação diz.

### Squads

Com squads configurados ([`configuration.md`](configuration.md), [`cycles.md`](cycles.md)), o runner escolhe o squad da execução, dá a ela o fluxo e os agentes do squad e cuida dos pedidos entre eles. Sem squads nada disso existe e a execução é como sempre foi (o teste `test/runner-golden.test.ts` fixa isso).

**Iniciar.** `runs:start(ref, repo?)` (e o escalonador) leem a issue, descartam os squads sem membros e roteiam pelo escopo: o repositório da execução, depois os rótulos da issue, depois as pastas dos arquivos que o texto dela (título, descrição e comentários humanos) cita; cada regra só estreita o que sobrou, e uma regra que não diz nada sobre a issue não estreita. Um squad só: a execução começa nele (`Run.squad`, `Run.routedBy`: `repo`, `label`, `path` ou `unclaimed`), com a cópia do fluxo dele e só os membros e os compartilhados como agentes (`flowOf` sobre `squadView`); a conversa diz por quê. Sem a repositório (o escalonador não escolhe um quando o projeto tem vários), os rótulos e as pastas falam, e o repositório é o único que o squad escolhido tem no projeto. Com o repositório que a chamada nomeou, ele vale. Antes de iniciar, o runner confere os squads (`checkSquads`) e recusa se houver erro. O rótulo do squad vai para a issue por `Publisher.squadRouted`, pela autonomia do contato (proposta se ele espera).

**Triagem.** Vários squads (ou nenhum) reivindicam a issue: a execução começa na primeira etapa do fluxo **do workspace**, com `Run.routing` (os candidatos, por que, a proposta e o que a porta de entrada produziu). Só nessa etapa o esquema da resposta tem `squad` (um id dos candidatos, ou nulo) e `squadReason`, e o prompt lista os candidatos. Quando a etapa termina: agente **autônomo** e um candidato proposto decidem (`routeSquad`); senão a execução fica em `question` do tipo `squad` (`askSquad`), com a proposta na conversa, esperando `runs:setSquad(id, squad | null)`. As palavras da pessoa não respondem a essa pergunta (`runs:answer` recusa, e uma mensagem na conversa é só uma mensagem). Decidido o squad, a execução continua na etapa depois da porta de entrada do fluxo do squad (a primeira dele, se ele não a tem), com o que a porta produziu e a passagem que ela deixou; sem agente na primeira etapa, a pessoa escolhe antes e essa etapa é pulada. `runs:setSquad` só serve a uma execução que espera a escolha.

**Autonomia.** O valor de um agente que uma etapa lê é o da chave dele **e** a do squad (`effectiveTeam`); a etapa o guarda ao ser alcançada, como sempre. `runs:setSquadAutonomous(squad, ligado)` muda a chave do squad; vale a partir da próxima etapa.

**Pedidos entre squads.** Quem segura uma pergunta e é o contato de um squad, havendo outro squad com contato, ganha no esquema o veredito `request` (`{ squad, kind, text }`) e uma linha no prompt com os outros squads. Um pedido válido vira uma mensagem `request` no canal `squads` (autor o contato, `to` o contato do outro squad, `params` com os squads, o tipo, a execução e a issue) e uma linha na conversa da execução; o contato que recebe é chamado **só lendo**, na pasta de um repositório do squad dele, e responde `answer`, `decline`, `issue` (com título e descrição) ou `needs-person`; a resposta dele é uma mensagem `answer` no canal que fecha o pedido (`replyTo`). `answer` e `decline` voltam como a resposta do contato de quem perguntou (`answerByAgent`), e a etapa de quem perguntou segue; `needs-person` passa a pergunta à pessoa (a conversa da execução mostra o motivo); um pedido que não pode ser feito (squad desconhecido, sem contato, o próprio) ou um contato que falha sobem a pergunta à pessoa com a razão, e o pedido que ficou aberto é fechado com uma resposta do app. O que o contato disser depois de a pessoa já ter respondido (ou de um cancelamento) não é usado.

**Issue e execução ligada.** `issue` cria a issue no tracker (`Publisher.requestIssue`: `createIssue` no projeto das issues, com o rótulo do squad e uma linha de origem na descrição), pela autonomia do contato que recebeu (`autonomousOf`: a dele e a do squad): autônomo, sai pela porta e é auditada; senão é uma proposta em Ações (`unit.purpose = 'request-issue'`), e a execução que pediu espera já (`waiting`, `linked-done`, `wait.by` o agente que perguntou) com o vínculo `proposed`. Com a issue criada (na hora, ou quando a pessoa aprova em Ações: `Runner.actionDone`), uma execução do outro squad começa nela (`routedBy: 'request'`, no repositório que o escopo dele tem), com o vínculo `origin` para a que pediu, e a que pediu guarda `requested` com a execução e a issue. Se a execução nova não pode começar, ou a escrita é recusada (workspace de teste) ou falha, o vínculo fica `refused` e a etapa que esperava segue sabendo disso. Um "não" em Ações a uma proposta não avisa o runner: o vínculo fica `proposed` e a pessoa deixa de esperar com `runs:skipWait`.

**`linked-done`** é resolvido pelo runner (o publicador não olha o host para ele): a execução que espera segue quando todos os vínculos `requested` dela terminaram (a execução ligada chegou a `done`, ou a issue dela foi fechada no tracker, lida pela fonte de issues) ou foram recusados. Quando a execução ligada chega a `done` o runner olha as que dependem dela na hora; a passada de 5 minutos cobre a issue fechada à mão. Uma execução cancelada não resolve a espera, e uma etapa `wait` de `linked-done` numa execução que não pediu nada segue na passada seguinte. A resposta com que a etapa segue (a lista do que terminou) é do app, não da pessoa.

**Canais.** `ensureSquadChannels` abre, quando há squads, o canal `squads` e um `squad-<id>` por squad (conversas do tipo `channel`); `forum:list(squad?)` lista tudo ou só o que está sob um squad (o canal dele e as conversas das execuções dele: o squad de uma execução é lido da execução na hora da lista). A pessoa escreve em qualquer canal como em qualquer conversa. Remover um squad (`runs:removeSquad(squad, confirmar)`) lista as execuções ativas dele sem `confirmar` e, com ele, remove o squad, torna os membros compartilhados e tira as execuções do squad (`leaveSquad`).

### Uma release

Uma release é uma execução cujo **assunto é uma versão**, não uma issue (`Run.subject: { kind: 'release', version, from, tracking, activities }`; uma execução de issue não tem o campo). Ela carrega uma `issue` sintetizada (`release:X.Y.Z`, número 0), que mantém "uma execução por vez" funcionando; o worktree próprio de sempre, com a pasta do ciclo (`0_ISSUE.md`, o registro da release, e `RELEASE_PLAN.md`); e o fluxo do modelo `release-flow`, guardado em `devCycle.flows.release` (um fluxo **por tipo de execução**, ao lado dos dos squads: nenhum squad pode se chamar `release`). Aplicar o modelo **acrescenta** esse fluxo, os comentários e o agente Release manager e deixa o fluxo das issues como está. Decisões D5, D6 e D11 do [`1_SPEC.md`](cycles/27-release-process/feat/1_SPEC.md), aprovadas pelo mantenedor em 2026-10-03.

`runs:startRelease(versão, de?, repo?)` (na janela do desktop e, com **"efeitos externos" ligado**, num navegador pareado: está em `EXTERNAL_EFFECT` em `src/main/webPolicy.ts`, ao lado de aprovar uma proposta, porque a release termina em scripts e código mesclado do repositório rodados como você; com a chave desligada o celular recebe a recusa no próprio campo. A tela das execuções tem o campo quando o workspace tem o fluxo, nos dois lugares, e cada push da release continua esperando o seu "sim" em Ações) confere a versão (`X.Y.Z`, números sem zero à esquerda; `de` é a tag estável `vA.B.C` de que um patch sai), recusa uma segunda execução ativa da mesma versão e um workspace sem o fluxo de release, cria o worktree, escreve o registro (se a branch `release/X.Y.Z` existe e as atividades) e começa. Em seguida o publicador faz, uma coisa de cada vez: cria ou adota a issue de acompanhamento, lista nela as atividades e **abre a branch** (ou propõe abrir) se ela ainda não existe.

**As atividades** são os pull requests que apontam para `release/X.Y.Z`, abertos ou integrados (um fechado sem integrar não é atividade), lidos pelo provedor (`listMrsByTarget`, nos três hosts; a aprovação e as verificações de cada aberto, um a um, por `getMr`). Entram só no registro e no comentário as issues abertas do milestone que tem o número da versão e que nenhum deles carrega. Decisão: só por branch de destino e por milestone; não existe rótulo de versão configurável. A execução guarda a lista (`subject.activities`), e ela é relida a cada passada de 5 minutos e depois de cada passo; cada etapa a lê no prompt (`runner.section.release`). Cada linha mostra o commit (`em abc123def`) em que o pull request estava na última leitura. **Aceitar o plano** (aprovar ou pular o primeiro gate do fluxo) **congela** esses commits (`subject.planned`) dentro da própria transição do gate: uma chamada que o gate recusa (sem motivo num pulo, uma ação que não existe) não congela nada. Se a execução volta ao plano (o gate reprovado, ou uma devolução a uma etapa antes dele) o congelamento é desfeito, e o próximo aceite do plano congela de novo o que a execução tiver lido então; os gates seguintes nunca congelam nem desfazem. O que se congela é o que a pessoa **viu**: um instantâneo (`subject.seen`) tirado **uma vez**, quando a execução entra no gate do plano (e refeito logo depois de o publicador ler o host no fim da etapa do plano), que nenhuma leitura posterior reescreve (a passada de 5 minutos reescreve `activities`, não `seen`); o gate copia `seen` em `planned`. Um pull request que recebe um push durante a espera do gate não está em `seen`, e o merge dele é recusado. O painel do gate na tela da execução mostra esses commits (o curto de cada pull request) e avisa o que já andou; logo depois do aceite o host é lido de novo, e um pull request que andou desde então, ou que não estava no plano, é dito na conversa (ele não é integrado de qualquer jeito: o `merge-pr` exige o commit congelado).

**A issue de acompanhamento** "Release X.Y.Z" é criada quando a execução começa, ou **adotada** se já há uma aberta com o mesmo título (sem diferenciar maiúsculas; uma fechada não serve) **e** ela é da própria pessoa (o autor é o usuário com que o app age) **ou** traz o rótulo que dá nome a esta versão (`devCycle.releaseLabelPattern`, grupo 1 igual à versão). Um pull request nunca é candidato (a lista de issues o deixa de fora). Uma issue de outra pessoa, com o mesmo título e sem o rótulo, não é onde uma release reporta: o app cria uma nova e diz na conversa por que não adotou aquela. Como toda escrita no host, passa pela porta das Ações: pelo Release manager (auditada) se ele é autônomo, ou como proposta (`purpose: release-tracking`) que espera um "sim" e avisa a execução quando sai. Cada etapa deixa nela o seu comentário, pelos modelos de `devCycle.comments` (`release-plan`, `release-assemble`, `release-beta`, `release-stable`, e o `gate` e o `question` de sempre); enquanto a issue não existe o comentário é um rascunho e sai quando ela existe (ou na passada seguinte). Três comentários são do app: um, editado no lugar, lista as atividades (`activities`); quando o host mostra uma beta publicada, outro diz qual e onde (`beta-published`, um por beta); quando mostra a estável publicada, outro diz (`stable-published`) e **a issue é fechada**, pela autonomia do agente (uma proposta `release-close` se ele espera). Isso é lido pela passada de 5 minutos, também numa execução que já terminou (por 30 dias). O host diz "publicada" pela API de releases (`getRelease`: uma release que não é rascunho e tem data de publicação); o Bitbucket não tem releases, então lá nada disso é visto: a issue não se fecha sozinha e `beta-age` só segue com `runs:skipWait`.

**Os passos da release** são uma ação própria da porta das Ações, `release-git`, cuja unidade guarda `{ op, version, runId?, pr?, head?, from?, branch?, channel? }` e nunca um caminho, um comando ou uma flag (`src/shared/release.ts`, `parseReleaseUnit`: qualquer outro campo é recusado, não ignorado; ela é julgada de novo quando a pessoa diz "sim"). O repositório vem da execução (`Run.repo`), a identidade é a de `runner.identity` (sem ela, o passo é recusado: o app nunca assina uma release como outra pessoa), e o que roda é o `scripts/release.sh` **do próprio repositório** ou `git` simples, **num worktree próprio da execução** (D14, decidida pelo mantenedor em 2026-10-03): o checkout da pessoa **nunca é tocado** (nem a branch, nem a árvore, nem a `main` dela). O worktree (`<worktrees>/<repo>/release-X.Y.Z-steps`, ao lado do da execução, derivado dela e nunca da unidade) é feito do clone no primeiro passo, **destacado** (sem branch), as pastas de dependências do clone são ligadas nele e escondidas do `git status` por um arquivo de exclusão que mora no diretório git do próprio worktree. Os passos de `release/X.Y.Z` fazem checkout dela ali; os que precisam da `main` ficam num **HEAD destacado** no que o remoto tem da `main` (ou no commit da `main` local, sem remoto): assim nenhuma branch tem checkout duas vezes (uma branch com checkout na pessoa é recusada com o caminho, não tomada):

| `op` | O que faz |
|---|---|
| `open` | **recusa antes de rodar qualquer coisa** se a branch `release/X.Y.Z` já existe (aqui ou no remoto), e **põe o worktree no que representa a `main`** (um HEAD destacado em `origin/main`) antes de rodar, de modo que só o script da `main` roda no `open`, nunca o de uma branch de release em que um pull request integrado pode ter mudado o `scripts/release.sh`. Roda `scripts/release.sh open X.Y.Z [--from vA.B.C] --author "Nome <e-mail>" --worktree` (cria `release/X.Y.Z`, a partir de `origin/main`, e vai para ela, no worktree; `--worktree` é a opção do script para quem não tem a `main` como branch) |
| `merge-pr` | `head` é **obrigatório** e é um commit **inteiro** (40 ou 64 dígitos hexadecimais; uma abreviação é recusada, e a comparação é de igualdade exata, nunca de prefixo). Confere no host que o pull request está aberto, é do mesmo repositório (um de fork é recusado: "vem de um fork"), não é rascunho, aponta para `release/X.Y.Z`, **tem a cabeça que o plano aceito congelou** (`subject.planned`, fixado quando a pessoa aceita o primeiro gate), que a cabeça que o host tem agora é a mesma, e que o commit lido do remoto (`git fetch`, só leitura) também é; conta como aprovação só a que é **sobre essa cabeça** e de quem é dono, membro ou colaborador do repositório (ou, com `runner.release.soleMaintainer`, o sim da pessoa: veja **Uma pessoa só mantém o repositório**, abaixo da tabela), e uma verificação que o host não consegue ler vale `running` (recusa: o app nunca falha aberto); **sem nenhuma verificação** vale `running` também se o pull request foi atualizado há menos de 10 minutos (as verificações de um push recém-feito ainda não começaram, e um repositório que as exige seria integrado sem elas), e só depois disso vale "nenhuma" (um horário que o host não deu, ou no futuro porque o relógio dele está adiantado, vale "agora": a dúvida espera; os limites são que uma fila de CI que demore mais de 10 minutos para começar ainda passa como "nenhuma", e um relógio muito atrás do nosso deixaria passar um push recente; o app não pergunta se o repositório as exige: isso pede direitos que ele não tem). Faz então `git merge --no-ff` na branch da release com a identidade configurada e a mesma lista de `-c` que o commit do app (sem hooks, sem assinatura, sem `fsmonitor`); nunca o botão de merge do host |
| `beta` | **sempre espera um "sim" (D18)**; vai para `release/X.Y.Z` e roda `scripts/release.sh beta --author ...` |
| `stable` | **sempre espera um "sim" (D18)**; põe o worktree em HEAD destacado em `origin/main`, integra `release/X.Y.Z` (fast-forward, ou um merge com a identidade) e roda `scripts/release.sh stable --author ... --worktree`; a tag estável fica nesse commit destacado, e a `main` da pessoa não se mexe |
| `push-branch` | `git push --no-verify origin <sha>:refs/heads/release/X.Y.Z`, com o sha **resolvido antes** (nunca o `HEAD` simbólico; para a `main`, depois da estável: o commit da tag estável, desreferenciada, no HEAD destacado, enviado como `<sha>:refs/heads/main`, e **só se a tag for anotada** (a do script) e o commit dela estiver em cima do que o remoto tem da `main`). Todo push leva `-c push.followTags=false -c push.recurseSubmodules=no -c push.gpgSign=false -c remote.origin.mirror=false`: a configuração do git da pessoa não acrescenta tags, submódulos nem referências a ele |
| `push-tag` | `git push --no-verify origin refs/tags/vX.Y.Z[-beta.N]`, a última beta ou a estável, só uma tag anotada e só depois de o remoto ter a branch dela |

**Uma pessoa só mantém o repositório.** O GitHub não deixa quem abriu um pull request aprová-lo, e o `merge-pr` exige uma aprovação no host: num repositório com uma pessoa só mantendo, nenhum pull request dela entraria numa release, e o Release manager ficaria pedindo uma aprovação que ninguém pode dar (a proteção da branch não exige revisão; a exigência é do app). Com `runner.release.soleMaintainer` ligado (Configurações › Runner, "Só eu mantenho o repositório"; desligado por padrão, e um config sem o campo vale desligado, sem passo de migração; **só o computador muda**: um navegador pareado o vê e não o muda, e o `config:cycle-save` recusa o caminho), **o sim da pessoa em Ações num `merge-pr` vale como a aprovação**, e só quando as três coisas valem: (1) o sim é dela, dado em Ações (`approveAction`): uma chamada que a autonomia do agente deixaria sair nunca tem esse valor; (2) o pull request foi aberto **pela conta que o app usa no host** (`currentUser`, lida na hora; o nome compara sem caixa, e um autor que o host não disse não é de ninguém); (3) **ninguém pediu mudanças** nele (uma revisão de "pedir mudanças" que não acabou mostra que há quem revise; a pessoa a resolve ou a descarta no host). Um pull request que **outra pessoa** abriu continua precisando da aprovação no host, e a recusa diz quem o abriu. Todas as outras conferências do `merge-pr` ficam como estão: aberto, do mesmo repositório, não rascunho, apontando para a branch da release, a cabeça congelada no plano igual à do host e à lida do remoto, verificações que passam. Com o interruptor ligado, **todo `merge-pr` espera o sim**, mesmo com o Release manager autônomo (`releaseWaits` em `src/shared/release.ts`; `runReleaseAuto` o recusa), inclusive o de um pull request aprovado no host: o interruptor diz que a revisão é o sim da pessoa, e um agente não o dá. Nas atividades, um pull request aberto que é da pessoa, sem pedido de mudanças, não rascunho e com as verificações passando aparece como **seu e integrado com o seu sim em Ações** (`selfReview`), em vez de "ainda não aprovado", e é isso que o Release manager lê para pedir o `merge-pr` sem esperar uma aprovação. O limite: o app não pergunta ao host se existe outra pessoa que possa revisar; é a pessoa que o diz ao ligar o interruptor, e num repositório com outras pessoas revisando ele fica desligado.

Nenhum passo recebe `--emergency` ou `--allow-branch`, e o que o script imprime (os comandos de push) nunca é lido: um push é um passo próprio, que monta as referências sozinho, sem force. **O script é quem decide** se uma versão pode ser cortada; o app não copia as regras dele. Cada passo é **auditado** (`kind: 'release'`, ou `push`; a operação, a versão, a execução e o commit antes e depois) e **recusado num workspace de teste**. **Quem decide se sai sozinho** (D6 e D18): `push-branch` e `push-tag` **e também `beta` e `stable`** **sempre** esperam o "sim" da pessoa em Ações, mesmo com o Release manager autônomo, e o app recusa os quatro por `runReleaseAuto` mesmo se pedirem. O motivo de `beta` e `stable` é que cortar roda o `scripts/release.sh` **do próprio repositório** (e, com ele, o que ele chama: `npm`, os testes, a compilação) sobre o código dos pull requests já integrados, **sem sandbox, como a pessoa**: um agente que decide sozinho não pode escolher o momento de rodar isso. `open` (que roda o script **da `main`**, não o de uma branch de release; o que representa a `main` é o `origin/main`, e a `main` local só vale num repositório **sem `origin`**: com um `origin` cuja `main` não se lê, o passo é recusado), `merge-pr` (com o portão endurecido acima; com `runner.release.soleMaintainer` ele também espera sempre o sim) e os comentários da issue de acompanhamento seguem a autonomia do agente: autônomo, saem pela porta, auditados com o agente; senão, uma proposta em Ações. Os passos de uma mesma release **não rodam ao mesmo tempo**: há uma fila por pasta de worktree (`release-X.Y.Z-steps`), no caminho do "sim" e no do agente, e um `beta`, um `push-branch` e um `push-tag` aprovados juntos rodam um depois do outro, na ordem dos cliques. **A ordem entre eles é a da dependência, não a dos cliques.** Cada passo que a execução propõe leva o seu grupo, a etapa e a tentativa que o pediram (`ReleaseAction.group`), e um passo **só pode ser aprovado depois dos passos do mesmo grupo de que ele depende** (`releaseStepNeeds` e `releaseBlockers` em `src/shared/release.ts`): um `push-branch` da release depois do `beta`, do `merge-pr` e do `open`; um `push-tag` da beta depois desses e do `push-branch` da release; o `push-branch` da `main` depois do `stable`; o `push-tag` da estável depois do `stable` e do `push-branch` da `main`; um `beta` ou um `stable` depois dos `merge-pr` e do `open`. Enquanto um desses espera, roda ou falhou, o "sim" é **recusado antes de qualquer coisa rodar** (`approveAction`, sem auditoria, a ação continua esperando) com o motivo, que aparece em Ações e na conversa da execução (`runner.release.stepWaits`); o botão de Ações já fica desligado e diz o que falta. Um passo que a pessoa **pulou** não segura nada (é decisão dela), e um passo de outra etapa ou de outra tentativa também não. O desenho é a recusa, e não uma fila que roda o push quando o corte terminar, porque o "sim" é dado sobre a prévia de um passo ("Ver o envio"): antes do corte, a prévia mostra o que o remoto já tem, e um "sim" dado nela não cobre o commit que o corte ainda vai fazer. Foi o que aconteceu numa release real: os dois pushes, aprovados antes do corte, não enviaram nada, e o corte ficou só no worktree do app. **Um push que não envia nada diz isso.** Antes de enviar, o push lê o remoto (`git ls-remote origin <ref>`); se ele já tem exatamente o objeto que seria enviado (o mesmo commit da branch, ou a tag da beta anterior), nada é enviado, a ação termina como **"nada enviado"** (`ReleaseAction.nothingSent`, um selo próprio em Ações, `sent: false` na auditoria) e a conversa diz que a release não andou no host (`runner.release.nothingSent`), em vez de um "feito". Se a pasta do worktree da release foi apagada e o git ainda a lembra (ele a lista como `prunable`), o app a refaz com `git worktree add --detach --force` **só para esse caminho**: nunca roda `git worktree prune`, que esquece também o registro de outros worktrees do repositório cuja pasta sumiu (um disco que não está montado); se ainda falhar, diz isso com o caminho. Isso pede o git **2.31 ou mais novo** (as versões anteriores não marcam o worktree como `prunable`, e então o git recusa o caminho) e **nunca toma um worktree travado** (`git worktree lock`): nos dois casos o erro diz para rodar `git worktree prune` ou `git worktree unlock <caminho>` no clone. O limite de tempo do script (`scriptTimeoutMs`) mata o **grupo de processos** inteiro, não só o `bash`, e libera o worktree: os locks que o script deixou (o índice e o `HEAD` do worktree, a branch da release e as tags da versão) são removidos **só se foram feitos depois de o passo começar** (um mais velho é de outro processo, o git da pessoa talvez), e a árvore volta **ao commit em que o passo começou** (`reset --hard` nele: um commit que o script morto fez no caminho é descartado; uma tag que ele fez fica, e o passo seguinte a vê). Só os locks de tag da própria versão (`vX.Y.Z.lock` e `vX.Y.Z-beta.N.lock`, nomes exatos) contam. Depois que o script sai, o que sobrou vivo no grupo dele também é morto. O passo termina quando o script **sai**, mais uma curta tolerância para as últimas palavras dele: um processo que saiu do grupo e segura os canos abertos não segura o passo nem a fila.

**O que a fronteira de confiança é.** Um corte **roda código da pessoa, não do app, sem sandbox**: o `scripts/release.sh` do repositório e o que os pull requests integrados puseram nele. É por isso que D18 o deixa sempre para o "sim"; D6 e D18 cobrem os envios e os cortes do app, e **nada além disso é isolado**. O checkout da pessoa não é tocado (arquivos, branch e HEAD), mas o worktree dos passos **divide referências com o repositório dela**: a branch `release/X.Y.Z`, as tags `vX.Y.Z[-beta.N]`, os `origin/*` que um `git fetch` atualiza e a entrada em `.git/worktrees` existem no repositório dela e aparecem num `git branch`, `git tag` ou `git worktree list`. Os comandos do app usam `-c core.hooksPath=/dev/null -c core.fsmonitor=false` (sem hooks do repositório e sem `fsmonitor`) em `worktree add`, `fetch` e `status`, mas o script do repositório roda como ele é. Ressalvas: o `git push` do app ignora `push.followTags` e o espelhamento (acima), mas **usa a configuração de transporte da pessoa como ela é** (`url`, `pushurl`, `insteadOf`, `core.sshCommand`, os ajudantes de credencial, `push.pushOption`); os **filtros e drivers de merge definidos na configuração do git da própria pessoa** (o LFS, o git-crypt e parecidos) **rodam** sobre o `.gitattributes` que um pull request traz, durante o `merge-pr` (o app desliga hooks e `fsmonitor`, não filtros nem drivers: a pessoa que os instalou já confia neles, e o `.gitattributes` é do pull request); e o `git worktree add --force` toma o registro de **um** caminho que o git lista como `prunable`, nunca o de outro.

**A ferramenta `ReleaseAction`** é como o Release manager pede um passo: uma ferramenta do app, como a `VcsRead`, nos dois motores (a ferramenta do motor aberto e um servidor MCP no SDK do Claude), só para uma execução de release. O esquema dela aceita as seis operações e uma versão, mais `pr`, `head`, `from`, `branch` (`release` ou `main`) e `channel` (`beta` ou `stable`) onde cabem: nenhum caminho, nenhuma flag. A resposta diz ao agente, em texto, se o passo **rodou**, se **espera a pessoa** ou por que foi **recusado**; ele não tem shell, não escreve arquivo e não faz push. Um passo que demora (a beta roda as verificações do CI) não faz o limite de silêncio da etapa parar o agente: a chamada avisa que está viva. Cada vez que uma etapa roda (a pessoa pode devolver para outra beta) é um passo novo, com chave própria.

**Quatro esperas** (`WAIT_KINDS`, o editor de fluxo e `flowCheck`): `release-approved` segue quando **nenhum** pull request está aberto contra a branch da release; um que a pessoa não quer na versão se fecha ou se aponta para outro lugar (ou `runs:skipWait`). `beta-age` (`minutes`, `label`) segue quando a **última** beta da versão está publicada no host há `minutes` minutos (a última é a maior entre as tags do clone, `localTags`, e as betas que o host mostra publicadas, perguntadas uma a uma de `beta.1` em diante: uma beta cortada em outro lugar também conta) e **nenhuma issue aberta** traz o rótulo bloqueante (`label`, `beta-blocker` se vazio); um "relato que bloqueia" é só isso. Uma beta cortada e ainda não publicada (um rascunho) não conta: a espera recomeça. Onde o host não diz (Bitbucket: sem releases e sem rótulos em issues) a espera continua até a pessoa seguir com `runs:skipWait`. `beta-age` sem `minutes` é um erro do fluxo (`wait-no-event`). As outras duas são o que impede uma execução de seguir, ou de terminar, com uma release que o host não tem: o fim de uma etapa de corte é o agente ter pedido os passos, não os passos terem acontecido. `beta-out` segue quando a **última** beta (a mesma conta de `beta-age`) tem a tag **no remoto**, lida na hora por `git ls-remote` (`remoteReleaseOf` em `src/main/runner/release.ts`, nunca o que o último `fetch` deixou), e a pré-release dela **publicada** no host; um corte que ficou no worktree do app, ou uma tag que ainda é a da beta anterior, a deixa esperando. `stable-out` segue quando a tag `vX.Y.Z` está no remoto e o commit dela está na `main` do remoto (também depois de a `main` andar). Um remoto que não se lê é "ainda não". As duas se pulam como as outras, com motivo (`runs:skipWait`).

**O fluxo do modelo** (`release-flow`, ids que começam por `release-`): planejar (`RELEASE_PLAN.md`) → gate → montar a branch (`open` se falta, `merge-pr` de cada um aprovado, ou de cada um da pessoa quando só ela mantém o repositório) → `release-approved` → cortar a beta (`beta`, `push-branch`, `push-tag`) → beta no host (`beta-out`) → `beta-age` (um dia, `beta-blocker`) → gate → cortar a estável (`stable`, `push-branch` na `main`, `push-tag`) → estável no host (`stable-out`) → publicada (a execução termina aqui, e só chega aqui com a tag estável na `main` do remoto; a issue é fechada quando o host mostra a estável publicada). Um workspace que aplicou o modelo antes das duas esperas guarda o fluxo antigo em `devCycle.flows.release`: aplicar o modelo de novo as acrescenta. Um gate reprovado volta à etapa que ele julgou (o da estável, à beta). O Release manager lê o host (`tracker: read`), não roda comandos (`shell: none`) e não muda arquivos (`permission: read`); é autônomo para o que a autonomia cobre (abrir a branch, integrar pull requests aprovados, comentar), e os cortes e os envios esperam um "sim" de qualquer modo (D18).

### Execução de documentação

Uma execução de documentação **cria ou atualiza a `.coxia/` de um repositório** (o formato, a entrega aos agentes e a conferência estão em [`harness.md`](harness.md)). Começa em Configurações › Documentação, por **Criar a documentação** (ou **Atualizar**), e não de uma issue: `Run.docs: { mode: 'create' | 'update' }`, ao lado de `Run.subject` (que continua sendo o da release), com a issue sintetizada `docs:<repo>`, número 0, que mantém "uma execução por vez" por repositório. `runs.activeFor` a acha; o publicador não escreve em issue nenhuma (a conversa da execução é o registro) e `prOf` e `prState` só usam o pull request gravado.

- **Início** (`Runner.startDocs`, canal `docs:start`): confere duplicata, o fluxo `docs-flow`, a identidade de commit e o repositório (`repo-ambiguous`, `no-clone`), cria o worktree a partir da ponta do remoto na branch `cycle/docs-<repo>-<AAAAMMDD>` (um segundo no mesmo dia dá `branch-exists`), escreve `.coxia/.gitignore` com `.run/`, o resumo da tarefa como `0_ISSUE.md` (o modo, o que `.coxia/` tem e o estado de cada arquivo, e os arquivos do Claude Code do próprio repositório como candidatos à importação) e faz o primeiro commit. Não instala dependências: o rascunho não roda código. Sem o fluxo no workspace, o início é recusado com `no-docs-flow` até a janela pedir o "sim" e aplicar o modelo (`applyFlow`).
- **O fluxo** (`devCycle.flows.docs`, do modelo `docs-flow`, `runKind: 'docs'`): `docs-draft` (trabalho, `docs-writer`, produz `IMPORT_NOTES.md`) → `docs-gate` (gate da pessoa, devolve a `docs-draft` com o motivo) → `docs-publish` (trabalho, o mesmo agente: aplica o que o gate pediu e escreve a descrição do pull request) → `docs-ready` (espera `pr-merged`) → `docs-done`. Duas etapas escrevem porque o push é proposto ao fim da última etapa que altera o worktree: só depois do gate. Nenhum squad pode se chamar `docs`.
- **Onde escreve:** `Confinement.writeRoot` faz o guarda de escrita valer só para `<worktree>/.coxia/`, enquanto a leitura segue no worktree inteiro; sem comandos. A pasta do ciclo fica em `.coxia/.run/`, ignorada pelo git: o pull request leva `.coxia/**` e o `.gitignore` de uma linha, e nada do registro.
- **Sem `Closes #<n>`:** a descrição vem do modelo `docs-pr` (`devCycle.comments`), com as seções "o que isto acrescenta", "o que veio do Claude Code", "o que ficou de fora e por quê" (do `IMPORT_NOTES.md`) e "o que conferir". O push e o pull request esperam o "sim" em Ações, e num workspace de teste são recusados na confirmação.
- **Antes do push** o app reescreve o texto de `.coxia/` (caminhos locais e credenciais, só no corpo), diz na conversa o que mudou e carimba o cabeçalho dos arquivos que a passada mexeu, num commit seguinte (veja [`harness.md`](harness.md)).

**Nas execuções comuns**, num repositório com `.coxia/`, a etapa que muda código recebe a seção da documentação (escolhida por etapa, papel e caminhos) e a instrução de corrigir no mesmo ramo a regra que a mudança torna falsa; a etapa de revisão recebe as regras não conferidas que o ramo deixou para trás, e cada uma vira um achado que não bloqueia por padrão. `pushStagesOf` não muda: a mudança de documentação segue no mesmo pull request. Sem `.coxia/`, a seção e a instrução não existem.

### As telas das execuções

- **Hoje.** O cartão de uma atividade do ciclo de agentes mostra o selo da execução (trabalhando, esperando você, com uma pergunta, esperando você iniciar ou aceitar, aguardando um evento, falhou, concluída; no selo: "Gate 1 · esperando você"), o squad quando há squads, e a pergunta ou a falha como bloqueio (entra na contagem de bloqueios e no filtro). **Iniciar o ciclo** aparece no cartão que não tem execução em andamento, no app e no navegador pareado; se o projeto da issue tem vários repositórios, pede qual. Um bloco "Execuções esperando você" lista o que está num gate, numa pergunta que chegou até você, numa etapa a iniciar ou a aceitar, ou falhou. **Execuções** e **Fórum** estão no topo de Hoje e no menu "Mais" do telefone, com a contagem do que espera você e das mensagens novas.
- **A execução.** O cabeçalho traz a issue, a branch, o squad (e por que a execução está nele), o pull request e as execuções ligadas; se a execução segue uma versão anterior do fluxo, diz isso e oferece passar para o fluxo atual (`runs:migrateFlow`). "O que falta" mostra o que a execução espera e os botões do estado:

  | Estado | Botões |
  |---|---|
  | a iniciar | iniciar a etapa, devolver para uma etapa |
  | a aceitar | aceitar (nota opcional), devolver (nota obrigatória), devolver para uma etapa |
  | gate | aprovar (motivo opcional), devolver ou pular (motivo obrigatório), devolver para uma etapa, e o quiz do gate como ferramenta |
  | pergunta | responder; o caminho que a pergunta fez fica à vista; devolver para uma etapa; numa execução que espera o squad, escolher entre os candidatos (a proposta da triagem vem marcada) ou seguir sem squad |
  | aguardando | seguir sem esperar o evento (motivo obrigatório; só anda para a frente e diz para onde), devolver para uma etapa |
  | falhou | tentar de novo, devolver para uma etapa |
  | encerrada | devolver para uma etapa (reabre a execução) |
  | qualquer um, até o fim | cancelar (pede um segundo clique; nada é apagado) |

  Debaixo, as chaves de autonomia do agente da etapa e do squad dele (valem a partir do próximo início de etapa ou publicação) e, enquanto uma etapa trabalha, a atividade ao vivo do agente. As **etapas** formam uma linha do tempo: cada uma com o agente, se age sozinho ou espera você (como estava quando a etapa começou), o estado, as tentativas, **o uso do modelo** (chamadas e tokens, somados nas tentativas, mesmo nas que falharam ou foram interrompidas; o custo é o que o provedor informou, como o OpenRouter, ou um valor marcado como estimativa quando a chamada do SDK não foi para a API própria da Anthropic: ali o número do SDK é um preço de lista, não o cobrado), os documentos (abrem na própria tela) e os comentários no rastreador com a situação (publicado, espera o seu sim, retido, recusado, apagado) e o link. **Desfazer** num comentário publicado propõe apagá-lo, uma ação que espera o seu sim em Ações. Mais abaixo, **Revisão e QA**: cada rodada com o veredito e os achados (arquivo, linha, gravidade, sugestão) e a situação da conversa de cada achado no pull request: aberta, ainda aberta na rodada seguinte (a conversa recebeu uma resposta) ou resolvida. Essa situação é deduzida das rodadas que a execução guarda (o mesmo critério com que o runner responde ou resolve), não lida do host.
- **A conversa.** Ao lado das etapas (no telefone, uma aba), a conversa da execução: cada mensagem com quem disse (agente com a função, você, o app), o tipo (relato, pergunta, resposta, passagem, decisão, sistema, pedido), se é registro público (pode ir ao rastreador) ou interno, o link do comentário quando foi publicado, os documentos que cita e quem chamou. Uma pergunta e tudo que se disse sobre ela viram um **caminho**: quem perguntou a quem, cada vez que passou adiante, e o motivo de ter chegado a você. As mensagens chegam ao vivo (`forum:message`). Escrever `@` completa com os agentes da equipe; um agente chamado responde ali, só lendo. **Com uma pergunta esperando, o que você escreve sem chamar um agente é a resposta**, e a caixa avisa.
- **O fórum.** Os canais (o geral, o dos squads, um por squad) e as conversas (das execuções e as gerais que você abriu), com as mensagens novas por dispositivo (a primeira vez que um dispositivo abre o fórum, o que já existe conta como lido), o filtro por squad e a criação de uma conversa geral. Num canal, `@` não chama agente.
- **As execuções.** Todas as execuções, com filtros por situação (esperam você, trabalhando, aguardando, falharam, encerradas) e por squad; o que espera você vem primeiro.
- **Avisos.** Um gate, uma pergunta que chegou a você, uma falha, uma etapa a iniciar ou a aceitar e o fim são avisados pelas notificações de sempre e, com o acesso pelo navegador, por push no telefone; tocar abre a execução.
- **Ações.** As propostas do runner (comentário, revisão, pull request, apagar, prioridade, status, issue para outro squad, rótulo do squad, push) mostram, antes do "sim", o que vão escrever: o comentário como vai ficar (e o texto como é enviado), as linhas da revisão com o veredito e o que acontece com a conversa de cada uma (comentário novo, resposta, conversa resolvida), a descrição do pull request, os rótulos que entram e saem, quantas escritas de um grupo já rodaram. As escritas em si ficam numa lista que se abre.
- **Cerimônias por squad.** Com squads, o cartão da pré-daily em Hoje e a tela da retro pedem para qual squad (ou o espaço de trabalho todo); a escolha vale para uma pré-daily que ainda não começou, e a chamada, a ata, o histórico e a retro dizem o escopo.
- **No navegador pareado.** Tudo isso abre no PWA, e tudo funciona: ler a execução, os documentos e a conversa, responder perguntas, escrever nas conversas, iniciar, aceitar, decidir portões, tentar de novo, cancelar, desfazer, escolher o squad, devolver para uma etapa, as chaves de autonomia e passar para o fluxo atual. A política do navegador (`src/main/webPolicy.ts`) não recusa nenhum canal `runs:*`; o que ela recusa é o que faria esta máquina rodar um programa ou ler uma pasta (a configuração inteira, os segredos, os comandos do runner). `test/run-web.test.ts` confere que nenhum botão da tela depende de um canal recusado, com uma exceção decidida: **Assumir o controle** da tela ao vivo, que o navegador não mostra (ele só assiste).

### Não verificado

- **O que rodou com um modelo de verdade, e o que não.** Um modelo real percorreu o ciclo, **uma vez e em pequeno**: DeepSeek v4.1 flash pelo OpenRouter, no motor aberto, em uma issue pequena de um projeto Node (uma função que gera o trecho de endereço de um título), de ponta a ponta (triagem, refinamento, plano, implementação, revisão, QA, merge e a nota para quem abriu a issue), contra um host GitHub **falso** com memória. Foram duas execuções de cerca de 50 chamadas ao modelo cada, a US$ 0,3 por execução: uma terminou; a outra parou no limite de rodadas da revisão. Dali saíram os defeitos corrigidos nesta fase (a revisão e a QA gastando um orçamento só, a proposta de prioridade perdida, a QA que não rodava nada, os commits e documentos com cabeçalho e prefixo da issue, o relógio que cortava quem trabalhava, entre outros). Depois das correções, duas execuções a mais com o mesmo modelo mediram o que faltava: a mesma issue do endereço do título e uma issue ambígua, que perguntou a quem a abriu e à pessoa e foi retomada depois de o processo ser reiniciado, a US$ 0,08 e a cerca de US$ 0,14 (o custo que o provedor informou). **Ainda não** se exercitou com um modelo de verdade: os laços de devolução entre a revisão ou a QA e o desenvolvedor, a pergunta do limite de rodadas, a segunda rodada da revisão, os saltos da cadeia de perguntas de agente para agente, os limites de passos (`turns`), um `needsPerson` sem pergunta, os squads, o desfazer, outro modelo ou provedor (Ollama, OpenAI, Groq), o caminho do Claude Agent SDK no runner, um host de código real (GitHub, GitLab ou Bitbucket de verdade) e um repositório grande. Todo o resto das garantias abaixo vem dos testes, que usam um motor roteirizado, um host que só lê (ou um host falso com memória) e repositórios git temporários: o que um modelo de verdade faz com os prompts em geral (e se escolhe bem o `commit`, os achados e as perguntas) segue sem medida; os prompts em inglês foram escritos por tradução.
- **Sandbox e leitura por agente (#30).** A sandbox foi exercitada de verdade no bubblewrap 0.9.0 de uma máquina Ubuntu 24.04 (o teste `test/sandbox-bwrap.test.ts` roda `bwrap` de verdade quando ele existe e funciona, e é pulado senão): escrita fora do worktree falha, a pasta pessoal não existe, nenhuma variável do app passa, só há o loopback, o `.git` não muda, um processo iniciado por um comando está lá no seguinte e some com a etapa, o limite de tempo interrompe, e a cópia da QA não chega ao worktree. O modo do registro foi exercitado só até o proxy (o repassador dentro da sandbox alcança o proxy e este recusa um endereço fora da lista), **sem rede e sem registro de verdade**: que `npm install` funcione por ele **não foi observado**. A rede **`open`** nasce **não exercitada** no que importa: no teste real desta máquina a sandbox ficou com a interface de rede do computador e `getent hosts` resolveu um nome público (em `/etc/resolv.conf`, que ali é um link para fora de `/etc`, o alvo real foi montado somente leitura), mas **alcançar um endereço público de verdade não foi observado**; e fora de um Linux com bubblewrap funcionando a escolha não existe. **Nunca** rodou com modelo de verdade, nem com o Claude Agent SDK de verdade (a ferramenta `Shell` e o servidor MCP foram vistos com o SDK substituído), nem em macOS ou Windows (lá não há sandbox), nem em outra distribuição ou kernel (o limite de processos conta por user namespace só desde o Linux 5.14; uma distribuição que recusa user namespaces é reportada como sem sandbox). Sem rede, um projeto cujos testes precisam de pacotes que não estão no repositório não roda: ligue o registro. A sandbox é uma mitigação, não uma máquina virtual: sem filtro seccomp, sem limite de CPU, sem teto para a soma da memória dos processos nem cota de disco no worktree; uma falha do kernel a vence. Um segredo **dentro do repositório** (um `.env` commitado) é legível por um comando no worktree (a saída é mascarada, e `Read`/`Grep`/`Glob` continuam recusando esses arquivos). Um `.gitattributes` criado na sandbox pode nomear um driver de filtro que a configuração de git **da pessoa** define, e o `git add -A` do app o rodaria fora da sandbox. Um agente sem confinamento no Claude Agent SDK ainda lê fora do worktree (menos nomes que parecem segredo): isso já existia e não foi tratado aqui.
- O guarda foi testado com travessia de caminho, links simbólicos, caminhos absolutos e `.git/hooks`, nos dois motores; **não** contra um repositório hostil de verdade. Um comando da lista executa código do repositório (um `npm test` roda o que o `package.json` mandar) e pode fazer tudo que o usuário pode: a lista curta e escolhida pela pessoa é a defesa. No Claude Agent SDK o comando roda como filho do processo do SDK, que tem a chave do provedor: as variáveis que parecem credencial são removidas por `env -u` em cada comando, o que foi testado com as opções que o SDK recebe e executando o comando reescrito, **não** com o SDK de verdade (que o hook possa devolver `updatedInput` com `allow` está nos tipos da versão instalada, mas o comportamento do processo real não foi observado). Uma credencial que não tenha nome de credencial passa.
- O `git add -A` leva para o commit tudo que um comando da lista criou e o `.gitignore` não cobre.
- Os links de dependências foram testados com repositórios git temporários e o guarda; **não** com um `npm install` de verdade dentro de um worktree ligado, nem com gerenciadores de pacotes que guardam as dependências fora de `node_modules` (pnpm global, Yarn PnP, `.venv` de outro caminho): nesses casos a conversa pode dizer que não há nada para ligar.
- Os comentários, a revisão, o push e o pull request só rodaram contra um host falso com memória (a forma do GitHub, o provedor e o validador de verdade na frente) e contra um repositório git temporário com uma origem local; **nenhum host real**. O mesmo vale para os provedores GitLab e Bitbucket (as escritas novas foram testadas por comandos planejados contra respostas modeladas na documentação; ver [`vcs-providers.md`](vcs-providers.md)). Não se sabe como um modelo de verdade escreve as seções do comentário, nem se o conferidor (palavras de agente, de ferramenta, primeira pessoa) segura ou deixa passar demais, nem se o texto de uma revisão de verdade casa com a posição no diff.
- A conferência do texto é de vocabulário: ela pega o que sabe nomear. Links e imagens que o agente escreve saem como foram escritos. Um segredo com cara de texto comum, um nome de pessoa e o conteúdo errado passam; e `redact` mascara também hashes longos de commit (32 caracteres ou mais).
- Os números de linha de um achado são os do commit que o revisor viu; o app os põe no diff atual do pull request sem saber se a cabeça dele é a mesma. Se o código andou, a linha pode apontar para outra coisa que também está no diff; o app só garante que não é uma linha fora do diff.
- A descrição do pull request é escrita quando ele é criado e não é editada depois; um pull request aberto à mão tem a descrição de quem o abriu. O pull request usa a integração primária (a das issues): um repositório de outro host não é tratado.
- As esperas, a cadeia de perguntas e o desfazer só rodaram com o motor roteirizado e o host falso: não se sabe se um modelo de verdade escolhe bem entre `answer`, `pass` e `needs-person` (o prompt manda não decidir o que é da pessoa, mas isso é texto, não uma garantia), nem se o agente da porta de entrada pergunta a quem abriu a issue no momento certo. `pr-merged` lê o estado do pull request pelo provedor; um pull request integrado por outro caminho (fora da branch da execução) não é visto, e `runs:skipWait` é a saída. `reporter-reply` toma por resposta o primeiro comentário de uma pessoa depois da pergunta, sem saber se responde a ela, e a conta do próprio usuário (que posta os comentários do app) também conta quando escreve sem o marcador do app.
- A proposta de prioridade do Product Owner reaproveita os rótulos de `devCycle.priority` que se podem gravar; o marco é só dito na conversa e na proposta, porque não há escrita para ele. Não se mediu se o Product Owner propõe prioridades razoáveis.
- O painel de custo e a retenção ainda não reconhecem as sessões do runner como sessões do app.
- Os squads só rodaram com o motor roteirizado e o host falso: não se sabe se um modelo de verdade propõe bem o squad na triagem, se o contato faz um pedido quando deve (e não quando consegue responder sozinho), nem se o contato que recebe separa uma pergunta de uma mudança e escreve uma issue que o outro squad consegue trabalhar sem a conversa. A criação de issue (`createIssue`) nunca rodou contra um host real, nem o `DELETE`, os rótulos e o fechamento de uma issue que a espera `linked-done` lê. A escolha do repositório quando o projeto tem vários e o escalonador não escolhe um (pelo squad que os rótulos ou as pastas apontam) é uma regra minha, não medida. Um "não" a uma proposta em Ações não avisa o runner; uma execução cancelada não resolve a espera. O canal `squads` guarda o que os contatos disseram, mas uma menção da pessoa nele (`@contato`) não chama o agente: só nas conversas de execução. A tela dos canais e do pedido existe agora (o fórum); a do editor de squads é da configuração.
- **A release como execução (#27).** Os passos rodaram contra repositórios git temporários com o `scripts/release.sh` de verdade (as verificações trocadas por um `npx` falso, o auditor público por um que passa), uma origem em disco e o host falso com memória (a forma do GitHub, o provedor e o validador de verdade na frente), e a execução inteira (planejar até a estável, as duas esperas, a issue de acompanhamento criada e fechada) com o motor roteirizado: **nenhum host real**, **nenhum modelo de verdade** (não se sabe se o Release manager escolhe bem o `head`, os passos e a ordem, nem se escreve o plano e os comentários com a qualidade que se quer) e **nenhum `npm run dist` nem fluxo do GitHub Actions** (a beta publicada e a estável publicada são o que o host falso diz; que `getRelease` ache o rascunho de uma pré-release publicado no GitHub de verdade, e o Bitbucket sem releases, não foram vistos). As verificações do corte (`tsc`, `vitest`, a compilação) rodam de verdade só na máquina da pessoa: o passo pode demorar minutos, e o tempo máximo do script é 40. O passo roda num worktree próprio e deixa o checkout da pessoa como estava (um teste confere o HEAD, a branch e o status dele depois de uma release inteira); o worktree recusa uma árvore suja. Uma branch da release que a pessoa deixou com checkout no clone dela é recusada (não pode ter checkout duas vezes). O `merge-pr` só entende o pull request do mesmo repositório (um de fork é recusado) e exige a aprovação sobre a cabeça do plano. O que cada host consegue provar: o **GitHub** diz o commit de cada revisão e a relação do autor (`author_association`), e só conta a revisão sobre a cabeça e de dono, membro ou colaborador (isso **não é** permissão de escrita: um colaborador convidado só para ler também aparece assim, e é o melhor que as revisões trazem; mais de 300 revisões num pull request deixam `onHead` falso, porque o que não foi lido não se sabe); o **GitLab** e o **Bitbucket** só dizem se há aprovação (ela vale para o estado atual do pull request, e o GitLab pode descartá-la quando chega um commit novo, conforme a configuração do projeto), e ali quem protege é a cabeça congelada no plano, a cabeça atual do host e o commit lido do remoto serem os mesmos; uma verificação que o host não lê é tratada como em andamento nos três; a ordem dos passos que esperam um "sim" é a de quem aprova (o script recusa o que fica fora de ordem, e uma ação que falhou pode ser confirmada de novo). Uma execução não vê um pull request aberto por fora do projeto das issues.
- **A execução de documentação.** Só rodou com o motor roteirizado, o host falso e repositórios git temporários: o rascunho, o gate, o push depois do gate, o corpo do pull request sem `Closes`, o guarda de escrita que só vale em `.coxia/` e a pasta do ciclo ignorada. **Não** se sabe se um modelo de verdade importa certo (o que é fato do projeto e o que é regra de sessão), nem como a tela de Ações mostra uma proposta de execução sem issue (o número 0 não deve aparecer); está no plano de teste da issue. ## English

The runner takes an issue through the [agent cycle](cycles.md) (`agent-flow`): it makes a branch and a worktree of the issue's repository, copies the issue into the cycle folder and runs the agent of each stage, one at a time, until a gate, a question, a failure or the end. What it does stays in the worktree and in the run's thread; what goes to the **code host** (a comment per stage on the issue, the review on the pull request's lines, the push and the pull request) follows [one rule](#what-goes-to-the-code-host): either the agent is autonomous and the write goes out by itself, recorded, or it waits for your "yes" in Actions; the push and the pull request always wait. Configuration: the `runner` section in [`configuration.md`](configuration.md) and the comment templates in `devCycle.comments` ([`cycles.md`](cycles.md)).

### Starting a run

`runs:start(ref)` (the card's reference, such as `app#101` or just `101`). A run always begins with an issue read from the host: a card that exists only on the workspace's **own board** never starts a run, because the board is not the tracker; a card that became an issue on the host is an issue the host lists, and starts a run like any other. The app reads the issue and its comments through the provider, read only, and then:

1. Picks the repository: the only one in `projects.repos` whose `projectPath` is the issue project (or the only one there is, or the one the call names); without a local checkout it looks one up by its origin.
2. Fetches the origin's default branch (a read) and makes the worktree at `<worktreesDir>/<repo>/<n>-<title>` on a new branch `cycle/<n>-<title>`. A branch or a folder that exists is refused, never reused.
3. Writes `docs/cycles/<n>-<title>/0_ISSUE.md` (title, address, labels, description and human comments, with anything that looks like a credential masked) and commits it as `feat: add the issue record #<n>`.
4. Links the dependency folders of its clone into the worktree (see [Dependencies of the clone](#dependencies-of-the-clone)), opens the run's thread and enters the first stage. Whoever starts the run starts its first stage too.

There is one run per issue at a time, and only in a workspace whose cycle is the agent cycle. If a step fails after the worktree exists, the worktree and branch that call made are removed: the only thing the runner ever deletes.

### Dependencies of the clone

A worktree starts with no `node_modules` or `.venv`, and without them the commands the app runs before QA and the `npm test` of an agent that writes fail with `vitest: not found` (exit 127). The person's clone usually has them installed, so the app **links** what is missing: for each dependency folder the clone has and the worktree lacks (`node_modules` and `.venv` at the root, one folder down such as `sidecar/.venv`, and under `packages`, `apps`, `libs` and `services` such as `packages/a/node_modules`; at most 30) it makes a symbolic link in the worktree to the clone's folder. That happens when the run starts and again before every stage that runs commands (an agent with the `worktree` permission, and the app's commands before QA), so a run made before this, or sent back to a stage, gets its links at the next such stage.

- **Only where the repository ignores the folder** (`git check-ignore`, before the link is made), so the app never commits it. Because a link is not a folder to git, `node_modules/` in a `.gitignore` does not cover the link: the app's `git add -A` and its check for changes leave `node_modules` and `.venv` out by name.
- **Never over something that is already there**, and only inside a folder of the worktree that is a real one (not a link).
- The thread says once which folders were linked, or that the clone has none (QA may not be able to run the tests; install them in the clone and the next stage that runs commands links them).
- **The commands run with the clone's dependencies**, which is the point: an `npm test` or `npm run typecheck` uses, and can change, what is there (an `npm install` inside the worktree would write to the clone). An agent, on the other hand, **cannot write** through the link: the guard refuses a path that leaves the worktree by a symbolic link, and that holds for a linked `node_modules` too.
- Switch it off with `runner.linkDependencies: false` (default: on; a stored config without the field reads as on). It is in the runner tab, also in a paired browser.

### A stage

For the current stage, its agent gets a prompt the app builds: the agent's job and instructions, the documents the stage must produce, the cycle folder as it is (the issue and the earlier documents), the latest messages of the thread, the note another stage left for it and the person's answer to a question of its own. Everything that came from outside (issue, comments, thread, files, diff) goes between `<data>` tags and the system text says it is material, not instruction. The texts are in the catalog as `prompt.<family>.runner.*`.

**Documents do not repeat the issue's head.** The prompt asks that each document open with a title of its own, without the issue's reference, title or address (the folder and the file name say which issue it is), and that the release note's title say what changed, with no internal reference (`app#101`). The app also tidies what comes that way when it writes: it takes the issue's reference and title out of the document's title and, right under it, the address, state, labels and author lines the issue record already has; a list that is something else (type, priority) stays.

**Only what was verified is asserted.** The system text of every agent of the runner says to state only what the stage verified (read, ran or saw working) and to mark the rest as not verified; the comment rules repeat it, and so does the guidance of the sections of the agent cycle's comment templates (how it was checked at implementation and in the pull request, what was only read in QA, what was left unverified). It is text for a model: the app does not check whether a claim is true. The read and write rules also say to look around with the Read, Glob and Grep tools and not with `ls`, `find` or `pwd`, which are not on the list and are refused.

**QA runs nothing, but is given results.** Before the QA stage the **app** runs, in the run's worktree and on the delivered code, the commands the workspace allows (`runner.commands`; with no list, the repository's test and typecheck scripts): each as a plain command, with no shell, with the environment cleaned of anything that looks like a credential, for up to 5 minutes, the output cut at its end (where a test says what failed) and masked. QA reads the results (command, exit code and the end of the output) in the prompt, next to what it read in the code; the agent still only reads, unless it is set to `shell: sandbox`: then the app runs those commands inside its sandbox and the agent runs its own ([below](#what-an-agent-may-read-and-run)). The exit codes are kept in `Run.qa[].commands` (the output is not), and the thread says what ran. With no commands configured the prompt says the behaviour was not exercised, only read. Each QA scenario carries a **severity** (`blocking` or `non-blocking`): only a failure that blocks sends the work back; one that does not goes into the comment and the thread. **A command that could not run is not a result of the code:** `ENOENT`, `EACCES` and the shell's exit codes 126 and 127 (the tool the script uses was not found) are kept in `Run.qa[].commands` with `notRun: true`, the thread says which commands did not run and why (`npm was not found by the app`, or what the shell said, such as `vitest: not found`), and QA's prompt marks those commands and tells it **not to pass a scenario that depends on them**: mark it `not-run` and say why. The app's commands (QA's, the ones an agent that writes may run, `runner.commands`, the conflict verification and the code host's CLIs) start with the person's **login shell `PATH`** in front of the app's (read once when the app starts, with `$SHELL -ilc` and a time limit; the AppImage's own folders are left out): an app opened from the desktop menu does not inherit the terminal's `PATH`, and that is where nvm and the version managers put `npm`. The credential cleaning does not change. `COXIA_NO_LOGIN_SHELL=1` turns the reading off (the tests use it).

The answer is structured: `summary` (what it did, for the thread), `commit` (the subject of the code commit: English, imperative, lowercase, with no type prefix and no issue number; the app strips a prefix and a reference that came anyway, and uses the stage's own text when the summary does not read as English, is empty, or the stage only writes documents or ended the pass without changing code), `artifacts` (name and complete content of each document), `handoff` (what the next stage is to do), `question` (something it cannot go on without: it pauses the stage and goes to the agent the author turns to, then to the person), `needsPerson` (the question is a decision only the person can take: it goes straight to them; if the agent marks that and writes no question, the app makes the question from what it said in the summary instead of taking the stage for done), `reporterQuestion` (in the flow's **first** stage: something only whoever reported the issue knows), `priority` and `milestone` (only in the stage that owns the priority, the last `backlog` work stage that has an agent, such as the Product Owner's refinement, when the workspace has priority labels that can be written: a proposal; the backlog stages before it, such as triage, are told the levels and only suggest one in their document, and a value that came anyway is said in the thread not to have been proposed; the proposal's key carries the stage and the attempt, and when no proposal is created — a duplicate, no host, a host with no label write, a label that cannot be written — the thread says why) and, when the cycle has a comment template for the stage, `comment` (a text per section of the template, plus `technical`; the stage that ends with the push also brings `pr`, the title and the sections of the pull request description) and `memory` (the new version of the cycle memory, rewritten by the stage that concludes; empty when the stage pauses on a question — see [The cycle memory](#the-cycle-memory)). A review stage adds `verdict` and `findings` (each with `path`, `line`, `endLine`, `side`, `severity` `blocking` or `suggestion`, `body` and `suggestion`, the exact replacement of the commented lines, only when complete); QA adds `scenarios` (`name`, `result` `pass`, `fail` or `not-run`, `detail`). The **app** writes the documents and makes the commit, never the agent: an agent that only reads produces its documents the same way, and a document the stage does not list is ignored (and said so in the thread). A document is named by its file name alone; a name that comes with its folder is read by its file name, and a name that cannot be written (hidden, with `..`, empty) is left out and said in the thread. A concluding answer that leaves out a document the stage produces (and that is not in the cycle folder) is asked **once** for it, in the agent's same session, before the stage fails; only the documents that were missing are taken from that round, and the rest of the answer stays as it came.

After the answer the app applies the transition, **by the stage's fields** (not by an order in the code): a question pauses the run (and walks the chain of agents, below); a question to whoever reported the issue leaves the stage waiting for the reply on the issue; a `blocking` finding (or `verdict: changes`) sends the work to the stage the review's `returnsTo` names, with the findings as the handoff, and counts a return to that stage (at the `roundLimit` of the stage that returns, the run stops and asks); a QA scenario that fails sends it back the same way, on the same count; anything else is the stage done and the run goes to its `next` (or ends, when there is none). The findings of each round and the scenarios of each QA pass are kept in the run (`Run.reviews`, `Run.qa`) as they were given: that is where the line comments will be built from.

### The cycle memory

The cycle folder keeps, besides the stages' documents, a file of a fixed name: **`MEMORY.md`**. It is the run's memory, and it exists so that a long run loses a decision neither to the folder's read budget nor to the 40-message window the stage gets from the conversation (see [A stage](#a-stage) and [`cycles.md`](cycles.md#the-cycle-memory)). Every stage reads it whole, before the documents, and the stage that concludes rewrites it from the answer.

- **Fixed shape.** The title and the sections in the order **Decisions**, **Constraints**, **Tried and discarded**, **Open questions** and **Where the work stands** (in the workspace language). What the stage returns is normalized to the file's shape: a section that is missing comes back empty, an invented one is dropped and blank runs are collapsed. A stage that pauses on a question writes nothing.
- **What enters by itself.** Before building the text, the app adds to the memory each answer the person gave and each handoff of the conversation, each on a line marked with the message number (`<!-- answer:3 -->`, `<!-- handoff:5 -->`): rewriting duplicates nothing, and what the person decided and what one stage passed to the next survive even after the conversation passes the window. The stage that concludes rewrites the rest, and the markers are reapplied over what it returned.
- **The size.** The cap is a code constant, `MEMORY_MAX` (`10,000` characters): it is not configuration and there is no config migration. Past the cap, the file is still read whole and the prompt tells the stage the limit and asks it to shorten the memory.
- **The person may correct it.** On the run screen the memory opens for editing (only it): `runs:memory(id, text)`. The app writes the person's version, commits it with the workspace identity (the commit message says "update the cycle memory") and records in the history (`memory-edited`, `by: person`) and in the thread (`runner.memory.edited`) that the edit was the person's, not an agent's; the next stage reads the corrected version. The edit is refused while an agent is working in the folder (`memory-busy`) — the person never disputes the file with an agent.
- **No code host.** The memory lives in the worktree and rides the run's commits, like the documents: nothing of it leaves for the tracker by itself, and editing it does not go through `Actions`.

### The record of the activities

Besides the memory of one run there is a record of **every activity of the workspace**, so that an agent called anywhere — a run's thread, a squad channel, a general conversation, the direct conversation of an agent — can answer what is in progress, and so that a restart does not lose where each activity stopped. It is not a document an agent rewrites: it is an index the app projects from the state it already keeps (the run store), and an agent receives a **cut** of it, never the file.

- **Where it lives.** `<workspace>/memory/activities.json`, in the workspace folder the app owns (the same one as `historico/`, `atividade/`, `qa/`; `ATAS` in `env.ts`). It is outside every worktree, so it never rides a pull request and never appears in a commit of the activity. Nothing of it goes through `Actions`: it never reaches the code host.
- **One front per activity.** The key is the reference the run writes (`app#101`; `release:X.Y.Z` and `docs:<repo>` for the synthesized subjects). A second execution of the same issue updates the same front; it is never two. The front carries the reference and the title, where the activity is now (the stage of the cycle, or that it is between stages, or that it ended), the agent working it and the last agent to move it, the decisions and the open questions, where the work stopped and the instant of the last update, plus what the person wrote over it.
- **The app is the only writer.** Every move of a run goes through the store, and the store keeps the front of the activity up to date there: one writer, merge by key, atomic write. A move that could not write the record is logged and swallowed — a move of a run never fails for this file — and the reader rebuilds that front from the run store, so the loss heals by itself. Two activities advancing at the same instant are two keys.
- **It was born before the first run.** A start records the reference once the identity and the repository are known and before the worktree is made, so a start interrupted there leaves a record of the activity ("known, never started") instead of nothing. A start refused before that point records nothing.
- **What a call sees.** A message that names an activity (the reference or the number it carries) or an agent receives the whole front of what it named; nothing named gets one line per activity in progress, plus a line saying one may be named to see it whole. Every stage receives the front of its own activity whole, plus the short list of the others. The section is its own, between `<data>` tags, with a line saying it is material of the app and not an instruction; the record is never added to the tools, to `allowedTools` or to any confinement's roots, so the only way out of it is text in the prompt.
- **What is old is not a lie.** Nothing is ever dropped, and a front whose last update is older than `STALE_AFTER_MS` (30 days) renders as probably finished together with what it records. The answer of one call is bounded (`SELECT_MAX`), and a front that does not fit is named in one line instead of being cut in the middle.
- **The person sees it and corrects it, without a model call.** The runs screen lists the activities (`runs:activities`), one row each with reference, title, stage, agent and where it stopped, and one opens for editing; the correction is saved with `runs:activitySave`, masked and capped, marked as the person's, and it stands until the activity moves again. Both channels are open to a paired browser like every other `runs:*` read and move, and no model is called anywhere in the path.

### Autonomy, the scheduler and restarts

- **Autonomous** agent: its stage starts when the run reaches it and its result goes on without waiting. An agent that **waits**: its stage stays in `to-start` until the person starts it (`runs:startStage`), and its result stays in `to-accept` until the person accepts it (`runs:accept`) or sends it back with a note (`runs:return`). Changing the switch (`runs:setAutonomous`) applies from the next stage, never in the middle of one. Gates do not change.
- A run keeps the **copy of the flow** it started with and follows it after the cycle is edited (`runs:migrateFlow` moves it to the current flow when its stage still exists there and is the same kind). Before starting, the runner runs the flow check and refuses on an error. `wait` stages hold the run (`waiting`) until the event (`pr-merged`, `reporter-reply`, `label`, `time`; `linked-done`: the runner resolves it itself, see [Squads](#squads-1)): the same 5-minute tick looks at the host (`runs:skipWait` lets the person go on without waiting, with a reason; it only moves forward: to send the work back to an agent there is `runs:sendBack`). A stage with `trackerStatus` puts the label on the issue when it is entered and takes it off when it is left, under the agent's autonomy (a gate's or a wait's waits for a "yes").
- With `runner.enabled`, a job every 5 minutes lists the open issues assigned to the person that carry the `runner.triggerLabel` label and starts runs up to `runner.maxConcurrentRuns` runs **working** at the same time (a run parked at a gate does not count). An issue that ever had a run, in any state, is not started again by itself: otherwise a cancelled run would come back on every pass. An issue the app cannot start (no local checkout, no identity) is tried once per session. The same job looks, on the same pass, at what the waiting runs wait for (a merged pull request, a reply, a label, the time) and posts the reviews that waited for the pull request. The pass **never waits for a stage to end** (stages run on their own, and a slow one does not delay the other runs' waits), and a pass that is still going is not started again; if one of the three looks fails (the host is down), the others still happen and the failure is recorded.
- When the app opens, a run that was in the middle of an agent starts that stage over (a new attempt); those waiting for the person keep waiting. A stage is stopped (and the run is `failed`) by two limits: `runner.stageIdleMs`, the agent's **silence** (no sign from the model, neither text nor a tool nor a usage report, for that long; one that keeps working never reaches it, however long it takes), and `runner.stageMaxMs`, a generous **wall-clock** cap for the stage that never finishes though it keeps talking. The message says which one it was. The run is `failed`, with retry (`runs:retry`) or cancel (`runs:cancel`). Cancelling stops the agent and deletes nothing: the worktree, the branch and the thread stay until the person removes them.
- **Plugin request** (`wait.kind: 'plugin'`). A plugin that needs the network or its write without a permission opens a request in Actions; while a request of the run waits, the run does not start its next stage and is `waiting` with `plugin` and `detail` (what it asks for) in its `wait`. Answering (once, this session, always or refuse, in Actions, on the computer) lets it go when none of its requests is left; a refusal goes to the conversation and the run goes on. `runs:skipWait` also goes on without answering (the request stays in Actions). See [`plugins/`](plugins/README.md).
- **Exhausted key budget** (`wait.kind: 'budget'`). When the provider refuses the call because the key's budget ran out (HTTP 402; a 403 whose body speaks of limit, quota, credit or balance; a 429 that does not clear), the stage does **not** fail: it waits, with the reason in plain words naming the provider, and the run is `waiting` with `provider` and `detail` in its `wait`. Retry is not offered (the action is "go on without waiting for the provider", `runs:skipWait`, or sending the work back). The text the provider returned — masked like the rest of the outside text — also goes into the generic failure when a call ends with no structured output, instead of only the SDK's subtype. While a provider has no budget, nothing new starts on it: the next stage of a run that was waiting, a new run (`scan`) and a mention (`@agent`) are held, and the thread says why. The 5-minute sweep makes **one** probe call per provider (never one per run); when it goes through, every run that was waiting on that provider goes on from where it stopped (`waitDone`).

### Sending back to a stage

- `runs:sendBack(id, stage, note)` is the person's decision to send the work back to an agent: from a **wait**, a **gate**, a stage to start or to accept, a failure, a question (but not the squad's) and **from the end** (the run is reopened: it is `working` again, and the history records `reopened` and `sent-back` with who and why). A cancelled run cannot be sent back, nor one an agent is working on. Reopening a finished run is refused while another run of the same issue is going.
- The target is any earlier **work** stage of the run's flow that has an agent. With no stage, the default applies: the current stage's `returnsTo`, unless it only verifies (review or QA: sending the work there would redo nothing); then the nearest earlier stage whose agent changes the worktree (the implementation).
- The note becomes a **handoff from the person** to that stage's agent, with what the review and QA left open since the stage last started: the findings of the latest review round (blocking ones and suggestions) and the QA scenarios that did not pass or could not be checked, with the commands that did not run. With no note, what is open is the instruction; with neither, the send back is refused. With a note, the note comes first and what is open follows, marked as context for the request rather than new work, so a note that narrows the work ("only redo the evidence") is not undone by the list.
- **Every stage that runs again knows why.** Sent back by the person, returned by the review or QA, retried after a failure or started over after the app restarted (read from the run's history), the prompt opens with the reason, the request of this attempt said once (left out of the thread window, with no handoff section at the end), the stage's documents already in the cycle folder, the evidence it already kept and its last report. The agent is told to do what was asked and only that, to leave out of `artifacts` a document it does not change (the app keeps the one in the folder) and to give back an empty `memory` to keep the memory; QA repeats the scenarios it does not check again as the test plan records them. A stage resumed by an answer keeps the answer section instead of this block.
- The stage starts again at once, as a **new attempt**, even if its agent waits for the person. It does **not spend** the review's or QA's rounds (it is the person's decision, not a finding). The later stages run again in order: the review sees round N+1 with the earlier ones, as always. The stage that is left stays as it ended (a wait becomes `skipped`; what waited for the person becomes `rejected`).
- What goes to the tracker: the comment of each stage that runs again is **edited in place**, as always. The comment of the final stage, if already posted, is not posted again unless that stage runs again (then it is edited; if it was undone, it is posted anew).
- On the screen (`Send back to a stage`): the stage picker with the default marked, the box for what to ask and one click. The action of a waiting run is called **`Go on without waiting for the merge`** (or `… the reply`, `… the label`, `… the linked issue`, `… out the time`) and says where it goes (`Goes forward, to the stage …`): it only moves forward. If the reason typed in it names an agent with `@` or reads as a request to send back (`volte`, `devolva`, `refaça`, `go back`, `send back`, `return`…), the screen does not go on: it offers to send back (with `Go on anyway` at hand). A person's message in the run's thread that names an agent still calls the agent to read only; with the run waiting or finished, the box says that this does not send the work back and leads to the send back action.

### Questions and mentions

An agent's question pauses the stage, notifies through the app's notifications and is answered by `runs:answer` or by a person's message in the run's thread (the message becomes the answer, and the stage starts again with the question and the answer in the prompt). A message that names an agent (`@developer ...`) is not an answer: it calls that agent, which answers in the thread **without ever writing to the run**, whatever its own permission (the call has no Edit and no Write). An agent with commands (`shell: sandbox` or `host`) gets its session over a **throwaway copy** of the code, to reproduce what it was asked about (on `host` every command waits for your yes, as in a stage); where no sandbox can be made, it answers without commands and the thread says why. An agent that reads the code host (`tracker: read`) may **propose an issue** with its answer (title, body and labels): it becomes a proposal in Actions that always waits for your yes (never created by itself, even for an autonomous agent), and the thread gets the link once the issue exists. Only a person's message calls anyone.

**An agent calls another in a conversation.** An agent answering in a conversation — its direct conversation, a squad channel, the general conversation or a run's thread — has the `CallAgent` tool: it asks another agent of the team about a point (the product owner the tech lead or support, the developer the tech lead, QA the developer). The question enters the same conversation naming the other, the other answers there **reading only**, as a mention does, and the answer comes back to the caller, who finishes its own. The called agent may call a third one too. A call back to an agent already in the exchange is refused, and one answer makes at most `runner.conversations.perStage` calls. The caller's clocks stop while the other answers. A ceremony does not offer the tool.

**Agents talk before they ask the person.** An agent's question goes first to the agent it turns to (`turnsTo`), in the run's thread; that agent is called **reading only** and answers in a structured way (`answer`, `pass` with a reason, or `needs-person`). `answer` makes the asker's stage go on with the answer, without the person; `pass` takes the question to the one it turns to itself (the person, when to no one); `needs-person` and a decision marked `needsPerson` go straight to the person. Every step is a message in the thread (the question from one to the other, the reason, the answer), the run is in `question` while the chain walks, the person is told (and the question goes to the issue, under the asker's autonomy) only when it reaches them, a limit of 4 hops sends the question up to the person anyway, and an answer from the person at any point ends the chain. An agent that fails, or that left the team, also sends the question up. No agent decides a gate.

**Turn limit of these calls.** An agent called with `@`, an agent answering a question of the chain and an agent answering a request between squads only read, and use the same step limit as a stage that only reads (`runner.turns.read`, in Settings › Runner), read at each call. If the agent spends every step without answering, the app resumes the same session **once**, with **no tool at all** and 2 steps, asking it to answer with what it has already read; the answer is used like any other and the thread says the agent ran out of steps and that it may be incomplete. If that second attempt also fails, or there is no session to resume, the usual failure message stands, with the reason. A stage does not get this second chance: running out of steps there is still a failure, so nobody takes a stage for done from a half answer.

### An agent that writes

An agent with the `worktree` permission runs with the run's worktree as its working directory, on both engines, with **one guard function** (`src/main/engine/guard.ts`) in front of every write: on the Claude Agent SDK it is a `PreToolUse` hook on `Edit`/`Write`; on the open engine it is the `Write` and `Edit` tools (which call the same function again, inside). The rules:

- Only paths inside the worktree. Refused: an absolute path outside it, `..` anywhere in the path, `~`, a symbolic link on the way that leads out (also for a folder, and a new file under it), a link that leads nowhere, the root itself.
- Nothing inside `.git` (any depth, any case, nor through a link to it), nor `.husky`, `.githooks`, `.gitattributes`, `.gitmodules`. Secret files (`secretPath`) neither.
- Reading (`Read`, `Grep`, `Glob`) only inside the worktree and outside `.git` and secrets.
- Shell only for the commands of `runner.commands`, **exactly as written**, when the agent is set to `shell: allowlist` (with `none` there is no shell; with `sandbox` the commands go to the sandbox, below) (the ceremonies' `shellAllowlist` machinery with a list of its own); without the list, only `Read`/`Grep`/`Glob`/`Edit`/`Write`. On the open engine the command runs without a shell and with an environment that has no credential-looking variables; on the Claude Agent SDK, whose process needs the provider's key, each allowed command is rewritten to start with `env -u NAME` for every credential-looking variable (the command is matched character for character before it is rewritten).
- No network (`WebFetch`, `WebSearch`), no `git push`, no MCP; of the code host, only the `VcsRead` tool, and only with `tracker: read`.
- Every refusal goes to the run's thread as an app message (who, which tool, what, why) and shows as "blocked" in the live activity.

After a stage, the **app** commits in the worktree (`git add -A`, without the linked dependency folders, and `git commit`) as the identity in `runner.identity` or, when empty, the one in the repository's own `.git/config` (read, never written), passed on the command line with `-c user.name=… -c user.email=…`; the global git identity and the `GIT_AUTHOR_*`/`GIT_COMMITTER_*` variables never get in, and without an identity a run does not start (nor does a stage commit), with `-c core.hooksPath=/dev/null` (a hook the agent touched does not run), no signing and no file-system monitor, and the message from `runner.commitMessage` (default `feat: <summary> #<n>`, with `{iid}` required). The message never carries a tool's attribution. The documents of stages that only read are committed by the app too. The review reads the diff with `--no-ext-diff --no-textconv`, without the cycle folder.

### What an agent may read and run

Two settings per agent, chosen in **Settings › Team**, with defaults per role (the Product Owner and the Tech Lead read the code host; QA, the developer and the Tech Lead run commands in a sandbox). Full rules, the threat model and what is only promised: [`docs/cycles/30-agent-permissions/feat/1_SPEC.md`](cycles/30-agent-permissions/feat/1_SPEC.md); the fields are in [`configuration.md`](configuration.md).

- **Code host read (`tracker`).** `read` lets the agent read issues, comments, labels, the milestone, the pull requests linked to an issue and their diff, review threads and checks. Never a write: what goes to the host is still only what this page's [door](#what-goes-to-the-code-host) lets out. Every agent of a run reads the host through the app's `VcsRead` tool only (never the host CLI or the tracker MCP, which stay for the ceremonies), and only the workspace's projects: its issue project and its repositories; a workspace that names no project gives no read at all. Linked issues (issue to issue) are not covered: the provider interface has no such read.
- **Commands (`shell`).** `none`: no command. `allowlist`: the commands of `runner.commands`, as before (only for an agent that writes). `sandbox`: any command, inside a sandbox the app builds for the stage and ends with it, through a `Shell` tool (the engine's own Bash is off for that agent). `host`: any command, **on this computer, as you and outside any sandbox**, through the same `Shell` tool, for what a sandbox cannot reach (a `docker compose`, an emulator, a window, the network).
- **Commands on the computer (`host`).** Every command **waits for you to allow it** before it starts: the run shows the whole command, tells you (when notifications are on) and you answer "Allow once", "Allow until the stage ends" or "Do not allow", with an optional note the agent reads. **The one exception is "Host commands without asking"**, the autonomy block's choice: with **Autonomous cycle** on and that choice on, an agent set to `shell: host` runs every command of its stage without the question, and the run's thread keeps one line saying the command ran on this computer under the cycle's autonomy, so the person always has the mark that an agent had the machine's own shell without being asked. While a command waits, the stage's clocks stand still. The command runs in the run's folder (an agent that only reads runs in a throwaway copy), with your login PATH and the app's environment without what looks like a credential; the files of your home folder, the network and Docker are within reach, which is why every command asks you. Only the sandbox's time limits apply; a process left in the background stays until the stage ends. The thread and the audit log say the command ran on this computer (`via: host`). Only the computer sets `host`: a paired browser cannot raise an agent to it, a cycle template never brings it (the agent gets a sandbox, or less), and allowing a command from a phone takes the same external-effects switch as approving a proposal — the autonomy block does not reach a command asked outside a run. The request lives as long as the stage: if the app closes, the stage starts over and asks again. In a conversation outside a run (a channel, a general conversation, an agent's direct one), the agent called with `@` runs over a throwaway copy of what git knows of the repository (the tracked files and the new ones that are not ignored, as they are in the folder; nothing built or installed, such as `dist` or `node_modules`, with the clone's dependencies lent read-only as in a worktree, and the `copyMb` limit) and the request is the ceremonies' command notice, on every screen and on the paired browser: "Allow once", "Always allow" the suggested rule (which goes into the agent's list in Settings › Team) or "Do not allow", with the note; a command that list already allows runs without asking, and a request with no answer in 15 minutes is refused.
- **The sandbox** (Linux with bubblewrap; Docker is not used, and macOS and Windows offer only `none` and `allowlist`, because no equivalent is available to an app there). Built for **each stage**, it holds: the worktree read-write (an agent that only reads gets a throwaway copy instead, so nothing it does reaches the branch); `/usr` and `/etc` read-only and nothing else of the system: **no home folder, no `/run`, no `/var`**, so no key, token, agent socket or container socket; `.git` read-only (the pointer file over itself, the repository's directory read-only with its `config` replaced by a copy that has only harmless keys and its `hooks` folder empty); an environment built from nothing (no variable of the app passes); **no network**, with two switches that open it: `registry`, only HTTPS to the listed hosts through the app's proxy, and **`open`**, where the sandbox shares the computer's whole network — its own services, the local network and the internet — with no proxy and no host list (a choice of risk, on the computer only, off by default; with it, the system's resolver target is mounted read-only so that names resolve inside). Limits per command (time, data memory, file size) and per stage (processes, total command time). A process a command starts (a dev server) stays for the next command and is killed when the stage ends; the sandbox ends **before** the app commits what the stage changed. A command that runs past its limit is stopped and said so. It never pushes or writes to the host: it has no credential and no route.
- **Testing an interface in the sandbox (#68).** Two settings, on the computer only (Settings › Runner › Sandbox), off by default. The **browsers folder** (`runner.sandbox.browsersPath`, usually `~/.cache/ms-playwright`) goes through the same guards as the read-only folders and reaches every sandbox, read-only at its own path, with `PLAYWRIGHT_BROWSERS_PATH` pointing at it; it is the exception to "no home folder", and it is not put on `PATH`. The **virtual display** (`runner.sandbox.display`) makes the sandbox of the QA stage (only that one; never a mention) start an Xvfb **inside** the sandbox (1280×800, no TCP, under the per-process limits of a command, its socket in the sandbox's own `/tmp`) and set `DISPLAY`; the program comes from the sandbox's `PATH` (`/usr/bin` or the `bin` of a read-only folder), and the computer's own screen is never used. With either on, the stage's prompt says how to test (dev server on `127.0.0.1`, Playwright from the repository's dependencies, `--no-sandbox`, screenshots in `/coxia/out`, never in the working folder) and the stage gets the **`ViewImage`** tool, which shows the model an image saved in `/coxia/out` and nowhere else (no link followed, no pipe waited on, up to 4 MB, type checked by content). A folder that is gone, an Xvfb that is missing or did not start never stop the stage: the thread says what is missing, the prompt tells the agent to mark the scenarios that depend on it not-run, and the status in Settings shows browsers and display on lines of their own, never making the sandbox unavailable. **The same holds for an agent set to `shell: host`.** Its commands see the browsers folder through `PLAYWRIGHT_BROWSERS_PATH` (no mount: the folder is the computer's own), and a QA stage gets a display of its own: the app starts an Xvfb (1280×800, no TCP, on a free display number it picks) before the stage and ends it with the stage; `DISPLAY` points at it, `WAYLAND_DISPLAY` is removed, and with the display on but not available `DISPLAY` is removed too, so a window app never opens on the person's screen. The program is looked for in the `bin` of the read-only folders, on the login `PATH` and in `/usr/bin`. Screenshots go to a folder the app makes for the stage (`COXIA_OUT`, named in the prompt), the only place `ViewImage` reads from. The prompt of these stages is the computer's own: no sandbox boundary, a free port for the dev server, an empty data folder for the app under test, and `--no-sandbox` only if the browser refuses to start. Starting the display is the app's doing, not a command of the agent, so it does not wait for the person; every command of the agent still does.
- **The live screen (#157).** A QA stage with the virtual display on (in the sandbox or for an agent set to `shell: host`) shows a **Live screen** button on its card, in the app and in a paired browser; it appears and goes away at once, because the app says when a screen opens or ends (`SCREEN_EVENT`, no pixels). The viewer asks for the latest frame (`runs:screen(id, since, width)`, a read open to a paired browser) about twice a second while it is open, and stops when it is closed, hidden or the stage ends; the app reads the screen only when someone asks (at most one read per 400 ms however many viewers there are), and a frame the viewer already holds comes back with no image. The frame comes over the app's own X11 connection to the display (`GetImage`; the app is the X client: no new program, no `-fbdir`, and no network opened in the sandbox, which only gets a folder of the `stageDir` bound over `/tmp/.X11-unix`); the connection is made **before the agent's first command** and never dialled again, so the agent cannot swap the socket for another one. The computer gets 1280×800 as JPEG quality 75 and the phone 640 wide at quality 60, as `data:` (the desktop's policy has no `blob:` for images). **Take control** is the desktop window's alone (the `screen:*` channels are refused to a browser by a pattern in `webPolicy.ts`): clicks, the wheel and keys become XTEST events; the viewer says control is on and recorded, and Ctrl+Alt+Shift+Esc gives it back (it is never sent). The phone sees a "controlled from the computer" mark. What the person does is **not a command of the agent**: it does not wait behind the agent's commands, spends none of the stage's budget and is not in the command log; the conversation gets a line when control is taken and given back and one per burst of use ("the person used the screen from … to …"), and the recording marks the same interval. The app **records** the screen from the first time it is used, that is, when a window appears on it (not when the display opens), and only while a window is mapped: it asks the X server for the root's children (`QueryTree` and `GetWindowAttributes`, the reply read with its size bounded) and, with the screen bare, reads and records nothing. It is a WebM video (VP8, encoded by a hidden window with WebCodecs and a muxer of the app's own), about one frame a second and only when the picture changes. A gap of more than 3 seconds between two frames plays as a pause of about 1 second, and the recording keeps each cut (`cuts`: the point of the video at which the pause ends and the stage's time that was left out; at most 500): `durationMs` is the **video's** time, `realMs` the stage's, `startedAfterMs` the time from the screen opening to the first frame, and the marks of the person's use are in the video's time, on the player's strip; the player shows a tick at each cut, the stage's time next to the length and the stage's time at the point being played. A stage whose agent never opened a window keeps no recording and says so **once** in the conversation ("no window was opened on the screen"), and it is not an error. The video is capped at 24 MiB and 60 minutes of video (the cap stops the recording and says so) and kept as **one** piece of evidence of the stage, made by the app, **also when the stage fails or is cancelled**, before the stage's folder is removed. The agent cannot cite it, delete it or save it (`SaveEvidence` still refuses video), and it goes neither to the code host nor to the cycle folder. The evidence block plays the video with the marks of the person's intervals, which seek the video; the conversation carries the attachment. A run that holds a recording is written as format 2, and as format 3 when the recording holds cuts or `startedAfterMs` (the new recordings): an older app refuses it as written by a newer app (0.9.0-beta.4 and beta.5 read a 2 but not a 3). **Retention** gets the group "Screen recordings of the stages", swept with the workspace's days (off by default); only the file goes, and the record stays marked as removed by retention. With the display on the QA prompt tells the agent to run the browser **headed** (`headless: false`), because a headless browser draws on no screen. Linux only; the person's own screen is never shown.
- **Handing the screen to the person (#178).** An agent with a live screen (the working stage, or the agent in a conversation; never a documentation run) is given the tool `screen_handoff(what, why?)` for a login, a code that reached the phone, or a field the person should type and the model should not see; the prompt tells it to use it and never to ask for or accept a secret in the conversation or in a tool's text. **The wait:** the call waits inside the tool (a question would end the stage attempt and, with it, the display), the clocks of the stage or of the answer stand still, and the app shows **a card** where the agent works (at the top of the run and in the conversation) and notifies the phone, with fixed catalog text (never the `what`), that the agent waits for the person **on the computer**. If nobody takes the screen in 15 minutes the result is `expired`. **The four results** are fixed sentences and nothing else (`done`, `declined`, `expired`, `unavailable`: a second request while one is open, or after a decline or an expiry in the same attempt or answer, is `unavailable` too). **The person** takes the screen on the computer after a warning composed from what the agent has (the app's browser, a shell in the sandbox or on the computer, or none) that says the interval **is recorded** and kept with the evidence; after the click, control is on with no switch, the pictures come over `screen:handoffFrame`, and *Give back* (`screen:handoffGive`) gives the screen back; with no input for 30 minutes the interval ends as `expired`. Declining (`runs:handoffDecline`) is open to a paired browser and needs no external-effects switch, since it gives the agent nothing; taking and giving back are the desktop's alone. **The interval:** from the click to its end, no picture of the screen goes to a web reader (`runs:screen` answers `held`, and the cache is dropped at both ends, before control is on); the recording keeps being fed and the interval is **one** mark of kind `handoff` (`RecordingMeta.handoff`), so a run that holds such a recording is written as **format 4** (formats 2 and 3 are as before; an app that reads up to 3 refuses it as written by a newer app; format 5 is a run in which a stage's record holds the procedures it used, #179, and stands on its own whatever the recording holds); the recording plays in a paired browser like any other. Closing the viewer or the exit chord turns control off and does **not** end the interval. **What the agent cannot do:** during the interval every call to the app's browser, its confirmation and a new request are refused with a fixed sentence, and so is a shell command (in the sandbox or on the computer, with no approval asked); after the give-back what the person typed (rebuilt from the keys, in memory only, never on disk, in the conversation, in the audit, in the step log or in the result) shows as `[secret]` in every read of the app's browser, in its plain, URL-encoded and JSON-escaped forms (4 characters or more), and the output of commands goes through the same masker; a picture of a page that shows the value is refused. **What the app cannot do:** programs the agent had already started in its shell keep running and could capture the screen or read the page (the warning says so); the guarantee there is best effort. The conversation gets fixed lines (asked, taken, given back, declined, expired and **one** line for the interval), the audit a `screen-handoff` entry (agent, `what`, outcome, interval, `sandbox` or `host`) and the step log one contentless step. None of this has a setting: the limits (15 and 30 minutes) are constants.
- **What is shown.** Every command, its exit code and the end of its output go to the run's thread (one message each), to the live activity (the call and how it ended) and to **Settings › Audit log** (kind "Sandbox command", with the agent that ran it). The commands the app runs before QA run **inside** the QA agent's sandbox when it has one.
- **The clone's dependencies.** The `node_modules` and `.venv` links the runner makes in the worktree would dangle in the sandbox: the folders they point to are shared **read-only** at the same path when their real path is inside the run's clone; a link that points anywhere else is left dangling and the thread says the agent must install its own dependencies. A tool that writes a cache into `node_modules/.cache` fails in there.
- **Where there is none.** A computer that cannot make a sandbox says why (bubblewrap missing, user namespaces refused by the system, `prlimit` or `timeout` missing), the editor does not offer it, templates bring `allowlist` or `none` instead, and a run whose team has an agent set to `sandbox` is refused at the start, or its stage fails, with the message. **Nothing falls back to running the commands outside.**
- **QA's evidence.** A QA agent with a sandbox marks each scenario `executed` (and cites the numbers of the commands behind it, the app's own first) or `read`. The app checks the claim: `executed` stands only if it cites a command of the stage, and a pass needs one that ended with exit code 0; otherwise it is recorded as `read` and **labelled** "claimed as executed, nothing backs it". The QA comment says how many scenarios were executed. Any other QA agent has every scenario recorded as `read`. It shows that a command ran, not that the behaviour is right: a script can print what it likes.
- **Who may change it.** Only the computer raises `shell` or `tracker` or touches `runner.sandbox`; a paired browser can lower them, `shell` only to `none`. The migration to schema 10 raised nothing for an existing workspace: an agent that writes kept its commands, a reader kept the host read it had, nobody got a sandbox; the recommended permissions are **offered** in the team editor.

### What goes to the code host

**One comment per stage, edited in place.** Each work stage (and each gate decided, and each agent's question) leaves its result on the tracker, from the template in `devCycle.comments`: the app composes the comment (the status on the first line, the template's sections in order, the technical detail last and collapsed, a hidden marker at the end with the run's and the stage's id) and **checks the finished text**. What can be fixed is fixed silently: secrets masked, a path in the worktree becomes a path in the repository, any other absolute path keeps only its last name, the run's id leaves the text, a mention (`@someone`) becomes text so it notifies nobody. What cannot is **reported**: the name of an agent, a tool or the forum, first person outside a quote, a status that is not the first line, a `<details>` that is open or not the last block. Reported text **does not go out by itself**, even from an autonomous agent: it becomes a proposal in Actions with the problems on top.

Before posting, the app looks for the stage's comment: the note the run remembers (`Run.comments[stage].noteId`), else the one that carries the marker, else it creates one. After posting it reads the comment back and compares; if the host changed the text (tables and collapsed sections are what breaks) the thread says so. When an edit changes what the comment says (the status on the first line: QA that failed and passed), a short comment with a link announces it; a gate decided several times leaves one comment per decision (with the reason and the link to the comment of the stage it judged); each agent question is a comment. A stage with no template in the cycle posts nothing, and changing the template changes the next comment.

**Who decides whether it goes out by itself.** The agent's `autonomous` value when the stage ended (what the stage record keeps; changing the switch in the middle of a stage does not apply to it): an **autonomous** agent: the comment goes out through the door of Actions (`runner/door.ts`), with one line in `auditoria.jsonl` per call (`by` the agent, the target, the body's hash and the host's answer); an agent that **waits**: the comment becomes a proposal in Actions, with the text in view, and the "yes" posts (or edits) it and the run learns the note's id. A gate's decision follows the agent whose work it judged. **A test workspace** refuses everything (the comment stays `refused`, the thread says so, nothing is read or written on the host); the push and pull request proposals still exist and confirming them is refused.

**Review on the pull request.** The review stage does not comment on the issue: the round becomes **one review** on the pull request, `request_changes` when a finding blocks and `comment` when none does (the app never approves; on a pull request that is the person's own the hosts do not take a request for changes, so the review goes as a comment and the first line of the general text says the rest). The pull request is the one the run recorded, or an open one from its branch that the app finds through the issue (the person may have opened it by hand). Each finding is placed on the pull request's **current** diff: where it says, if the lines are in the diff, on the right side; otherwise on the file, saying which line it was (never on a wrong line); if the file left the diff, in the general text. Each comment says whether it blocks or is a suggestion. The review's **general text** does not repeat the findings that are already on their lines: it carries what the agent wrote that is about no finding (the app drops paragraphs and list items that say what a finding says, or that cite its place), the findings of files that left the diff and **one line** with how many comments the review left on the code; the sections of the review template are "Beyond the lines of the code" and "What was not reviewed". The replacement a finding proposes becomes the host's **suggestion block** (GitHub `suggestion`; GitLab `suggestion:-N+0`, N computed from the range) only when the comment stands exactly where the finding says and on the new side; anywhere else, and on Bitbucket, it is described in a code block. The mapping per provider is in [`vcs-providers.md`](vcs-providers.md).

The **next round** reads the threads the run opened (each comment's marker says the round and the finding): a finding that is still there (the same words, the same file; the line does not count) gets a reply in its own thread; one that was fixed, a one-line reply and its thread resolved (where the host resolves threads); only the new finding opens a thread. The whole round (replies, resolutions and the review) is **one action**: one proposal in Actions with one "yes", or a set of audited calls under the same name. If the pull request does not exist yet, the review waits as a draft and goes out once it does (the latest round that waited: the earlier ones were answered by the work that followed).

**The push and the pull request always wait.** At the end of the last stage before the review whose agent changes the worktree (the implementation), the app writes the pull request's description (the `pr` template: the status, the sections, `Closes #n`, the technical detail) and **proposes the push** of the branch (`run-push`): the action holds the run's id, not a folder; on confirmation the app reads the run's worktree and branch, refuses if the worktree is on another branch or holds something that was not committed, and makes the plain `git push --no-verify origin HEAD:refs/heads/<branch>`, no force, audited. A newer push of the same run replaces one that still waited. **When the push is done**, the app proposes the **pull request** (`createMr`, title and body from the template, to the repository's default branch), which waits for its own "yes"; on confirmation the run records the pull request (`Run.comments.pr`: its number in `noteId`) and the review that waited goes out on it. Each later stage whose agent changes the worktree (a QA that writes tests, the implementation a review sent back to) proposes a new push, which only updates the pull request; a flow with no review pushes once, at its last writing stage. None of this skips the "yes", in any case, not even in a test workspace (the proposal exists; confirming it is refused).

**The evidence of a stage.** An agent with a sandbox keeps what it captured while it worked as **evidence** of the stage: a `SaveEvidence` tool reads a file the stage itself made in its output folder (never a path elsewhere, never a path through a link; the kind is read from the **bytes**, never from the name), refuses anything over 8 MiB and keeps it under a short, stable id in the run, `ev-<digits>` (for example `ev-3`), which is what a QA scenario and a stage output cite. The evidence is published **at once** in the run's conversation, as an attachment of an agent's message, and is listed under the stage that kept it; the person opens, downloads and deletes it (an agent keeps, never deletes). It is removed with the run. A second tool, `AnnotateImage`, draws marks (rectangle, arrow, ellipse, label, numbered marker and the **blur box**, which hides what should not be seen) on an image and keeps the result as a **new** piece of evidence, linked to the one it came from, with the original kept; the drawing is done by the main process, from data, and no program of the agent runs to draw. `ViewImage` (the same tool that shows a capture from `/coxia/out`, always just one) also takes the id of a piece of evidence, and lets the agent look at the image it produced and mark it again. What is accepted: images (PNG, JPEG, GIF, WebP), `text/plain` and PDF; video, audio, an archive, an executable and any content that does not confirm what it says is refused (the one exception is the screen recording the app itself makes, described under "The live screen": it does not go through this tool). **Where the evidence lives** is a workspace choice, in Settings › Runner: **app data only** (the default: with the run, in the workspace's data, and never in a commit) or **also in the cycle folder** (a copy goes to `docs/cycles/<n>-<slug>/evidence/` and is taken by the stage's commit). Only the computer changes the choice. **Taking it to the host:** when a stage comment or the pull request's description cites a piece of evidence, the image is sent to the host and embedded in the text, through the same door as the other writes (an autonomous agent publishes by itself and is audited; anyone else waits for the "yes" in Actions, with the images in view; a test workspace refuses; when the autonomy block opens the pull request by itself, the images its description cites go up first, by themselves and audited, and the description embeds their addresses). The image is part of the **same write** that cites it: it goes up together with the comment, in the group of commands one "yes" releases, and never before it — a comment that waits in Actions puts no image on the host until the person confirms. Each provider sends in its own way (GitHub through the host's own file hosting, GitLab through the project's file upload, Bitbucket through the repository's file upload); where embedding is not possible, the comment says how many pieces of evidence there are and that they are in the app, instead of dropping them or breaking. No real host was used in this project: what each one accepts is what the documentation says.

### Squads

With squads configured ([`configuration.md`](configuration.md), [`cycles.md`](cycles.md)) the runner picks a run's squad, gives it the squad's flow and agents, and handles the requests between them. With none, none of this exists and a run is as it always was (`test/runner-golden.test.ts` pins that).

**Starting.** `runs:start(ref, repo?)` (and the scheduler) read the issue, drop the squads that have no members and route by scope: the run's repository, then the issue's labels, then the folders of the files its text mentions (title, description and human comments); each rule only narrows what is left, and a rule that says nothing about the issue does not narrow. One squad: the run starts in it (`Run.squad`, `Run.routedBy`: `repo`, `label`, `path` or `unclaimed`), with the copy of its flow and only the members and the shared agents as agents (`flowOf` over `squadView`); the thread says why. With no repository (the scheduler does not choose one when the project has several), the labels and the folders speak, and the repository is the only one the chosen squad has in the project. A repository the call names is the one used. Before starting, the runner checks the squads (`checkSquads`) and refuses on an error. The squad's label goes onto the issue through `Publisher.squadRouted`, under the liaison's autonomy (a proposal when it waits).

**Triage.** Several squads (or none) claim the issue: the run starts at the first stage of the **workspace's** flow, with `Run.routing` (the candidates, why, the proposal and what the front door produced). Only at that stage does the answer schema have `squad` (an id of the candidates, or null) and `squadReason`, and the prompt lists the candidates. When the stage ends: an **autonomous** agent and a proposed candidate decide (`routeSquad`); otherwise the run stays in a `squad` kind of `question` (`askSquad`), with the proposal in the thread, waiting for `runs:setSquad(id, squad | null)`. A person's words do not answer this question (`runs:answer` refuses, and a message in the thread is only a message). Once the squad is decided the run goes on at the stage after the front door in the squad's flow (its first, when it lacks the front door), with what the front door produced and the handoff it left; with no agent at the first stage the person chooses first and that stage is skipped. `runs:setSquad` serves only a run that waits for the choice.

**Autonomy.** The value of an agent that a stage reads is its own switch **and** the squad's (`effectiveTeam`); the stage captures it when reached, as always. `runs:setSquadAutonomous(squad, on)` changes the squad's switch; it applies from the next stage.

**The autonomy block.** Settings › Runner holds one block of five fields for a run, every one off by default: **Autonomous cycle** and, under it, **Host commands without asking**, **Gates pass by themselves**, **Push without a yes** and **Open the change request without a yes**. The four below only mean anything while **Autonomous cycle** is on. The workspace's block has a sixth, **Board writes go to the host without a yes** (`runner.autonomy.board`, under its own heading): it is the board's choice, not a step of a run, so it is independent of **Autonomous cycle**, it is absent from a flow's block, and neither the run's header nor its note ever lists it (`autonomyOf` and `onChoices` leave it out; `boardAutonomous` reads it). Like the rest of the workspace's block, a paired browser cannot change it either way. The block exists twice: the workspace's (`runner.autonomy`) and each flow's (`devCycle.autonomy`, by the flow's key: the main flow, each squad's, the release flow). A flow's block starts with **Use the workspace's setting** on: while it is on, the workspace's block decides for that flow and the flow's fields are shown off with a hint; off, the flow's own block decides and the workspace's has no effect on its runs. The block is read from the config (`autonomyOf`, `choiceOn`) at every step of a run — the stage start, the command, the gate, the push and the pull request — so a change applies from the next decision and never in the middle of one; the stage captures its own value in `StageRecord.autonomous` when the flow is resolved (`cycleAutonomous || autonomous`).

What each choice does: **Autonomous cycle** makes every stage start and hand its result on without waiting, whatever the agent's own switch says, and the comments go out as an autonomous agent's do. **Host commands without asking** runs the commands of an agent set to `shell: host` without the question, and the thread records one line saying the command ran on this computer under the cycle's autonomy. **Gates pass by themselves** approves a gate by itself (`gateBy(..., 'app')`) and records the automatic approval with the reason and where the decision came from (the workspace's block or the flow's). **Push without a yes** pushes the branch through the door of Actions when the stage that changes the code ends, audited, and the change request follows it. **Open the change request without a yes** opens it through the door, audited. With a choice off, that step waits as it always did. Only the computer turns any of these on (a paired browser may turn them off: `raisedAutonomy` refuses a field going from off to on); a test workspace keeps refusing the push and the change request. A release run is left out of the two last choices: its cuts and its pushes always wait for a "yes" (D18 of the release process).

**Requests between squads.** Whoever holds a question and is a squad's liaison, when another squad has a liaison, gets the verdict `request` in its schema (`{ squad, kind, text }`) and a line in the prompt about the other squads. A valid request becomes a `request` message in the `squads` channel (author the liaison, `to` the other squad's liaison, `params` with the squads, the kind, the run and the issue) and a line in the run's thread; the liaison that receives it is called **read only**, in the folder of a repository of its squad, and answers `answer`, `decline`, `issue` (with a title and a description) or `needs-person`; its answer is an `answer` message in the channel that closes the request (`replyTo`). `answer` and `decline` come back as the answer of the asker's liaison (`answerByAgent`), and the asker's stage goes on; `needs-person` passes the question to the person (the run's thread shows the reason); a request that cannot be made (an unknown squad, one with no liaison, its own) or a liaison that fails sends the question up to the person with the reason, and the request that stayed open is closed with an answer from the app. What the liaison says after the person already answered (or after a cancel) is not used.

**An issue and a linked run.** `issue` creates the issue on the tracker (`Publisher.requestIssue`: `createIssue` in the issue project, with the squad's label and a line of origin in the description), under the autonomy of the liaison that received the request (`autonomousOf`: its own and the squad's): autonomous, it goes out through the door and is audited; otherwise it is a proposal in Actions (`unit.purpose = 'request-issue'`), and the run that asked waits at once (`waiting`, `linked-done`, `wait.by` the agent that asked) with the link `proposed`. With the issue created (at once, or when the person approves in Actions: `Runner.actionDone`), a run of the other squad starts on it (`routedBy: 'request'`, in the repository its scope has), with the `origin` link to the one that asked, and the one that asked keeps `requested` with the run and the issue. If the new run cannot start, or the write is refused (a test workspace) or fails, the link is `refused` and the stage that waited goes on knowing that. A "no" in Actions to a proposal does not tell the runner: the link stays `proposed` and the person stops waiting with `runs:skipWait`.

**`linked-done`** is resolved by the runner (the publisher does not look at the host for it): the run that waits goes on when all its `requested` links have ended (the linked run reached `done`, or its issue was closed on the tracker, read through the issue source) or were refused. When the linked run reaches `done` the runner looks at the runs that depend on it at once; the 5-minute pass covers an issue closed by hand. A cancelled run does not resolve the wait, and a `linked-done` wait stage on a run that asked for nothing goes on at the next pass. The reply the stage goes on with (the list of what ended) is the app's, not the person's.

**Channels.** `ensureSquadChannels` opens, when there are squads, the `squads` channel and a `squad-<id>` for each squad (threads of kind `channel`); `forum:list(squad?)` lists everything or only what is under a squad (its channel and its runs' threads: a run's squad is read from the run when the list is made). The person writes in any channel as in any thread. Removing a squad (`runs:removeSquad(squad, confirm)`) lists its active runs without `confirm` and, with it, removes the squad, makes its members shared and takes the runs out of the squad (`leaveSquad`).

### A release

A release is a run whose **subject is a version**, not an issue (`Run.subject: { kind: 'release', version, from, tracking, activities }`; an issue run has no such field). It carries a synthesized `issue` (`release:X.Y.Z`, number 0), which keeps "one run at a time" working; its own worktree as ever, with the cycle folder (`0_ISSUE.md`, the record of the release, and `RELEASE_PLAN.md`); and the flow of the `release-flow` template, kept in `devCycle.flows.release` (a flow **per kind of run**, next to those of the squads: no squad may be called `release`). Applying the template **adds** that flow, its comments and the Release manager agent, and leaves the flow of the issues as it is. Decisions D5, D6 and D11 of [`1_SPEC.md`](cycles/27-release-process/feat/1_SPEC.md), approved by the maintainer on 2026-10-03.

`runs:startRelease(version, from?, repo?)` (in the desktop window and, with **"external effects" on**, in a paired browser: it is in `EXTERNAL_EFFECT` in `src/main/webPolicy.ts`, next to approving a proposal, because a release ends in the repository's own scripts and merged code run as you; with the switch off the phone gets the refusal in the field itself. The runs screen has the field when the workspace has the flow, in both places, and every push of the release still waits for your "yes" in Actions) checks the version (`X.Y.Z`, numbers without a leading zero; `from` is the stable tag `vA.B.C` a patch is cut from), refuses a second active run of the same version and a workspace with no release flow, makes the worktree, writes the record (whether the branch `release/X.Y.Z` exists, and the activities) and starts. The publisher then does, one thing at a time: makes or adopts the tracking issue, lists the activities on it and **opens the branch** (or proposes to) when it does not exist yet.

**The activities** are the pull requests aimed at `release/X.Y.Z`, open or merged (one closed without a merge is no activity), read through the provider (`listMrsByTarget`, on all three hosts; the approval and the checks of each open one, one by one, by `getMr`). Only in the record and in the comment come the open issues of the milestone that carries the version's number and that none of them carries. Decision: by target branch and by milestone only; there is no configurable version label. The run keeps the list (`subject.activities`), and it is read again every 5-minute sweep and after every step; each stage reads it in its prompt (`runner.section.release`). Each line shows the commit (`at abc123def`) the pull request was at in the last read. **Accepting the plan** (approving or skipping the first gate of the flow) **freezes** those commits (`subject.planned`) inside the gate's own transition: a call the gate refuses (no reason for a skip, an action that does not exist) freezes nothing. When the run goes back to the plan (the gate rejected, or a send-back to a stage before it) the freeze is undone, and the next acceptance of the plan freezes again what the run has read by then; later gates never freeze or undo. What is frozen is what the person **saw**: a snapshot (`subject.seen`) taken **once**, when the run enters the plan gate (and taken again right after the publisher reads the host at the end of the plan stage), which no later read rewrites (the 5-minute sweep rewrites `activities`, not `seen`); the gate copies `seen` into `planned`. A pull request pushed to during the gate's wait is not in `seen`, and its merge is refused. The gate panel on the run screen shows those commits (the short one of each pull request) and says what has moved; right after the acceptance the host is read again, and a pull request that moved since, or that was not in the plan, is said in the thread (it is not merged either way: `merge-pr` requires the frozen commit).

**The tracking issue** "Release X.Y.Z" is made when the run starts, or **adopted** when one is already open with the same title (case does not matter; a closed one will not do) **and** it is the person's own (its author is the user the app acts as) **or** it carries the label that names this version (`devCycle.releaseLabelPattern`, group 1 equal to the version). A pull request is never a candidate (the list of issues leaves them out). Somebody else's issue with the same title and no such label is not where a release reports: the app makes a new one and says in the thread why it did not take that one. Like every write to the host it goes through the door of Actions: by the Release manager (audited) when it runs by itself, or as a proposal (`purpose: release-tracking`) that waits for a "yes" and tells the run when it goes out. Each stage leaves its comment there, from the templates of `devCycle.comments` (`release-plan`, `release-assemble`, `release-beta`, `release-stable`, and the usual `gate` and `question`); while the issue does not exist the comment is a draft, and goes out when it does (or on the next sweep). Three comments are the app's own: one, edited in place, lists the activities (`activities`); when the host shows a beta published, another says which and where (`beta-published`, one per beta); when it shows the stable published, another says so (`stable-published`) and **the issue is closed**, by the agent's autonomy (a `release-close` proposal if it waits). The 5-minute sweep reads this, also in a run that has ended (for 30 days). The host says "published" through its releases API (`getRelease`: a release that is not a draft and has a publication date); Bitbucket has no releases, so none of this is seen there: the issue does not close by itself, and `beta-age` only goes on with `runs:skipWait`.

**The steps of the release** are an action kind of their own in the door of Actions, `release-git`, whose unit holds `{ op, version, runId?, pr?, head?, from?, branch?, channel? }` and never a path, a command or a flag (`src/shared/release.ts`, `parseReleaseUnit`: any other field is refused, not ignored; it is judged again when a person says "yes"). The repository comes from the run (`Run.repo`), the identity is `runner.identity` (without it the step is refused: the app never signs a release as anyone else), and what runs is the repository's **own** `scripts/release.sh` or plain `git`, **in a worktree of the run's own** (D14, decided by the maintainer on 2026-10-03): the person's checkout is **never touched** (not its branch, nor its tree, nor its `main`). The worktree (`<worktrees>/<repo>/release-X.Y.Z-steps`, next to the run's, derived from it and never from the unit) is made from the clone on the first step, **detached** (no branch), the clone's dependency folders are linked into it and kept out of `git status` by an exclude file in the worktree's own git directory. The steps on `release/X.Y.Z` check it out there; those that need `main` stay on a **detached HEAD** at what the remote has of `main` (or at local `main`'s commit when there is no remote): so no branch is ever checked out twice (a branch the person's checkout has is refused with its path, not taken):

| `op` | What it does |
|---|---|
| `open` | **refuses before running anything** when the branch `release/X.Y.Z` already exists (here or on the remote), and **puts the worktree on what stands for `main`** (a detached HEAD at `origin/main`) before it runs, so that only `main`'s script runs for `open`, never the one of a release branch in which a merged pull request may have changed `scripts/release.sh`. Runs `scripts/release.sh open X.Y.Z [--from vA.B.C] --author "Name <email>" --worktree` (makes `release/X.Y.Z`, cut from `origin/main`, and switches to it, in the worktree; `--worktree` is the script's option for a place where `main` is not a branch) |
| `merge-pr` | `head` is **required**, and a **full** commit name (40 or 64 hex digits; an abbreviation is refused, and the comparison is exact equality, never a prefix). Checks on the host that the pull request is open, from the same repository (a fork's is refused: "comes from a fork"), not a draft, aimed at `release/X.Y.Z`, **at the head the accepted plan froze** (`subject.planned`, fixed when the person accepts the first gate), that the head the host has now is the same, and that the commit read from the remote (`git fetch`, read only) is too; the only approval that counts is one **on that head** by an owner, member or collaborator of the repository (or, with `runner.release.soleMaintainer`, the person's yes: see **One person maintains the repository**, below the table), and a check the host cannot read counts as `running` (refused: the app never fails open); **no check at all** counts as `running` too when the pull request was updated less than 10 minutes ago (the checks of a push just made have not started, and a repository that requires them would be merged without), and only after that does it count as "none" (a time the host did not give, or one in the future because its clock is ahead, counts as "now": the doubt waits; the limits are that a CI queue that takes longer than 10 minutes to start still passes as "none", and a clock far behind ours would let a recent push through; the app does not ask whether the repository requires checks: that takes rights it does not have). Then runs `git merge --no-ff` into the release branch with the configured identity and the same `-c` list as the app's commit (no hooks, no signing, no `fsmonitor`); never the host's merge button |
| `beta` | **always waits for a "yes" (D18)**; switches to `release/X.Y.Z` and runs `scripts/release.sh beta --author ...` |
| `stable` | **always waits for a "yes" (D18)**; puts the worktree on a detached HEAD at `origin/main`, merges `release/X.Y.Z` into it (a fast-forward, or a merge with the identity) and runs `scripts/release.sh stable --author ... --worktree`; the stable tag is on that detached commit, and the person's `main` does not move |
| `push-branch` | `git push --no-verify origin <sha>:refs/heads/release/X.Y.Z`, with the sha **resolved first** (never the symbolic `HEAD`; for `main`, after the stable: the commit of the stable tag, peeled, on the detached HEAD, sent as `<sha>:refs/heads/main`, and **only when the tag is annotated** (the script's) and its commit is on top of what the remote has of `main`). Every push carries `-c push.followTags=false -c push.recurseSubmodules=no -c push.gpgSign=false -c remote.origin.mirror=false`: the person's git configuration adds no tags, submodules or refs to it |
| `push-tag` | `git push --no-verify origin refs/tags/vX.Y.Z[-beta.N]`, the latest beta or the stable, only an annotated tag and only once the remote has its branch |

**One person maintains the repository.** GitHub does not let the person who opened a pull request approve it, and `merge-pr` requires an approval on the host: in a repository one person maintains, none of their pull requests would get into a release, and the Release manager would keep asking for an approval nobody can give (branch protection does not require a review; the requirement is the app's). With `runner.release.soleMaintainer` on (Settings › Runner, "I am the only maintainer of the repository"; off by default, and a config without the field reads as off, with no migration step; **only the computer changes it**: a paired browser sees it and cannot change it, and `config:cycle-save` refuses the path), **the person's yes in Actions on a `merge-pr` stands for the approval**, and only when all three hold: (1) the yes is theirs, given in Actions (`approveAction`): a call the agent's autonomy would let out never carries it; (2) the pull request was opened **by the account the app uses on the host** (`currentUser`, read at the time; the name compares without case, and an author the host did not name is nobody's); (3) **nobody asked for changes** on it (a "request changes" review that is not over shows there is a reviewer; the person resolves or dismisses it on the host). A pull request **someone else** opened still needs the approval on the host, and the refusal says who opened it. Every other check of `merge-pr` stays as it is: open, from the same repository, not a draft, aimed at the release branch, the head the plan froze equal to the host's and to the one read from the remote, checks that pass. With the switch on, **every `merge-pr` waits for the yes**, even with an autonomous Release manager (`releaseWaits` in `src/shared/release.ts`; `runReleaseAuto` refuses it), a pull request approved on the host included: the switch says the review is the person's yes, and an agent does not give it. In the activities, an open pull request that is the person's, with no changes asked, not a draft and with its checks passing shows as **yours and merged on your yes in Actions** (`selfReview`) instead of "not approved yet", and that is what the Release manager reads to ask for the `merge-pr` without waiting for an approval. The limit: the app does not ask the host whether anyone else could review; the person says so by turning the switch on, and in a repository with other reviewers it stays off.

No step gets `--emergency` or `--allow-branch`, and what the script prints (the push commands) is never read: a push is a step of its own that builds its refs by itself, with no force. **The script is what decides** whether a version may be cut; the app does not copy its rules. Every step is **audited** (`kind: 'release'`, or `push`; the operation, the version, the run and the commit before and after) and **refused in a test workspace**. **Who decides whether it goes out by itself** (D6 and D18): `push-branch` and `push-tag` **and also `beta` and `stable`** **always** wait for the person's "yes" in Actions, even with an autonomous Release manager, and the app refuses all four through `runReleaseAuto` even if asked. The reason for `beta` and `stable` is that a cut runs the repository's **own** `scripts/release.sh` (and what it calls: `npm`, the tests, the build) over the code of the pull requests already merged, **unsandboxed, as the person**: an agent that decides by itself must not pick the moment to run that. `open` (which runs **`main`'s** script, never a release branch's; what stands for `main` is `origin/main`, and local `main` counts only in a repository **with no `origin`**: with an `origin` whose `main` cannot be read the step is refused), `merge-pr` (with the hardened gate above; with `runner.release.soleMaintainer` it too always waits for the yes) and the comments on the tracking issue follow the agent's autonomy: autonomous, they go out through the door, audited with the agent; otherwise a proposal in Actions. The steps of one release **do not run at the same time**: there is a queue per worktree folder (`release-X.Y.Z-steps`), on the "yes" path and on the agent's, and a `beta`, a `push-branch` and a `push-tag` approved together run one after the other. When the release's worktree folder was deleted and git still remembers it (it lists it as `prunable`), the app makes it again with `git worktree add --detach --force` **for that path only**: it never runs `git worktree prune`, which also forgets the registrations of other worktrees of the repository whose folders are gone (a drive that is not mounted); if that still fails, it says so with the path. This needs git **2.31 or newer** (earlier versions do not mark the worktree `prunable`, and git then refuses the path) and **never takes a locked worktree** (`git worktree lock`): in both cases the error says to run `git worktree prune` or `git worktree unlock <path>` in the clone. The script's time limit (`scriptTimeoutMs`) kills the whole **process group**, not only `bash`, and frees the worktree: the locks the script left (the worktree's index and `HEAD`, the release branch and the version's tags) are removed **only when they were made after the step began** (an older one belongs to another process, the person's git perhaps), and the tree goes back to **the commit the step began at** (`reset --hard` to it: a commit the killed script made on the way is dropped; a tag it made stays, and the next step sees it). Only the tag locks of the version itself (`vX.Y.Z.lock` and `vX.Y.Z-beta.N.lock`, exact names) count. After the script exits, whatever of its group is still alive is killed too. The step ends when the script **exits**, plus a short grace for its last words: a process that left the group and still holds the pipes does not hold the step or the queue.

**What the trust boundary is.** A cut **runs the person's code, not the app's, unsandboxed**: the repository's `scripts/release.sh` and what the merged pull requests put in it. That is why D18 leaves it always to the "yes"; D6 and D18 cover the app's pushes and cuts, and **nothing beyond that is isolated**. The person's checkout is not touched (files, branch and HEAD), but the steps' worktree **shares references with their repository**: the branch `release/X.Y.Z`, the tags `vX.Y.Z[-beta.N]`, the `origin/*` a `git fetch` updates and the entry in `.git/worktrees` exist in their repository and show in a `git branch`, `git tag` or `git worktree list`. The app's own commands use `-c core.hooksPath=/dev/null -c core.fsmonitor=false` (no repository hooks, no `fsmonitor`) in `worktree add`, `fetch` and `status`, but the repository's script runs as it is. Caveats: the app's `git push` ignores `push.followTags` and mirroring (above), but **uses the person's transport configuration as it is** (`url`, `pushurl`, `insteadOf`, `core.sshCommand`, the credential helpers, `push.pushOption`); the **filters and merge drivers defined in the person's own git configuration** (LFS, git-crypt and the like) **run** on the `.gitattributes` a pull request brings, during `merge-pr` (the app switches off hooks and `fsmonitor`, not filters or drivers: the person who installed them already trusts them, and the `.gitattributes` is the pull request's); and `git worktree add --force` takes the registration of **one** path that git lists as `prunable`, never another's.

**The `ReleaseAction` tool** is how the Release manager asks for a step: an app tool, like `VcsRead`, on both engines (the open engine's tool and an MCP server on the Claude SDK), only for a release run. Its schema takes the six operations and a version, and `pr`, `head`, `from`, `branch` (`release` or `main`) and `channel` (`beta` or `stable`) where they fit: no path, no flag. The answer tells the agent, in text, whether the step **ran**, **waits for the person**, or why it was **refused**; the agent has no shell, writes no file and pushes nothing. A step that takes a while (the beta runs the checks of CI) does not let the stage's idle limit stop the agent: the call says it is alive. Each time a stage runs (the person may send it back for another beta) is a new step, with its own key.

**Two waits** (`WAIT_KINDS`, the flow editor and `flowCheck`): `release-approved` goes on when **no** pull request is open against the release branch; one the person does not want in the version is closed or aimed elsewhere (or `runs:skipWait`). `beta-age` (`minutes`, `label`) goes on when the **latest** beta of the version has been published on the host for `minutes` minutes (the latest is the highest of the clone's tags, `localTags`, and the betas the host shows published, asked one by one from `beta.1` on: a beta cut elsewhere counts too) and **no open issue** carries the blocking label (`label`, `beta-blocker` when empty); a "blocking report" is only that. A beta that was cut and not yet published (a draft) does not count: the wait starts over. Where the host cannot say (Bitbucket: no releases, no labels on issues) the wait goes on until the person moves on with `runs:skipWait`. `beta-age` without `minutes` is an error of the flow (`wait-no-event`).

**The flow of the template** (`release-flow`, ids that start with `release-`): plan (`RELEASE_PLAN.md`) → gate → assemble the branch (`open` if missing, `merge-pr` for each approved one, or for each of the person's own when they alone maintain the repository) → `release-approved` → cut the beta (`beta`, `push-branch`, `push-tag`) → `beta-age` (a day, `beta-blocker`) → gate → cut the stable (`stable`, `push-branch` on `main`, `push-tag`) → published (the run ends here; the issue is closed when the host shows the stable published). A rejected gate goes back to the stage it judged (the stable's, to the beta). The Release manager reads the host (`tracker: read`), runs no command (`shell: none`) and changes no file (`permission: read`); it is autonomous for what autonomy covers (opening the branch, merging approved pull requests, commenting), and the cuts and the pushes wait for a "yes" anyway (D18).

### A documentation run

A documentation run **creates or updates the `.coxia/` of a repository** (the format, the delivery to the agents and the check are in [`harness.md`](harness.md)). It starts in Settings › Documentation, with **Create the documentation** (or **Update**), and not from an issue: `Run.docs: { mode: 'create' | 'update' }`, next to `Run.subject` (which stays the release's), with the synthesized issue `docs:<repo>`, number 0, which keeps "one run at a time" per repository. `runs.activeFor` finds it; the publisher writes to no issue (the run's thread is the record) and `prOf` and `prState` only use the recorded pull request.

- **Start** (`Runner.startDocs`, channel `docs:start`): checks for a duplicate, the `docs-flow` flow, the commit identity and the repository (`repo-ambiguous`, `no-clone`), creates the worktree from the tip of the remote on the branch `cycle/docs-<repo>-<YYYYMMDD>` (a second one on the same day gets `branch-exists`), writes `.coxia/.gitignore` with `.run/`, the task summary as `0_ISSUE.md` (the mode, what `.coxia/` has and the state of each file, and the repository's own Claude Code files as candidates for the import) and makes the first commit. It installs no dependencies: the draft runs no code. Without the flow in the workspace, the start is refused with `no-docs-flow` until the window asks for the "yes" and applies the template (`applyFlow`).
- **The flow** (`devCycle.flows.docs`, from the `docs-flow` template, `runKind: 'docs'`): `docs-draft` (work, `docs-writer`, produces `IMPORT_NOTES.md`) → `docs-gate` (the person's gate, returns to `docs-draft` with the reason) → `docs-publish` (work, the same agent: applies what the gate asked and writes the pull request description) → `docs-ready` (waits for `pr-merged`) → `docs-done`. Two stages write because the push is proposed at the end of the last stage that changes the worktree: only after the gate. No squad may be called `docs`.
- **Where it writes:** `Confinement.writeRoot` makes the write guard apply only to `<worktree>/.coxia/`, while reading stays on the whole worktree; no commands. The cycle folder lives in `.coxia/.run/`, ignored by git: the pull request carries `.coxia/**` and the one-line `.gitignore`, and nothing of the record.
- **No `Closes #<n>`:** the description comes from the `docs-pr` template (`devCycle.comments`), with the sections "what this adds", "what came from Claude Code", "what was left out and why" (from `IMPORT_NOTES.md`) and "what to check". The push and the pull request wait for the "yes" in Actions, and in a test workspace they are refused at confirmation.
- **Before the push** the app rewrites the text of `.coxia/` (local paths and credentials, in the body only), says in the thread what changed and stamps the header of the files the pass touched, in a following commit (see [`harness.md`](harness.md)).

**In ordinary runs**, in a repository with `.coxia/`, the stage that changes code receives the documentation section (chosen by stage, role and paths) and the instruction to correct, on the same branch, the rule the change makes false; the review stage receives the rules that are not checked and that the branch left behind, and each becomes a finding that does not block by default. `pushStagesOf` does not change: the documentation change goes in the same pull request. Without `.coxia/`, the section and the instruction do not exist.

### The run screens

- **Today.** The card of an agent-cycle activity shows the run's badge (working, waiting for you, has a question, waiting for you to start or accept, waiting for an event, failed, done; on the chip: "Gate 1 · waiting for you"), the squad when there are squads, and the question or the failure as a blocker (it counts in the blockers tile and the filter). **Start the cycle** appears on a card with no run going, in the app and in a paired browser; when the issue's project has several repositories it asks which. A "Runs waiting for you" block lists whatever is at a gate, at a question that reached you, at a stage to start or to accept, or failed. **Runs** and **Forum** are at the top of Today and in the phone's "More" menu, with the count of what waits for you and of new messages.
- **The run.** The header has the issue, the branch, the squad (and why the run is in it), the pull request and the linked runs; if the run follows an earlier version of the flow it says so and offers to move it to the current one (`runs:migrateFlow`). "What is next" shows what the run waits for and the buttons of its state:

  | State | Buttons |
  |---|---|
  | to start | start the stage, send back to a stage |
  | to accept | accept (optional note), send back (required note), send back to a stage |
  | gate | approve (optional reason), reject or skip (required reason), send back to a stage, and the gate quiz as a tool |
  | question | answer; the path the question took is in view; send back to a stage; on a run waiting for its squad, choose among the candidates (triage's proposal is marked) or go on with no squad |
  | waiting | go on without waiting for the event (required reason; it only moves forward and says where), send back to a stage |
  | failed | try again, send back to a stage |
  | finished | send back to a stage (reopens the run) |
  | any, until the end | cancel (asks for a second click; nothing is deleted) |

  The head of the screen says whether the run is autonomous, which of the four choices of the block are on and where that decision comes from (the workspace's block or the flow's, and which flow); a release run has no such line, because the block does not decide its push and its change request. Below it, the autonomy switches of the stage's agent and of its squad (they apply from the next stage start or publication) and, while a stage works, the agent's live activity. The **stages** are a timeline: each with its agent, whether it runs by itself or waits for you (as it was when the stage began), its state, its attempts, **the model's use** (calls and tokens, added over the attempts, including those that failed or were stopped; the cost is what the provider reported, as OpenRouter does, or a value marked as an estimate when the SDK call did not go to Anthropic's own API: there the SDK's figure is a list price, not what was charged), its documents (they open in the screen) and its tracker comments with their status (posted, waits for your yes, held, refused, deleted) and the link. **Undo** on a posted comment proposes deleting it, an action that waits for your yes in Actions. **Commands** lists every command the run's agents ran, by agent and, inside each agent, by the stage: the number, the command, where it ran (the sandbox or this computer), how it ended (the exit code, the timeout, the refusal, or that it did not run to an exit) and how long it took; it reads the messages the run already writes (`runner.exec`, `runner.exec.host`), so it follows the run live and stays afterwards, and nothing of it goes to the code host. Further down, **Review and QA**: each round with its verdict and findings (file, line, severity, suggestion) and where each finding's thread stands on the pull request: open, still open in the next round (its thread got a reply) or resolved. That state is worked out from the rounds the run keeps (the same test the runner uses to reply or resolve), not read from the host.
- **The end of a run.** When the run ends — done, cancelled or failed —, the app posts **one** message in its thread carrying the same list of the commands, by agent, so the record is in the conversation and not only in the screen. Nothing else is written by it, and it never goes to the code host.
- **The thread.** Beside the stages (a tab on a phone), the run's thread: each message with who said it (an agent with its role, you, the app), its kind (post, question, answer, handoff, decision, system, request), whether it is a public record (it may go to the tracker) or internal, the comment's link once it was posted, the documents it points to and whom it called. A question and everything said about it become a **chain**: who asked whom, each time it was passed on, and why it reached you. Messages arrive live (`forum:message`). Typing `@` completes with the team's agents; a named agent answers there, read only. **With a question waiting, what you write without naming an agent is the answer**, and the box says so.
- **The forum.** The channels (the general one, the squads', one per squad) and the threads (of the runs, and the general ones you opened), with new messages per device (the first time a device opens the forum what is already there counts as read), the squad filter and creating a general thread. In a channel `@` does not call an agent.
- **The runs.** Every run, filtered by state (waiting for you, working, waiting, failed, finished) and by squad; what waits for you comes first.
- **Notices.** A gate, a question that reached you, a failure, a stage to start or to accept and the end are announced by the usual notifications and, with browser access, by push on the phone; tapping opens the run.
- **Actions.** The runner's proposals (comment, review, pull request, delete, priority, status, issue for another squad, squad label, push) show, before the "yes", what they will write: the comment as it will read (and the text as it is sent), the review's lines with the verdict and what happens to each one's thread (new comment, reply, thread resolved), the pull request's description, the labels that go in and out, how many writes of a group already ran. The writes themselves are in a list that opens.
- **Ceremonies per squad.** With squads, the pre-daily card on Today and the retro screen ask for which squad (or the whole workspace); the choice holds for a pre-daily that has not started, and the call, the minutes, the history and the retro say the scope.
- **In a paired browser.** All of it opens in the PWA, and all of it works: reading the run, its documents and the thread, answering questions, writing in the threads, starting, accepting, deciding gates, retrying, cancelling, undoing, choosing the squad, sending back to a stage, the autonomy switches and moving to the current flow. The browser policy (`src/main/webPolicy.ts`) refuses no `runs:*` channel; what it refuses is what would make this machine run a program or read a folder (the whole configuration, the secrets, the runner's commands). `test/run-web.test.ts` checks that no button of the screen depends on a refused channel, with one decided exception: **Take control** of the live screen, which the browser does not show (it only watches).

### Not verified

- **What ran with a real model, and what did not.** A real model went through the cycle, **once and small**: DeepSeek v4.1 flash through OpenRouter, on the open engine, on one small issue of a Node project (a function that makes the address part of a title), end to end (triage, refinement, plan, implementation, review, QA, merge and the note for whoever opened the issue), against a **fake** GitHub host with a memory. That was two runs of about 50 model calls each, at US$ 0.3 a run: one finished; the other stopped at the review's round limit. The defects fixed in this phase came out of it (the review and QA spending one budget, the lost priority proposal, QA that ran nothing, commits and documents with the issue's prefix and head, the clock that cut off an agent that was working, among others). After the fixes, two more runs with the same model measured what was missing: the same title-address issue again, and an ambiguous issue that asked the reporter and the person and was resumed after a process restart, at US$ 0.08 and about US$ 0.14 (the cost the provider reported). **Still not** exercised with a real model: the return loops between the review or QA and the developer, the round limit question, review round 2, the hops of the agent-to-agent question chain, the turn caps (`turns`), a `needsPerson` without a question, squads, undo, another model or provider (Ollama, OpenAI, Groq), the Claude Agent SDK path in the runner, a real code host (a real GitHub, GitLab or Bitbucket) and a large repository. Everything else below comes from the tests, which use a scripted engine, a host that can only be read (or a fake host with a memory) and temporary git repositories: what a real model does with the prompts in general (and whether it picks the `commit`, the findings and the questions well) is still not measured; the English prompts were written by translation.
- **Sandbox and per-agent reads (#30).** The sandbox was really exercised on bubblewrap 0.9.0 on an Ubuntu 24.04 machine (`test/sandbox-bwrap.test.ts` runs a real `bwrap` where it exists and works, and is skipped otherwise): a write outside the worktree fails, the home folder does not exist, no variable of the app passes, only the loopback is there, `.git` does not change, a process one command starts is there for the next and goes with the stage, the time limit stops a command, and QA's copy never reaches the worktree. The registry mode was exercised only as far as the proxy (the forwarder inside the sandbox reaches the proxy and the proxy refuses a host that is not listed), **with no network and no real registry**: that `npm install` works through it was **not observed**. **The open network (`open`) is unexercised**: what was seen is that a sandbox with `open` shares the computer's network (one of the machine's interfaces exists inside) and that the system's name resolver is bound in; reaching a public address over TCP was **not observed** (where the machine cannot reach one, the test skips it). It has **never** run with a real model, with the real Claude Agent SDK (the `Shell` tool and the MCP server were seen with the SDK replaced), on macOS or Windows (no sandbox there), or on another distribution or kernel (the process limit counts per user namespace only since Linux 5.14; a distribution that refuses user namespaces is reported as having no sandbox). With no network, a project whose tests need packages that are not in the repository does not run: turn the registry on. The sandbox is a mitigation, not a virtual machine: no seccomp filter, no CPU limit, no cap on the sum of the processes' memory and no disk quota on the worktree; a kernel bug defeats it. A secret **inside the repository** (a committed `.env`) is readable by a command in the worktree (the output is masked, and `Read`/`Grep`/`Glob` still refuse such files). A `.gitattributes` created in the sandbox can name a filter driver that the person's **own** git configuration defines, and the app's `git add -A` would run it outside the sandbox. An unconfined agent on the Claude Agent SDK still reads outside the worktree (secret-looking names excepted): that existed already and is not dealt with here.
- The guard was tested with path traversal, symbolic links, absolute paths and `.git/hooks` on both engines; **not** against a real hostile repository. A command on the list runs the repository's code (an `npm test` runs whatever `package.json` says) and can do anything the user can: the short list the person chooses is the defence. On the Claude Agent SDK the command runs as a child of the SDK process, which holds the provider's key: the credential-looking variables are removed by `env -u` on each command, tested against the options the SDK receives and by running the rewritten command, **not** against the real SDK (that the hook may return `updatedInput` with `allow` is in the installed version's types, but the real process's behavior was not observed). A credential whose name does not look like one gets through.

- The dependency links were tested with temporary git repositories and the guard; **not** with a real `npm install` inside a linked worktree, nor with package managers that keep dependencies outside `node_modules` (global pnpm store, Yarn PnP, a `.venv` elsewhere): in those cases the thread may say there is nothing to link.
