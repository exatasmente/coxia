# Internationalization

Coxia's interface, and the text it sends to the agents, exist in **Brazilian Portuguese (`pt-BR`)** and **English (`en`)**. Portuguese is the source language: it is where a missing key falls back to. Adding a third language is a matter of one more catalog and a few lines in `src/shared/i18n/index.ts` (see [Adding a language](#adding-a-language)).

## The rules

1. **Every user-facing string goes through `t()`.** No literal text in JSX, in a title or label attribute, in a notification or in an error shown to a person. In the renderer use the hook (`const t = useT()` from `src/renderer/src/i18n.ts`) so the screen re-renders when the language changes; in the main process and in `src/shared/` import `t` from `src/shared/i18n`.
2. **Both catalogs, always.** A key is defined in `src/shared/i18n/pt-BR.json` **and** `src/shared/i18n/en.json`. The setup wizard has its own pair, `wizard.pt-BR.json` and `wizard.en.json`; they are merged into the same catalogs.
3. **Same placeholders in both.** `{name}` placeholders are replaced by the params you pass. The test suite fails when a key exists in only one language or when the placeholders differ.
4. **Flat dotted keys**, named by area: `settings.title`, `wizard.models.testOk`, `prompt.sdd.turn.main`.
5. **Plurals** use the `count` param: with `t('history.count', { count: n })` the translator looks for `history.count_one` when `n` is 1 and `history.count_other` otherwise, then for the plain key.
6. **Compose sentences with placeholders**, not by concatenating translated pieces; word order differs between languages.
7. **Texts for the agents are catalog entries too** (`prompt.<family>.<id>`); see [`cycles.md`](cycles.md) for the families, the overrides and the placeholders (`{theUser}`, `{mode}`, ...).

```ts
t('settings.title');                          // "Configurações" / "Settings"
t('history.count', { count: 3 });             // uses history.count_other
t('wizard.vcs.connected', { user: 'ana' });   // placeholder
```

A key missing in the active language falls back to `pt-BR`; a key missing everywhere returns the key itself. So a gap shows up on screen as a raw key, and in the lint below, never as a crash.

## Voice on, voice off: `tv()`

With voice on the app says "call"; with voice off it says "chat" (English) or "conversa" (Portuguese). That is done with a second key, not a string replace: `tv('call.enter')` reads `call.enter` while voice is on and `call.enter.novoice` while it is off, and falls back to the plain key when there is no variant. Use `tv()` (or `useTv()` in a component) for any string that says "call". Both languages need the `.novoice` variant, and it must keep the same placeholders and never say "call". The rules and the table of wordings are in [`voice.md`](voice.md).

## Checking your work

```bash
npm run i18n:lint                          # both catalogs define the same keys
node scripts/i18n-lint.mjs                 # table of files with the most literal strings
node scripts/i18n-lint.mjs --file <path>   # every finding of one file
node scripts/i18n-lint.mjs --json          # the same as JSON
node scripts/i18n-lint.mjs --max <n>       # exit 1 when the total is above n (a ratchet)
```

The lint for literals is a heuristic (JSX text, `title`/`aria-label`/`placeholder`/`alt`/`label` attributes and string literals that look like prose); it reports, and a ratchet in CI keeps the number from growing. `npm run i18n:lint` is what CI enforces. `test/i18n.test.ts` and `test/voice-terminology.test.ts` check the catalogs.

## Translating well

- Write for a person, not for a dictionary: short, direct, the same register the surrounding screens use.
- Keep technical names as they are (`CLAUDE.md`, `glab`, `merge request`).
- A prompt for the agent is not a UI string: it is read by a model. Keep its structure and its placeholders, and when you reword it, run the prompt tests (`test/cycle-prompts.test.ts` and the parity tests) so a reworded text is still recognized by the code that classifies the app's own sessions.
- The English prompts were written by translation and the model's answers with them were not measured. Improvements are welcome.

## Adding a language

1. Add the code to `LANGUAGES` in `src/shared/config/types.ts` (the JSON Schema is derived from it) and to `normalizeLanguage` and `CATALOGS` in `src/shared/i18n/index.ts`.
2. Create `<code>.json` and `wizard.<code>.json` with every key of the English catalogs, and update the two catalog tests to include it.
3. Add the language to the language picker in the wizard and Settings.
4. Run the whole suite; the key and placeholder tests tell you what is missing.

## Glossary (pt-BR ↔ English)

See the table in the Portuguese section above: the terms are the same. Each ceremony's name comes from the workspace's cycle template (`cycle.label.*`), so "pré-daily" is "pre-daily" and only becomes "pre-standup" if the template says so.

Commands typed into a ceremony chat accept both languages ("próximo" and "next", "aprofundar" and "deepen"...).
