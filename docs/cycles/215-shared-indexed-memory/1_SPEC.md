# Every agent gets a shared, indexed memory of the whole app

## What is asked

The issue, in short: every agent, wherever it runs, has the context of what was decided and found before, across the whole app, without loading everything. Today memory is split and partial:

- the cycle memory (`MEMORY.md`) lives inside one run and is read whole by every stage of it;
- the activities record (`memory/activities.json`, #141) says where each activity stands, and only the app writes it;
- the procedures (`memory/procedures/`) are the closest thing to an index (a list, then a read of one record), but their granularity is a whole record and they hold how to do a recurring thing, not what was decided or found;
- a conversation outside a run (direct, squad channel, general) has no memory at all.

The issue is the foundation for agents that call each other and delegate work in parallel with smaller context windows (#216), and for agents that improve the process over time (#217).

## What the maintainer settled

These came out of the conversation that opened this refinement. They are product decisions, not proposals; the rules below follow from them.

1. **Conversations have memory.** It persists like `activities.json` and the procedures and lives outside any worktree.
2. **One memory, read everywhere an agent runs:** a run stage, a run's thread, a direct conversation, a squad channel, the general conversation, and an agent called by another (inside a conversation and from a stage). Ceremonies read it and never write it (gate 1, rule 2).
3. **The memory files are indexes.** They point to the documents that agents' sessions produce from decisions and findings across the app. An agent reads the index and opens only the excerpt it needs, never whole documents by default. Context windows must stay small: this is what #216 stands on.
4. **An agent can learn** the current version of the product, the priorities of the roadmap and the progress of the activities.
5. **A folder per conversation; inside it a folder per agent**, made the first time that agent is called there and reused afterwards. Each agent writes its own files, never the same file as another agent.
6. **The person and the agents can view, edit and remove these files.** This reverses rule 4 of the #141 spec ("any agent reads, no agent writes") and differs from the procedures, where an agent never deletes. It is a deliberate reversal (see "The reversal").
7. **A run is notified** when documents relevant to it appear elsewhere; it checks them and they may change its direction.
8. **At gate 1:** ceremonies read the memory and never write it; the paired phone has the same capabilities as the desktop over the memory already in this delivery; the delivery goes in the next beta of `0.9.0`. Every other open question is settled as this spec recommended (see "Open questions").
9. **Related issues, outside this one:** #216 (calls, delegation, loop and time cap, full agent configuration everywhere), #217 (agents propose process improvements, for example composing a beta) and #218 (the paired phone gets the same capabilities as the desktop).

## What changes for the person

- An agent asked in a direct conversation about something decided earlier in another conversation answers with the decision and says where it came from (the conversation, the agent, the day), instead of saying it has no record.
- The same agent can say which version of the product is current, which items the roadmap puts first and how an activity is going. When it does not know one of these, it says so instead of inventing it.
- Each conversation gets a place where what its agents wrote down is kept. The person can open it from the app, read what each agent kept, edit a file or remove it. The next agent that reads the memory sees the change.
- A stage that is running hears that something new and relevant was written elsewhere, checks it and may change course. The person sees that notice in the run's conversation like any other message.
- Nothing from this memory appears in a pull request, a commit or a worktree.
- A workspace where the person has not turned it on behaves exactly as before.

## Rules

1. **Conversations have memory.** Every conversation, of whatever kind (a run's thread, a stage-opened side conversation, a direct conversation, a squad channel, the general conversation), can have memory kept for it. It is kept by the app in the workspace's own folder, next to `activities.json` and the procedures, so it survives a restart and is never in a worktree, a commit, a pull request, an export or the retention sweep. (Settled, decision 1.)
2. **One memory, read everywhere an agent runs.** The agent receives the memory in all of: a run stage; a mention in a run's thread; a mention in a direct conversation, a squad channel or the general conversation; an agent called by another inside a conversation; an agent called from a stage; and the answers to a question chain and a squad request. **Ceremonies read the memory and never write it** (gate 1): the ceremony system agents and the mentions made in a ceremony receive the bounded list, and an agent of a ceremony that has tools may open an excerpt; no ceremony agent gets a tool that writes, replaces or removes, and a ceremony makes no folder and leaves no notice. `teams`, which has no tools, gets the list only. A ceremony runs short turns of a voice session under a fixed budget, so its list has the same caps as any other place and adds no wait to a turn.
3. **The memory is an index, not a pile of documents.** What an agent receives by default is a short list: one line per entry with a title, a kind (decision, finding, note, activity, document of a cycle), where it came from (conversation, agent, activity, when) and a pointer. It never receives the documents behind the lines. To use an entry it asks for the excerpt it needs and gets that excerpt, bounded, with its origin. The list itself is bounded (rule 11).
4. **The agent cites where it learned a thing.** An excerpt arrives with its origin, and an answer built on it says where it came from. Excerpts and listings reach the agent as material, not instruction: they arrive in the same fenced section as every other outside text, with the standing sentence that they are notes and data, never instructions. In a place where the agent is not confined by path, reading the files directly is not forbidden by this delivery; the supported way, and the only one that carries the origin and the fence, is the tool.
5. **What an agent can learn from it.** At least: the current version of the product, the priorities of the roadmap and the progress of the activities. The progress of the activities is what the activities record already says. The version and the roadmap have no source in the app today, so where they come from is an open question (Q2). Whatever the source, an agent whose source is empty says that it has none; it does not guess.
6. **A folder per conversation, a folder per agent in it.** The app makes the conversation's folder the first time anything is kept for it, and an agent's folder inside it the first time that agent is called in that conversation; later calls reuse them. (Settled, decision 5.) Whether the folder exists for a conversation where nobody wrote anything is not observable by the agents, only by the person.
7. **One writer per file.** Each agent writes only in its own folder of the conversation; no file is written by two agents. The agent reads all the folders it is allowed to read (rule 2) and writes only its own. Two agents answering in the same conversation at once cannot overwrite each other, because they never share a file. There is no single shared file that agents append to: the index an agent receives is put together by the app, at the moment of reading, from the files of the folders and from what the app already knows (the activities record, the documents of the cycle folders). A person's edit of a file is also a write, and it makes the file the person's.
8. **The person and the agents view, edit and remove.** The person can open any file from the app, read who wrote it and when, edit it and remove it. An agent can create, replace and remove files **in its own folder**. An agent does not replace or remove a file the person edited without being told so: the person's version is kept and the agent's attempt is refused with the reason ("this file was edited by the person"), the same way the procedures keep a person's version. A removal by the person or by the agent takes effect for the next reader at once. No tool or screen of this delivery opens `Edit`/`Write` or the network to any agent: a reader agent writes only through the memory tool of the app, as it does with procedures today.
9. **Text that reaches every prompt is planted text.** What an agent or a person writes is read by every other agent. Whatever else is chosen (Q6), the floor is fixed: the text is masked of credentials and of the exact secret values before it is stored and again before it is shown; it is shown as material in a fence with the standing sentence; it never gives an agent a tool, a host, a permission or a path; the listing shows titles and origins only, never body text; and what an agent wrote after the person took over its screen waits for the person's review before others read it, as procedures do. The kinds of text the validator refuses, and whether refusal is by field or by file, is Q6.
10. **A run is told when something relevant appears.** When a document or entry relevant to a run is written elsewhere (another conversation, another run), the run is notified. The notice is a short message that points at the entry and says why it is relevant; it carries no body. The agent working the run may open the excerpt and change direction. A running stage gets it between two steps, the way a message addressed to it does today; a run between stages gets it as the first thing the next stage reads. A notice is not repeated for the same entry and is recorded in the run's conversation, so the person sees what the agent was told. What counts as relevant and where the notice is delivered is Q3. (Settled, decision 7.)
11. **Context stays small, in a way that can be measured.** The prompt carries the bounded list and the excerpts the agent opened, never a whole document unless the document is itself shorter than the excerpt cap. The list, an excerpt, the size of one file written and the number of files per agent and conversation have named, fixed caps; a write over a cap is refused with the reason and never cut (the procedures way). When the list does not fit it says how many entries were left out and how to ask for them by name. Each call writes to the log how many entries and characters of memory it carried, so the claim "small windows" can be read back and not only believed (the #141 delivery logged its section in the same spirit; it is an open divergence that the activities section is not compact today, see "Divergences").
12. **Nothing existing stops working.** The activities record keeps being projected by the app, kept in the same file and corrected from the same screen. The cycle memory keeps being read whole by a stage and rides the pull request. The procedures keep their store, tools and rules. The new index covers these (an entry can point at an activity front or at a cycle document) but replaces none of them in this delivery (Q7).
13. **A switch, off in existing workspaces.** The memory is on or off per workspace. Off, there is no tool, no section in any prompt, no folder made, no notice, and no agent writes; the person can still view, edit and remove what exists. Existing workspaces keep it off after an update; a new workspace has it on; only the computer changes it, not a paired browser. The name and the migration step are the plan's; whether this is the right default is Q8.
14. **The paired phone has the same capabilities as the desktop over the memory** (gate 1, ahead of #218): a paired browser lists, reads, edits and removes memory files as the window does. The new channels are still named in the policy on purpose, as open, and a test pins them, so a later change of the default does not close or open them by accident. The audit records whether each edit or removal came from the window or a paired browser (`callOrigin()`), and the file shows the person as the author either way. This departs from the procedures, whose writes stay closed to the phone; #218 decides the rest of the app.
15. **Public repository.** The memory files live in the person's data folder, which the public audit does not scan, and nothing here writes into the repository. The code, tests, fixtures and documents of the delivery use neutral placeholders (`example.com`, `group/project`, `#123`) and no real data of any person.

## The reversal

Rule 4 of the #141 spec read "any agent reads, no agent writes" and the activities record is still that way: only the app writes it, from the state of a run. Procedures took a middle road: the agent creates and replaces but never deletes, because an agent that deletes hides what another learned. This issue goes further, by the maintainer's decision: the agents can write and remove their own files and the person can edit and remove anyone's. The reasons the earlier rules gave do not disappear, they move:

- "No agent writes" protected every prompt from planted text. The protection is now the write path: rule 9 and Q6.
- "An agent never deletes" protected what another agent learned. Because no agent writes in another's folder (rule 7) and the person's edit wins (rule 8), an agent can only remove what it wrote itself.
- The activities record is **not** reversed by this issue: it stays written by the app only, from the run. The reversal applies to the new files.

## Out of scope

- **Calls between agents, delegation, the loop and time cap, and the full agent configuration everywhere.** That is #216. This issue only makes sure an agent called by another reads the memory.
- **Agents proposing improvements to the process** (for example composing a beta from finished work). That is #217. The memory is what lets them see what happened; the proposing is theirs.
- **The paired phone getting the capabilities of the desktop in the rest of the app.** That is #218. For the memory it lands here (rule 14).
- **Ceremonies writing** the memory, making folders or receiving notices (rule 2). They read it.
- **Replacing the activities record, the cycle memory or the procedures**, or merging them into one store (rule 12, Q7).
- **A model-built summary** of the app's history, and semantic or embedding search. The index is built from what the app and the agents already write; searching it by keyword is the most this delivery decides on (Q1).
- **Publishing the memory to the tracker**, exporting it, or carrying it in a pull request.
- **Sharing memory between workspaces or between computers.**
- **Enforcing "open only the excerpt" by path** in places where an agent is not confined (rule 4): it is guided by the tool and the prompt, not forced.
- **Changing the retention sweep**: it does not touch the memory folder and still will not.
- **The local state server** (read-only, opt-in, outside the app) showing the new memory: left as it is; it may be extended later.

## Acceptance criteria

Each one is a check a person makes on screen or by test, with the data folder pointed at an empty one.

1. **A decision found in another conversation.** In a conversation, an agent records a decision. In a different conversation (a different kind, for example a direct one) the person names another agent and asks about that decision: the answer states the decision and says where it came from (conversation, agent, day).
2. **Version, roadmap, progress.** With the sources of Q2 in place, the person asks an agent for the current version, the roadmap priorities and the progress of an activity: the three answers are right. With a source missing, the agent says it has none. For the same call, the log shows the number of entries and characters of memory carried, and the prompt (read from the log or a test) holds the list and the opened excerpts, not whole documents.
3. **Two agents at once.** Two agents named in one message answer in the same conversation at the same time and both write: each has its own folder and file, and nothing of one is lost or mixed into the other. An agent that tries to write in another agent's folder is refused with the reason.
4. **The person edits and removes.** The person opens an agent's file from the app, edits it, then removes another: the next agent that reads the memory sees the edit and does not see the removed file. An agent that then tries to replace the edited file is refused with the reason, and the person's text stays.
5. **An agent removes its own.** An agent removes a file it wrote: the next reader no longer finds it. It cannot remove a file it did not write.
6. **First call makes the folder, the second reuses it.** The first time an agent is called in a conversation its folder appears (visible to the person); a later call in the same conversation uses the same one, and a call in another conversation makes a different one.
7. **A run is told.** A stage is running. In another conversation, an agent writes a decision that concerns the same activity: the run's conversation shows a notice that points at it, the agent opens the excerpt, and the person can see what it did next. A decision that concerns something else produces no notice.
8. **Restart and worktree.** After closing and reopening the app, the memory is the same. The files are not in any worktree, and a pull request opened from the run does not contain them.
9. **Planted text.** A file whose text asks the next agent to ignore its instructions, or to use a tool, a host or a permission it does not have, or that carries something shaped like a credential: the text is refused or shown masked, as the answer to Q6 decides; the agent that reads it treats it as data and does not obey it; no permission changes.
10. **Switch off, nothing changes.** In a workspace where the memory is off, no prompt carries a memory section, no tool is offered, no folder is made, the prompts of the existing golden fixtures are unchanged, and the person can still view and remove what exists.
11. **Ceremonies read, never write.** A ceremony agent asked about a decision recorded in a conversation answers with it; a ceremony offers no tool that writes, makes no folder and leaves no notice; `teams` gets the list and no tool.
12. **Small windows.** With hundreds of entries in the memory the list in a prompt stays within its cap and says how many entries were left out; opening one entry adds only its excerpt.
13. **The paired phone.** From a paired browser the person lists, reads, edits and removes memory files exactly as from the window; the audit shows which one did it.

## Open questions

Answered at gate 1 (2026-10-09). The maintainer changed three things: ceremonies read the memory (rule 2), the paired phone has full capabilities over it now (Q5, rule 14), and the delivery goes in the next beta of `0.9.0`. Every other question is settled as recommended below, including the two sub-questions: a notice goes only to the stage that is running or the next one to start (Q3), and a note that fails the validator is refused whole, with the reason (Q6). The questions are kept as they were asked, for the record.

**Q1. Who writes the index, how fine it is, and how an agent searches it.**
Options: only the app (deterministic, like the activities record); only the agent (at the end of its session, like the procedures' last turn); both.
*Recommendation: both, with a division that keeps one writer per file.* The app indexes what it already holds without a model call: the title and the headings of every document a stage produced, the activities fronts, and the entries the agents wrote. The agent writes its own notes and index entries for them through a tool, in its own folder. The app puts the list together at read time (rule 7). Granularity: the entry points at a document and a section (heading), and an excerpt is a bounded slice of that section, not a whole file. Search: keyword over title, kind, origin and headings in this delivery; no semantic search, which needs a model or a provider and a cost the maintainer has not asked for. Whether the agent is also prompted at the end of its session to leave an entry (like the procedures' last turn) is left to #216/#217; here the agent is told it can, by rule.

**Q2. Where the version and the roadmap come from.** Nothing in the app reads a repository's own version or a roadmap today.
*Recommendation:* the **version** from the repositories of the workspace, read by the app (never by asking the agent to run git): the latest release tag and the version of the manifest of each repository, with the release runs' version when one is open. If neither exists, the entry says "unknown". The **roadmap** from a pointer the person gives in the workspace configuration (a document of the repository or a document in the data folder), indexed by its headings and read as an excerpt; without the pointer the agent says there is no roadmap. The priorities of issues stay what they are today (labels and the card's priority), and "roadmap priorities" means the sections of the roadmap document. Adding that pointer is a configuration field, which means a migration step (Q8). The alternative, the agent reading the repository's roadmap file with its own tools, works only in a run's worktree and in places that are not confined, and gives different answers in different places, so it is not recommended.

**Q3. How a run is notified, and what counts as relevant.**
*Recommendation:* use the stage inbox for a stage that is working (it already delivers between two steps in both engines) and a "new since your last stage" section at the top of the next stage for a run that is between stages. Relevant, in this delivery and without a model call: the entry is about the same activity (reference) as the run, or about a repository of the run, or it was written by or addressed to an agent working that run. A notice is one message with at most a handful of pointers, merged if several arrive close together, never repeated, and never carrying the body. Anything fuzzier ("this decision might matter to that run") is left for #216/#217. The question for the maintainer: is a notice also due to a stage that has not started yet (a gate is waiting), or only to the stage that is running or the next one to start?

**Q4. Folder, format, caps, retention, and removal of a conversation or an agent.**
*Recommendation:* `memory/conversations/<thread>/<agent>/` in the workspace, next to `activities.json` and `procedures/`, using the thread id as is (it already fits the folder name). One file per note, in plain text with a short header (who, when, kind, title) so the person edits it comfortably; file names that avoid the words the secret filter holds back (`secret`, `credential`, `token`) so a reader agent is not blocked from its own notes. Caps, named and pinned by tests, refused and never cut: a note at most 8,000 characters; at most 50 files per agent per conversation; the list in a prompt at most 40 lines or 3,000 characters; an excerpt at most 4,000 characters; a title at most 80. Retention: none by the sweep, as with procedures; a note without a change for 90 days is shown as old, never removed. Removal: no channel deletes a conversation today except a discarded agent draft; that case removes its memory folder with the thread, as the attachments are dropped. A workspace deletion moves the whole folder to the trash with the rest. An agent that leaves the team: its folders stay (the notes are the team's history, unlike a login that must not be inherited), and the person sees them as "of an agent that left" and removes them when they want. The alternative, sweeping them like the browser profiles, is simpler but loses decisions. A second agent with the same id as a removed one reads the old notes and may be told they are from before.

**Q5. The paired phone until #218.** *Answered: full capabilities over the memory now (rule 14).*
The state today: a new channel with no rule is open to a paired browser; the procedures close writes by pattern; and `runs:memory` and `runs:activitySave` are already open (Divergence 4).
*Recommendation:* the reads of the new memory open (the person away from the computer can see what the agents kept), every write, edit and removal closed by a pattern like the procedures', so a paired browser cannot plant text that every agent reads, and no new channel is left to the default. Decide Divergence 4 in the same breath and close those two, or keep them open knowingly. Alternatives: close reads too (strictest, like the procedures' offers), or open all (parity with `runs:activitySave`, which contradicts the precedent). #218 later replaces whichever is chosen.

**Q6. Safeguards for agent-written text, given the reversal.**
*Recommendation, in layers like the procedures'* (the floor is rule 9): (1) mask credentials and exact secret values on write and on read; (2) a validator that refuses, by file and with the reason and without echoing the value, text that carries a credential, an e-mail, a path in a person's home folder, a long run of digits, or invisible and direction-changing characters (reusing the procedures' checks for these; the procedures' rules about titles and quoted page text do not apply to prose notes); (3) the fence and the standing sentence at every read; (4) the origin of each file (agent, person, which conversation) always shown to the reader; (5) a file written after the person took over the agent's screen waits for the person's review before others read it; (6) a memory entry never grants a tool, a host or a permission; (7) the listing shows titles and origins, never text. A file the person writes is treated as the person's but is still masked. Question for the maintainer: is refusing by file right for prose, or should a note be accepted with the offending lines masked?

**Q7. The existing memories: fold them or leave them.**
*Recommendation: leave them, and index them.* Activities stay as the app's projection (rule 12), with one index entry kind pointing at a front; the cycle memory stays a cycle document read whole by the stages of its run and is listed in the index by its sections for readers outside the run; the procedures stay their own list and tools and are not duplicated in the index. Folding `MEMORY.md` into the new memory would remove the only memory that rides the pull request, which is a decision about the repository's history and about #216's smaller windows (a stage that reads the cycle memory whole is the opposite of small); it is better taken after this delivery, with data on how the index is used. If the maintainer wants it folded now, the fix of Divergence 6 comes with it.

**Q8. The switch, its default and the migration.**
*Recommendation:* a boolean in the `runner` section, in the manner of `runner.procedures`: absent reads as off, an existing workspace gets `false` written by a migration step that raises no permission, a new workspace has it on, only the computer changes it, and off means no tool, no section, no folder and no notice. The schema is at 24 in this tree, so the step takes the next number; other branches aimed at the same open release may take it first and the number must be checked at the plan. If the Q2 roadmap pointer is added it is the same step. The alternative, no switch (always on), is simpler but gives existing workspaces new tools and a larger prompt without being asked, which the procedures delivery chose not to do.

**Q9. A small one: do agents edit each other's files?**
The settled decision says people and agents can view, edit and remove the files, and also that each agent writes only its own. This spec reads it as: agents read all, write and remove only their own; the person does everything. Confirm, or say that agents may also edit and remove another agent's file, in which case rule 7 needs a different guard than "never the same file".

**Q10. How much goes in this delivery.** The rules are many. *Recommendation:* one issue and one delivery, ordered so that rules 1 to 9, 11 and 13 can ship if the notice (rule 10) has to follow: a run that reads the index is useful without being notified, and the notice is the part that needs the most care with engines and the stage inbox. The maintainer says if the notice must ship in the same release.
