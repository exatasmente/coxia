# Let any agent have a virtual screen, and watch it from the conversation it works in: technical plan

Gate 2 is waived by the maintainer, and two answers were taken on 2026-10-09: the app's browser shares the display of the agent's shell session (D3), and page text is not redacted (D17, which amends spec rule 8).

The plan for `1_SPEC.md` (gate 1 approved on 2026-10-09; gate 2 waived by the maintainer, so this plan is followed directly by the implementation). It says what is built and where; the spec argues the why. Base: `origin/release/0.9.0` at 0.9.0-beta.6 (`7678170f`), schema 20. `@playwright/mcp` 0.0.83 is already in `package.json` (exact pin) and installed. Every `file:line` below was read on this tree today. Names of fields, channels, tools and keys are fixed here; where the spec says "suggested", this plan decides.

## 2. Decisions the spec left to the plan

**Open question 19, where the server runs: the server in the app's process tree, the browser in a `bwrap` of its own.** Per agent browser session the app starts (a) the **display**: the agent's shell session's own display when it has a session (its socket is bound into the browser sandbox by file, at its own name, and `DISPLAY=:N` comes from that name: `<stage>/x11/X99` for a sandbox session, `/tmp/.X11-unix/X<n>` for a host session), otherwise a **display sandbox** of the app's own (a `bwrap` with `--unshare-net` running only `Xvfb`, its socket in a private folder of the session), (b) the **Playwright MCP** as a child of the app (`process.execPath` with `ELECTRON_RUN_AS_NODE=1`, `cli.js`, stdio held only by the app, `cwd` and `HOME` in the session folder), and (c) the server launches Chromium through `--executable-path <wrapper>`, an app-written script that `exec`s a second `bwrap` (`--unshare-user --unshare-ipc --unshare-pid --unshare-uts --disable-userns --die-with-parent --clearenv`, system layout from `systemLayout()`, `--unshare-net` unless the network is shared, the display socket at `/tmp/.X11-unix/<name>`, the profile rw at its own path, the browsers folder and the app's executable folder read-only, 512 MiB `/tmp`, `prlimit --core=0 --fsize`). The network is a property of the namespace: no interface but `lo`, one forwarder (`FORWARDER_JS`, run by the app's executable) to the per-session unix socket of `createRegistryProxy`. Why this shape: it makes "no route around the proxy" true by construction (measured), keeps the control channel (the server's stdio) out of every sandbox, keeps the profile out of the agent's shell sandbox (rule 27), and reuses the display, proxy and forwarder code. The display is shared with the agent's shell session, so an X client there can send input to the browser (accepted, D3 and risk 1). `shell: host` agents and workspace `open` get `--share-net` plus `nameResolverBinds()` and no proxy flag (the person's network, as rule 25 says); the browser is still confined in the filesystem. Rejected: the server inside the agent's sandbox (shared process space with the agent's commands, needs a Node image and puts the profile in reach), the server outside with a loopback listener and flags only (the browser reaches the person's loopback unless every flag is right).

**Display (spec rule 6 as written; maintainer decision at gate 2).** The app's browser uses the display of the agent's shell session when there is one, so there is one screen and one key per agent session. A session of an agent with `screen` is therefore opened with a display (a sandbox session through the supervisor's `Xvfb`, a host session through `startHostDisplay`); a QA stage keeps `run:<id>` and its display as today, and its browser, if the agent has the switch, draws on that display. Only an agent with no shell session (`shell: none` or `allowlist`) gets the display sandbox described above. A separate display for the browser was proposed and rejected by the maintainer (D3).

**Open question 16, server layout: two servers.** `coxia_browser` (the 15 browser tools) exists iff the agent has the switch. `coxia_screen` (`screen_confirm`; #178 adds `screen_handoff`) is offered by rule 37 to sessions that may have no browser (shell path with a display, a host list, or `shell: host`). Both are built from one request over a shared `ScreenAsks` service, so #178's tool needs the viewer (pending ask, notice, hub input marks) and not the browser.

**Open question 21, the mask: only the place.** `MaskSet` (`mask.ts`) is a per-screen-session list of `(text) => text`; the intermediary applies it to every text that carries page content, and before the cap. Page text is **not** redacted or filtered (D17); it goes inside the data fence and is cut to the cap. Nothing adds a mask in #177 (a stub is added in tests). #178 masks the values the person typed during a hand-off, a separate decision approved in its own spec, and decides `--secrets` vs its own mask.

**Open question 22, Enter in a form field: the app reads it.** Before a `browser_click`, `browser_type`, `browser_press_key`, `browser_select_option`, `browser_hover` or `browser_drag` the intermediary takes its **own** `browser_snapshot` (role and name of the ref, `[active]`) and, for a ref or for the focused element, runs `browser_evaluate` with one fixed function (tag, `type`, `form` present, `submitter`, name/value/title text, `window !== top`, `location.origin`). Both are tools the agent is never offered. Enter in an `input` (not a `textarea`, not a button) with `form` present is held (`submit`); a `submitter` click is held; Enter or Space on a focused button or link goes by name. Evaluate failing, a ref missing from the fresh snapshot (answer "stale ref, take a snapshot", not forwarded and not held), or a frame from another origin make the step unclassifiable. The page's DOM can lie to this read (a hostile page); risks, section 9.

**Names.**
- Agent fields: `screen?: boolean`, `allowedHosts?: string[]`, `browserProfile?: boolean`. Absent means off and empty.
- Screen keys (`src/shared/browser.ts`): `run:<runId>` is the screen of a stage's agent session (as today; its browser, if any, shares the display); `call:<thread>:<agentId>` is the screen of an agent in a conversation or in a run's thread. One screen and one key per agent session. A bare run id given to `runs:screen`, `screen:control` or `screen:input` means `run:<id>`. Thread and agent ids hold no `:` (`safeThread` in `src/main/attachments.ts`, `ID` in `schema.ts`).
- Channels (all in `src/main/runner/module.ts`, so `test/runs-policy.test.ts` reads them): `runs:screens(thread?)` list of `OpenScreenInfo` (open); `runs:screenClose(key)` (open); `runs:callStop(thread, agent)` (open); `runs:screenAnswer(askId, decision, note?)` (**external**, joins `EXTERNAL_EFFECT` at `src/main/webPolicy.ts:22`); `runs:screen` and `screen:control`/`screen:input` keep their names and take the key; The Sessions panel of Settings uses `screen:sites(agent)` and `screen:revoke(agent, site?)`, desktop only by the `^screen:` pattern at `webPolicy.ts:72`, so no list of channels has to name them. Event: `SCREEN_EVENT` carries `{ key }` and `SCREEN_ASKS_EVENT` the pending asks.
- Tools: `browser_navigate, browser_navigate_back, browser_snapshot, browser_find, browser_click, browser_type, browser_press_key, browser_fill_form, browser_select_option, browser_hover, browser_drag, browser_wait_for, browser_tabs, browser_handle_dialog, browser_take_screenshot` (Claude SDK: `mcp__coxia_browser__<name>`) and `screen_confirm` (`mcp__coxia_screen__screen_confirm`). Refused by name, listed in `allowlist.ts`: `browser_close, resize, console_messages, emulate_media, evaluate, file_upload, drop, network_requests, network_request, run_code_unsafe`. The exposed schemas are the app's own; `target` is `^(f\d+)?e\d+$`, `filename` is dropped everywhere, `browser_take_screenshot` is offered only where the engine takes images (`ctx.seesImages` on the open engine; always on the Claude SDK).
- Audit kinds: `screen-open`, `screen-close` (carries the step counts by tool and the hosts summary), `screen-hold`, `screen-confirm`, `screen-use`. Conversation commands reuse `exec`.

## 5. Flow and prompts

**Network (rules 24-26).** `effectiveNetwork(workspace: RunnerSandbox, agent)` returns `{ mode: 'off' | 'proxy' | 'open', hosts }`: workspace `off` + list → `proxy`/list; `registry` → `proxy`/registry hosts + list; `open` + list → `proxy`/list (the list narrows); `open` without list → `open`; no list → today. `SandboxService.open` takes `agent?: Pick<AgentDef, 'allowedHosts'>` and `network` in `bwrapArgs` follows the result; `openHost` ignores the list. The proxy of a **browser** uses `maxConnections 48, maxClients 96, idleMs 120_000` (constants in `launch.ts`; the package-install defaults of 16 and 60 s do not fit a page); `onDecision` feeds `hosts.ts`, which keeps counts per host and says one line in the thread the first time a host is refused **while a call is in flight** (so Chromium's own idle traffic is not blamed on a page), appends the refused hosts of the call to that call's result for the agent, and hands one summary to the audit at close. A sandbox session of a conversation gets the same `onProxy` that `answer.ts:356-357` lacks.

**A call.** `answerMentions` and `executeStage` ask `ScreenSessions.acquire({ key, agent, thread, place, config, signal, clock })` when the agent has `screen` (and the workspace display switch is on, Linux). It returns the tools or a plain reason (no browsers folder, no Chromium, no Xvfb, no `bwrap`, test workspace, cap of 4 reached, key already open, platform), said once in the thread. Acquire opens or reuses: the shell session and its display (kept between messages of a conversation, commit 17) or the display sandbox, the server, the profile lock (`profile.ts`: first session of the agent holds `<workspace>/browser/<agentId>/`, any other gets a throwaway profile in its session folder and says so), the hub screen, the recorder. `release(key)` at the end of an answer starts the 10-minute idle clock; a running answer, a browser step, a pending ask (`pause`), or the person's input on the screen (hub callback) stop it; watching does not. It closes at the first of: Close, 2 h (`runner.stageMaxMs`), agent removed or `screen`/`shell` changed or workspace display off (`onConfigChange`), app quit (`endAll`), thread deleted, a run thread's stage change (`executeStage` start/finish call `closeThread('run-<id>')`). Closing: keep the recording (before the browser dies), decline pending asks, kill the server group, the browser sandbox, the display sandbox and a kept shell session, release the lock, delete the throwaway profile, write one thread line and one `screen-close` audit line. A start-up purge removes leftover session folders (the sandbox purge at `runner/module.ts:107` already walks `sandbox/`; the sessions live under it).

**The intermediary**, per call, in this order: URL checks (`http`/`https` only; host in the effective list unless the network is shared; else a plain refusal, not forwarded) → classify (rules 34, 35; `classify.ts` is pure over `{ tool, args, target?: { role, name, active, form, submitter, frame }, page }`) → hold through `ScreenAsks` if irreversible (or unclassifiable without a pass for this site) → forward to the server → for an acting tool take the page's snapshot itself and use it as the result's snapshot → `MaskSet.apply`, fence (`fence` at `prompt.ts:98`), cut to `RESULT_MAX` (no redaction or other content filter, D17) → step log → count for the audit. The server runs with `--codegen none --snapshot-mode none --no-webmcp --idle-timeout 0 --output-max-size 20971520`, `--user-data-dir <profile>`, `--output-dir <session out>`, `--image-responses allow|omit`, `--proxy-server http://127.0.0.1:3128` only when the mode is `proxy`, `--config` (0600, in the session folder) with `launchOptions.args` `--disable-features=AutofillServerCommunication,OptimizationHints,Translate,MediaRouter --disable-quic --no-pings --dns-prefetch-disable --force-webrtc-ip-handling-policy=disable_non_proxied_udp`; no `--cdp-endpoint`, no `--caps`, no `--allowed-origins`, no `--secrets`, no `--storage-state`, no save-trace/session/video. The word list of rule 34 lives in `classify.ts` (English and Brazilian Portuguese; "sign in"/"entrar" are explicitly free) and is pinned by the table test; `Control|Meta + S|Enter` are irreversible, `+ A C V X Z Y F` free, any other chord with a modifier unclassifiable; `browser_handle_dialog accept:true` is irreversible; `browser_navigate`, `browser_tabs`, typing, `fill_form`, `select_option`, hover, wait and reads are free.

**Holds.** `ScreenAsks` copies the shape of `createCommandStore` (`src/main/ceremonyCommands-core.ts:47-110`): `ask()` returns a promise, a 15-minute timer counts as declined, `list()`, `answer()`, `changed` (event), `asked` (notification through `ctx.notify`, opens the conversation), `audit`. A decision `site` is valid only for `why: 'unclassified'` and records a pass for (screen, site) in memory; asked again for an irreversible step it is downgraded to `yes`. The call's `StageClock.pause()` / the answer's `watch.pause` stand still while it waits. `screen_confirm` is `ask()` with `kind: 'confirm'`.

**Prompts (rule 45).** `guiRules` (`prompt.ts:125`) and `mentionCall` (`call.ts:165`) take the agent's `{ screen, hosts, profile: 'own' | 'busy' | 'none', browser: ok | reason }` and pick the `rules.screen*` variants only when `screen` or `allowedHosts` is set; with none of them the strings and the order are today's, byte for byte (the existing goldens do not move). Content of the variants: the hosts (or "none"), that anything else is refused and a page may break; that `coxia_browser` is the way to any external site and the agent's own Playwright is for the app under test; that the app holds some steps and asks the person; that the profile is the logged-in one, a fresh one because it is in use, or none; to run its own headed browser on its display when it has one; to call `screen_confirm` before an irreversible step taken any other way; that everything is recorded and audited; the reason when there is no browser. `rules.shell.registry` gets a hosts variant ("the proxy reaches: {hosts}").

## 6. Seams for #178 and #179

- **`screen_handoff` (#178)** plugs into `coxia_screen`: `engineTool.ts` builds the server's tool list from `screenTools(ctx): ScreenTool[]` where `ctx = { key, ask: ScreenAsks, masks: MaskSet, hub, clock }`; #178 appends one entry. It needs: `ScreenAsks.ask({ kind: 'handoff', ... })` (the type union already reserves it), the hub's input marks (`ScreenHubDeps.used` reports each burst `[from, to]` and its audit line already exists), and `MaskSet`.
- **Where the mask set lives:** `ScreenSession.masks: MaskSet` (`src/main/browser/mask.ts`: `add(mask): () => void`, `apply(text): string`, `size`). The intermediary calls `masks.apply` in exactly one function (`finishText` in `intermediary.ts`) for every result that carries page text, including the snapshot it takes itself and `browser_find`.
- **The step log (#179):** `StepLog` (`stepLog.ts`) per `ScreenSession`, `StepEntry { n, at, tool, role?, name?, site, path, class: 'free' | 'irreversible' | 'unclassified', held?: { why, answer: 'yes' | 'no' | 'site' | 'timeout' | 'closed' }, passed?: true, outcome: 'ok' | 'error' | 'declined' | 'not-run', ms }`. `site` is the host, `path` has no query or fragment, `name` is the control's accessible name cut to 80 characters; no typed value, no page text, no cookie. ## 9. Risks and what the maintainer must decide

1. **Accepted cost (maintainer, gate 2): the display is shared with the agent's shell session,** so an X client in that session can send input to the app's browser around the hold. The hold, the recording and the audit stay the bounds; `shell: none` is the setting where it cannot happen, and the editor recommends it for site work.
2. **Page text is not redacted (maintainer decision at gate 2, amends spec rule 8).** The agent receives what the page shows, secrets and personal data included, inside the data fence and cut to the cap. The bounds are the host list, the hold, the recording and the audit; the step log never holds page text. #178's mask for typed hand-off values is a separate decision.
3. **The classification is DOM-read and spoofable by a hostile page** (labels, a faked `form` getter). It guards an agent misled by a page, not a page that attacks the app. Said in the docs.
4. **Server and client versions differ** (client wants build 1247, the folder holds 1234): works today, no guarantee on an upgrade; the exact pin and the contract test catch tool changes, not protocol drift. The browsers folder must hold a full `chromium-*` (headless shells cannot draw on the display).
5. **The server is third-party code running as the person, outside any sandbox,** with the page's data in memory. The browser it drives is confined; the server itself is not.
6. **Packaged app not tested.** Electron in Node mode reading `cli.js` from the package is verified from `node_modules` only; `asarUnpack` (commit 27) is the mitigation. `npm run dist` is never run, so this is checked by `electron-vite build` and by reading the builder config.
7. **Chromium's own traffic** (four hosts above) shows up in the refused summary; it is not filtered by suffix because a real site may need Google hosts.
8. **Limits unmeasured on a real site:** 48 tunnels, 120 s idle, 512 MiB `/tmp`, no `--nproc` for the browser (threads count and Chromium needs many).
9. **A conversation session outlives its answer** (rule 13, commit 17 is the riskiest): copy, sandbox and processes held for up to 2 h. The caps and the close paths are tested; a leak is an `Xvfb`, a server and a Chromium until the app quits.
10. **The structural hold bounds only the app's browser.** `shell: host` still reads the profile and has the person's network. The editor says so.
11. **Approval from a phone** of a held step needs the external-effects switch; without it the person must be at the computer. A held step with nobody there is declined after 15 minutes.
12. **Order with #170 and #176:** #170 renumbers after this; #176 (idle gaps) should be merged before long conversation screens are recorded, or the 60-minute cap is eaten by idle time.
