## Commit 2: the persona out of the cycle, the templates and the export

Built as planned: `outOfCycle` inside `workingTeam` and `stageAgent` (class A is covered by that alone); the direct readers of class B (`mentionableIds`, `chatAgents`, `mentionChoices`, `forum:list`, `templateFromConfig`, `mergeTemplateTeam`, `parseTemplate`, `adjustable`, the creator's three doors, the Team list, `promoteDraft`); the export, the import and the preview (`transfer.ts`, `config-transfer.ts`); the tests (`test/persona-team-readers.test.ts` with the source scan of class D, `test/persona-transfer.test.ts`, a persona case in `test/agent-assist-draft.test.ts` and `test/forum-policy.test.ts`).

Deviations and decisions:

- **`mentionableIds` for the persona's own thread.** The plan's class B row keeps the ordinary working team in the list and only withholds the owner; the "no `@` in the persona's thread" of rule 15 is the `quiet` post of commit 4 (a persona thread posts with `mentions: []` and no system line). `mentionableIds(team, personaThread)` therefore still lists the working team; the walk test pins that the persona itself is never in it.
- **`parseTemplate` drops the kind, `mergeTemplateTeam` skips the persona.** Both as the plan says: a template file that names a persona is read as an ordinary agent with a warning at `template.team[<id>].kind`; a team handed to `mergeTemplateTeam` programmatically never adds a persona.
- **`parseImport` strips before it validates.** The plan says "removes any entry of kind persona from a file it reads"; doing it on the document before the schema check means a file with two personas (which validation would refuse) still imports, minus the persona, with the warning at `agents.team`.
- **`applyImport` and a clash of ids.** The kept persona wins over an imported agent that has its id (two entries with one id would make the written file fail validation and the load would reset the team). A kept persona whose own model points at a provider (or a pool entry) the imported file does not have goes back to the `deep` role's, for the same reason. Neither case is in the plan.
- **Readers of `agents.team` found by the search and not in the plan's class C**, all looked at: lookups of an agent by id (`service.ts:1117,1579,1601`, `executor.ts:186`, `publish.ts:1444`, `ceremonyCommands.ts:25`, `mentions/ceremony.ts:54`, `browser/sessions.ts:694`), the id lists (`publish.ts:328`, `browser/module.ts`), `runner/module.ts:435`, the pool walkers of the wizard (`poolEdit.ts`), `flowFile.ts:65` (agents named by a flow file) and `squadEdit.ts:95-120`. None decides who works, is called or is offered, so none is filtered.

## Commit 3: a call that answers in plain text and streams what it writes, in both engines

Built as planned: `TextSink` and the optional `schema` in `contract.ts` and `AgentCall`; `onPiece`, `onTurnEnd`, `onRestart` in the open loop (a sub-agent's events drop all three, beside `onThought`); `runOpenEngine` feeds the sink and settles the whole text; `runClaudeSdk` asks for partial messages only when a sink is given, reads the text deltas of the call's own turns, restarts on a tool turn, exempts `stream_event` from the thought flush, and accepts a success result with no structured output for a call with no schema; `src/shared/persona.ts` (the event, the client assembly) and `src/main/persona/live.ts` (the store); the tests (`test/persona-live.test.ts`, `test/persona-stream-open.test.ts`, `test/persona-stream-sdk.test.ts`). The module that publishes the event and serves the read is commit 4, as the plan has it.

Deviations and decisions:

- **`restart()` is also called at the start of every model of the pool** (`withPool`, in `runAgent`), and `onRestart` also fires when a model call fails (the `catch` of the loop's `call()`), not only on a pool switch. Both are idempotent in the live store (a restart with nothing written emits nothing); they keep a failed attempt's pieces and a first model's pieces out of the answer whatever the seam.
- **The Claude loop restarts at the `content_block_start` of a top-level `tool_use` as well as at the assistant message that carries it.** The real check showed the stream event arriving about 300 ms before the assistant message of the same block, so the narration leaves the bubble that much earlier. The assistant-message restart stays for a stream that sends no partial event for it.
- **`settle` publishes the whole text at once, unthrottled and without the held-back word.** The plan only says a sink that got no piece "shows it now"; a final text has no unfinished word, and `end` follows at once.
- **`end(thread, to, how)`** takes `done` (publish the complete text, then the end event) or `dropped` (a failure: only the end event); the plan's third parameter was unspecified.
- **`PersonaLive.active()`** is added (any answer being written), for the module of commit 4.
- **`applyRead`** is added beside `applyLive` in `src/shared/persona.ts`: a read is taken only when it is newer than what the device holds.

### The real check of the Claude SDK path (the plan's "real check, outside the suite")

Run on 2026-10-10 with the SDK `0.3.292` and the CLI `2.1.291` in this repository's `node_modules`, using the Claude login of this computer. A throwaway script in the git-ignored `scratch/` (deleted afterwards), run with `env -i HOME="$HOME" PATH="$PATH"` and empty `CERIMONIAS_DATA_DIR` and `CERIMONIAS_SPECS_DIR` folders, `permissionMode: 'dontAsk'`, `settingSources: []`, isolated settings, `includePartialMessages: true`, no `outputFormat`, the persona-like system text, `Read` allowed. Scenarios: a prompt that needs `Read` and then a long answer (three runs, with the default thinking, with `display: 'summarized'` and with `type: 'disabled'`), the same with a sub-agent (`Agent`), a plain long answer, and a prompt that asks for one sentence of narration in the same turn as the tool call.

1. **Do `text_delta` events arrive in several pieces before the assistant message? Yes.** 57 to 76 `text_delta` events per answer of 786 to 1088 characters, all `parent_tool_use_id: null`, all before the `assistant` message holding the text block (`assistant ... blocks=text(786)` after the last delta). **Caveat:** how they are spread in time depends on whether the model thought first. Without thinking the deltas came over the length of the answer (`first 1738 last 4486 spread 2748` ms). When the model thought first (it did in every run that read a file, even with `thinking: disabled`, which this model ignores), the thinking block took 3 to 4 s, delivered as one burst of `thinking_delta` with empty or summarized text, and then all the text deltas arrived within about 8 ms (`first 7058 last 7065 spread 7`). On the Claude engine the bubble therefore grows gradually only for a turn that does not think first; after a thinking pause the text appears at once. The code is right either way (the pieces are in order and the final text is the same); the effect is the API's and the CLI's, not something the app can ask for with the options tried.
2. **Does the text of a tool turn arrive as deltas followed by a `tool_use` block? Yes.** With narration: `content_block_start text` at 2.677 s, `assistant ... text(28)` at 2.857 s, `stream_event content_block_start tool_use` at 2.857 s, `assistant ... tool_use(Read)` at 3.181 s. The result's `result` held only the last turn's text (165 characters) and not the 28 of narration plus it, which is what the app needs.
3. **Does a success result carry `result` without a structured output? Yes.** In every run: `RESULT subtype=success is_error=false resultLen=786..1088 structured_output=absent turns=1..2`, and `result` equal to the text of the last turn.
4. **Does a `stream_event` appear between the blocks of one turn? Yes.** `assistant id=T2dcfb blocks=thinking`, then `stream_event content_block_stop`, `content_block_start text`, and only then `assistant id=T2dcfb blocks=text`: same message id, partial events in between. This is what the `flushThought` exemption is for, and `test/persona-stream-sdk.test.ts` fails without it.
5. **Sub-agents:** with `Agent`, no `stream_event` of the sub-agent was sent at all (its messages arrive as `user`/`assistant` with `parent=toolu_...` and no partial event). The `parent_tool_use_id` guard stays as defence; nothing in the fallback list was needed.

None of the plan's fallbacks was triggered: the Claude engine streams, and ends with a usable success result.

**Decision recorded by the maintainer's session (2026-10-10), on acceptance 9 for the Claude engine.** The text arriving all at once after a thinking pause (point 1 above) satisfies acceptance 9: the pieces still arrive in order and the stored text equals the last streamed text. The open engine streams gradually; the Claude engine streams gradually only for a turn that does not think first. This is the API's and the CLI's behaviour, not the app's, and nothing is to be built to change it.

## Commit 4: the persona's messages answered as streamed plain text, with the work and the buttons behind them

Built as planned: the persona branch of `answerMentions` and `mentionCall` (no schema, no proposals, the persona's own system and main texts, `call.text` fed by the live store, `OpenScreen` pushed into `runnerTools` for the real persona and not its test copy, `answersTo` and `buttons` on the stored post, Stop with text and failure); `answersTo` and `buttons` in `ForumDraft`, `ForumMessage` and the store's schema; `OpenScreen` (`src/main/persona/openScreen.ts`); `personaModule` with `persona:live-read` and the persona's conversation made at start and on a change of the configuration; `PERSONA_CHANNELS` and the pattern in `webPolicy.ts`; the `quiet` posts; `chat`, `overview`, `board`, `procedures` and `memory` in `PUSH_SCREENS`; the tests (`persona-mentions`, `persona-queue`, `persona-open-screen`, `persona-policy`, `push-targets`, and the persona cases of `forum-store`).

Deviations and decisions:

- **A third prompt key.** The plan names `runner.mention.persona.system` and `.main`; the paragraph that teaches `OpenScreen` is `runner.mention.persona.buttons`, appended only for the real persona, so the test copy is not told of a tool it does not have (rule 11). The three go through `cp()` with the cycle's `{ceremony}` word where the text says the pre-daily, as `test/host-terms-leak.test.ts` asks of any text that is shown for every cycle.
- **`ScreenFacts.ceremonyName`.** The refusal of a ceremony the cycle has turned off names it as the workspace does (`host-terms-leak` refuses the word "pre-daily" in a `main.*` text): the real facts take the pre-daily's name from the cycle (`ceremonyLabel()`) and the other ceremonies from `main.persona.openScreen.ceremony.*`. The plan did not list the field.
- **The store's schema keeps `to` of a button as a string**, not an enum of the vocabulary, and the reading filters through `parseTarget`: a screen that goes away in a later build drops its button when the message is read, where an enum would have made the store skip the whole message line. - **`quiet` is a flag of `personPost` and `attachmentPost`** (both keep their callers), set by the two handlers through the new `isPersonaThread(team, thread)` of `shared/forum.ts`, for the persona and for its test copy.
- **`PERSONA_CHANNELS` holds the one channel that exists (`persona:live-read`).** The wizard's and the editor's nine channels join the set, and so the pattern (built from the set, so the two cannot drift), in commit 5 when they are registered; `test/persona-policy.test.ts` already fails for a registered channel that is not in the set.
- **`targetToScreen` sends `chat` and `overview` to Today** until the chat and the Overview exist as screens (commits 6 to 9); without that a hand-typed `?open=chat` would have set a screen the app cannot draw. Commit 7 replaces it.
- **`OpenScreen` is `principalOnly` and a `note` tool.** A sub-agent never offers a button; a model that only offers buttons for a few steps is taken as done (the engine's rule for notes).
- **`answer.ts` is now a "both" reader in the guard of class D**: it still reads `workingTeam` for `CallAgent`, and now tests `isDraft` of the persona to decide whether the test copy gets the button tool.
- **CallAgent and the other conversation tools stay** (the plan's question 1 default). The persona's `CallAgent` cannot call the persona (it is not in `workingTeam`), and the callee's answer is posted into the persona's thread with the callee's name, with no `answersTo` and no buttons.
- **The CHANGELOG still waits for commit 10.** Nothing a person can reach changes yet: the conversation is hidden from the Forum, the chat is not a screen, and no persona can be made until commit 5.
- **Hermetic test config.** `test/persona-mentions.test.ts` and `test/persona-queue.test.ts` start from a neutral configuration. A first draft of the first one, copied from `activity-calls.test.ts`, started from `installLegacyConfig` with the open engine forced, and the system text it sent to the fake model carried the documentation of the computer that runs the suite (the `CLAUDE.md` found up from the projects folder). ## Commit 5: the persona wizard in the main process

Built as planned: `persona:round`, `persona:review`, `persona:saveDraft`, `persona:conclude`, `persona:discard`, `persona:finish`, `persona:save`, `persona:clear` and `persona:delete` in `src/main/persona/assist.ts`, registered by `personaModule` and added to `PERSONA_CHANNELS` (the pattern that denies any other `persona:` channel is built from the same set); the prompts (`prompt.sdd.persona.*`, both catalogs) with `assistCore.ts`; `PERSONA_REVIEW_SCHEMA`, `readPersonaReview`, `personaAccess`, `personaAccessPatch` and `PERSONA_LIMITS` in `shared/persona.ts`; the audit kind `persona` (`window` or `paired`, the agent's id and nothing else) for finish, save, clear and delete; the `persona.round` and `persona.review` openers in `custo-core.ts` and `retention-core.ts`; the tests (`persona-assist-prompts`, `persona-assist-module`, the wizard's channels and the configuration route in `persona-policy`, one line in the class D list of `persona-team-readers`).

Deviations and decisions:

- **The persona's own request section.** The plan reuses the creator's `assist.section.request` ("What the person asked for"). For the persona the person describes themselves, so `persona.section.request` says "What the person said about themselves, or about what to change". The other sections (rounds, answers, draft, test, note) are reused as planned.
- **The four headings come from a constant.** The review prompt takes `{headings}` from `PERSONA_HEADINGS` (English in both languages, as the instructions are) instead of repeating them in each catalog, so the prompt and the code that names them cannot drift. The themes of the round prompt are the four `persona.theme.*` words, in the workspace's language.
- **The opening of `persona.round` is its own.** The recognition of an app prompt by how it begins (`openersOf`) must tell the persona's round from the creator's, and "Write the next round of questions..." began both; the persona's round opens "Get to know the person: write the next round of questions..." (and its pt-BR counterpart). Both are still counted and swept as the assistant's.
- **Busy check for Clear and Delete.** The plan names `callStops.running(thread)`. A message waiting its turn is not running yet, so `answerPending(thread)` (new, in `mentions/module.ts`, the chain of one answer at a time) is checked as well.
- **Ids.** A new persona's id is `persona` made free of the team, the ids the app keeps and every direct conversation (`uniqueId`), not a slug of its name: the name is edited in the review and the id is the thread's and the memory folder's. A copy made by adjusting is `<id>-draft`, as the creator's.
- **Audit only for changes of the persona.** The audit has finish, save, clear and delete, as the plan lists. The draft steps (save draft, conclude, discard) change no persona and write nothing.
- **Conclude and discard need an id; finish may do without.** `persona:conclude` and `persona:discard` refuse an absent id, as the creator's do. `persona:finish` with no id finishes the draft there is (the screen holds it, but another device may have made it); it still refuses an ordinary agent given by id.
- **Making and adjusting are told by `from`.** `persona:saveDraft` and `persona:finish` with a `from` adjust the persona with that id; without one they make the first and are refused when a persona exists, as the plan's table says. A `from` that is not the persona's id is "persona to adjust was not found".
- **`persona:save` and the model.** The model is any object with a provider and a model name; the configuration's own validation refuses a provider that does not exist, and the error is said as "could not be saved: <reason>". From a paired browser the change goes through `refusedPaths`, so a reserve model added to the list is refused by name.
- **Exports for reuse.** `AssistError`, `explain` and `endScreensOn` (agentAssist.ts), `roundsText` and `draftParts` (agentAssist-core.ts) are exported; no behaviour of the creator changed.
- **The audit label is in `ui-today`.** `ui.audit.kind.persona` is needed now (the audit screen types its labels by `AuditKind`); the `ui-persona` catalogs of the plan start in commit 6.
- **Wording.** `main.persona.draftName` is "My persona" / "Minha persona": a value identical in both catalogs would be refused by the lint, and a persona that was never renamed keeps this name.
