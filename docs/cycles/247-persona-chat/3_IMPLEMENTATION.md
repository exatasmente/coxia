## Commit 3: a call that answers in plain text and streams what it writes, in both engines

Built as planned: `TextSink` and the optional `schema` in `contract.ts` and `AgentCall`; `onPiece`, `onTurnEnd`, `onRestart` in the open loop (a sub-agent's events drop all three, beside `onThought`); `runOpenEngine` feeds the sink and settles the whole text; `runClaudeSdk` asks for partial messages only when a sink is given, reads the text deltas of the call's own turns, restarts on a tool turn, exempts `stream_event` from the thought flush, and accepts a success result with no structured output for a call with no schema; `src/shared/persona.ts` (the event, the client assembly) and `src/main/persona/live.ts` (the store); the tests (`test/persona-live.test.ts`, `test/persona-stream-open.test.ts`, `test/persona-stream-sdk.test.ts`). The module that publishes the event and serves the read is commit 4, as the plan has it.

Deviations and decisions:

- **`restart()` is also called at the start of every model of the pool** (`withPool`, in `runAgent`), and `onRestart` also fires when a model call fails (the `catch` of the loop's `call()`), not only on a pool switch. Both are idempotent in the live store (a restart with nothing written emits nothing); they keep a failed attempt's pieces and a first model's pieces out of the answer whatever the seam.
- **The Claude loop restarts at the `content_block_start` of a top-level `tool_use` as well as at the assistant message that carries it.** The real check showed the stream event arriving about 300 ms before the assistant message of the same block, so the narration leaves the bubble that much earlier. The assistant-message restart stays for a stream that sends no partial event for it.
- **`settle` publishes the whole text at once, unthrottled and without the held-back word.** The plan only says a sink that got no piece "shows it now"; a final text has no unfinished word, and `end` follows at once.
- **`end(thread, to, how)`** takes `done` (publish the complete text, then the end event) or `dropped` (a failure: only the end event); the plan's third parameter was unspecified.
- **`PersonaLive.active()`** is added (any answer being written), for the module of commit 4.
- **`applyRead`** is added beside `applyLive` in `src/shared/persona.ts`: a read is taken only when it is newer than what the device holds.

### The real check of the Claude SDK path (the plan's "real check, outside the suite")

Run on 2026-10-10 with the SDK `0.3.292` and the CLI `2.1.291` in this repository's `node_modules`, using the Claude login of this computer. A throwaway script in the git-ignored `scratch/` (deleted afterwards), run with `env -i HOME="$HOME" PATH="$PATH"` and empty `CERIMONIAS_DATA_DIR` and `CERIMONIAS_SPECS_DIR` folders, `permissionMode: 'dontAsk'`, `settingSources: []`, isolated settings, `includePartialMessages: true`, no `outputFormat`, the persona-like system text, `Read` allowed. Scenarios: a prompt that needs `Read` and then a long answer (three runs, with the default thinking, with `display: 'summarized'` and with `type: 'disabled'`), the same with a sub-agent (`Agent`), a plain long answer, and a prompt that asks for one sentence of narration in the same turn as the tool call.

1. **Do `text_delta` events arrive in several pieces before the assistant message? Yes.** 57 to 76 `text_delta` events per answer of 786 to 1088 characters, all `parent_tool_use_id: null`, all before the `assistant` message holding the text block (`assistant ... blocks=text(786)` after the last delta). **Caveat:** how they are spread in time depends on whether the model thought first. Without thinking the deltas came over the length of the answer (`first 1738 last 4486 spread 2748` ms). When the model thought first (it did in every run that read a file, even with `thinking: disabled`, which this model ignores), the thinking block took 3 to 4 s, delivered as one burst of `thinking_delta` with empty or summarized text, and then all the text deltas arrived within about 8 ms (`first 7058 last 7065 spread 7`). On the Claude engine the bubble therefore grows gradually only for a turn that does not think first; after a thinking pause the text appears at once. The code is right either way (the pieces are in order and the final text is the same); the effect is the API's and the CLI's, not something the app can ask for with the options tried.
2. **Does the text of a tool turn arrive as deltas followed by a `tool_use` block? Yes.** With narration: `content_block_start text` at 2.677 s, `assistant ... text(28)` at 2.857 s, `stream_event content_block_start tool_use` at 2.857 s, `assistant ... tool_use(Read)` at 3.181 s. The result's `result` held only the last turn's text (165 characters) and not the 28 of narration plus it, which is what the app needs.
3. **Does a success result carry `result` without a structured output? Yes.** In every run: `RESULT subtype=success is_error=false resultLen=786..1088 structured_output=absent turns=1..2`, and `result` equal to the text of the last turn.
4. **Does a `stream_event` appear between the blocks of one turn? Yes.** `assistant id=T2dcfb blocks=thinking`, then `stream_event content_block_stop`, `content_block_start text`, and only then `assistant id=T2dcfb blocks=text`: same message id, partial events in between. This is what the `flushThought` exemption is for, and `test/persona-stream-sdk.test.ts` fails without it.
5. **Sub-agents:** with `Agent`, no `stream_event` of the sub-agent was sent at all (its messages arrive as `user`/`assistant` with `parent=toolu_...` and no partial event). The `parent_tool_use_id` guard stays as defence; nothing in the fallback list was needed.

None of the plan's fallbacks was triggered: the Claude engine streams, and ends with a usable success result.

**Decision recorded by the maintainer's session (2026-10-10), on acceptance 9 for the Claude engine.** The text arriving all at once after a thinking pause (point 1 above) satisfies acceptance 9: the pieces still arrive in order and the stored text equals the last streamed text. The open engine streams gradually; the Claude engine streams gradually only for a turn that does not think first. This is the API's and the CLI's behaviour, not the app's, and nothing is to be built to change it.

- **The four headings come from a constant.** The review prompt takes `{headings}` from `PERSONA_HEADINGS` (English in both languages, as the instructions are) instead of repeating them in each catalog, so the prompt and the code that names them cannot drift. - **Ids.** A new persona's id is `persona` made free of the team, the ids the app keeps and every direct conversation (`uniqueId`), not a slug of its name: the name is edited in the review and the id is the thread's and the memory folder's. A copy made by adjusting is `<id>-draft`, as the creator's.

- **Making and adjusting are told by `from`.** `persona:saveDraft` and `persona:finish` with a `from` adjust the persona with that id; without one they make the first and are refused when a persona exists, as the plan's table says. A `from` that is not the persona's id is "persona to adjust was not found".
- **`persona:save` and the model.** The model is any object with a provider and a model name; the configuration's own validation refuses a provider that does not exist, and the error is said as "could not be saved: <reason>". From a paired browser the change goes through `refusedPaths`, so a reserve model added to the list is refused by name.
- **Exports for reuse.** `AssistError`, `explain` and `endScreensOn` (agentAssist.ts), `roundsText` and `draftParts` (agentAssist-core.ts) are exported; no behaviour of the creator changed.
- **The audit label is in `ui-today`.** `ui.audit.kind.persona` is needed now (the audit screen types its labels by `AuditKind`); the `ui-persona` catalogs of the plan start in commit 6.
- **Wording.** `main.persona.draftName` is "My persona" / "Minha persona": a value identical in both catalogs would be refused by the lint, and a persona that was never renamed keeps this name.

## Review and visual fixes

A review of the branch and a pass over the real app (Electron under a virtual display, an empty data folder, a fake model; screenshots of the desktop, a 390 px phone, a tablet and the dark theme) found the items below. One `fix:` commit each, or a group where the pieces share a file. The spec was brought to the maintainer's decision at gate 1 (rule 38) in the same pass.

1. **A persona that breaks a rule no longer wipes the configuration.** `validate.ts` reported a persona that lists stages twice: at its kind, and again at each unknown stage id, and the repair answers an error at `agents.team[i].stages` by resetting the whole team. The unknown-stage check now skips a persona (its stages are reported once, at the kind). The repair that drops a persona's `kind` (`migrations.ts`) also makes the demoted agent inert: no `system`, `squad`, `stages` or `turnsTo`, `autonomous: false`, so personal instructions never work a stage. An unknown `kind` on an agent that was never the persona is dropped alone and the agent is left as it was. Tests (`persona-config`): a persona with `system: true`; a persona with an unknown stage id, a squad, `turnsTo` and `autonomous`; the unknown kind; the existing demotion test now pins the inert result. `docs/configuration.md` says it in both languages.
2. **The chat box keeps its focus.** `Composer` used `disabled={busy}`, which drops the focus; it is `readOnly` with `aria-busy` now, and takes `autoFocus` (the computer's chat, not the wizard's test and not the phone, whose keyboard would cover the conversation). The phone screenshot with the sent text still in the box was **not a bug**: the script pressed Enter, which on the phone breaks the line (the button sends), and the messages above it were the ones left by an earlier run on the same data folder. The box clears after a send (`setText('')` after the post), as before.
3. **Accessibility.** The combobox attributes are on the box only when `mentions` is on (`composerAria`), and `aria-controls="chat-menu"` of the menu button only while the desktop menu is open (`menuControls`). Both are plain functions in `chatModel.ts`, tested in `chat-model`.
4. **The pre-daily notice with no persona.** `targetToScreen` takes `noPersona`: `chat`, and `call` with no cards, land on the Overview, where the pre-daily card is, instead of the wizard; the app passes it from the tray/notice event and the push tap (a ref, because the listeners are registered once), only when the configuration has been read and holds no persona. `notify.preDaily.body` and its `.novoice` variant say *open*, take the ceremony's name (`{ceremony}`, as the title does) and no longer say "the chat" or "the conversation", which now mean the persona's chat. `voice-terminology` exempts the text-mode variant from "turns every call into chat" with the reason; `gitlab-catalogs-unchanged` lists the intended change (a separate commit, because the first commit of this item missed that guard).
5. **Audit.** `persona:saveDraft`, `persona:conclude` and `persona:discard` now record `persona:draft`, `persona:conclude` and `persona:discard` with the door (window or paired) and the agent id, never a text, as rule 38 asks. The branch now asks the mailbox (`deliver()`), which is what its own comment says it does, and calls `events.onRestart?.()` before the `continue`. No call without a schema has a mailbox in the app today (the persona has none; the stages that have one have a schema), so nothing changes for a person; the change is what makes the fix real and testable (`persona-stream-open`: pieces, restart, pieces, settle; fails without the call).
