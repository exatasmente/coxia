## Commit 2: the persona out of the cycle, the templates and the export

Built as planned: `outOfCycle` inside `workingTeam` and `stageAgent` (class A is covered by that alone); the direct readers of class B (`mentionableIds`, `chatAgents`, `mentionChoices`, `forum:list`, `templateFromConfig`, `mergeTemplateTeam`, `parseTemplate`, `adjustable`, the creator's three doors, the Team list, `promoteDraft`); the export, the import and the preview (`transfer.ts`, `config-transfer.ts`); the tests (`test/persona-team-readers.test.ts` with the source scan of class D, `test/persona-transfer.test.ts`, a persona case in `test/agent-assist-draft.test.ts` and `test/forum-policy.test.ts`).

Deviations and decisions:

- **`mentionableIds` for the persona's own thread.** The plan's class B row keeps the ordinary working team in the list and only withholds the owner; the "no `@` in the persona's thread" of rule 15 is the `quiet` post of commit 4 (a persona thread posts with `mentions: []` and no system line). `mentionableIds(team, personaThread)` therefore still lists the working team; the walk test pins that the persona itself is never in it.
- **`parseTemplate` drops the kind, `mergeTemplateTeam` skips the persona.** Both as the plan says: a template file that names a persona is read as an ordinary agent with a warning at `template.team[<id>].kind`; a team handed to `mergeTemplateTeam` programmatically never adds a persona.
- **`parseImport` strips before it validates.** The plan says "removes any entry of kind persona from a file it reads"; doing it on the document before the schema check means a file with two personas (which validation would refuse) still imports, minus the persona, with the warning at `agents.team`.
- **`applyImport` and a clash of ids.** The kept persona wins over an imported agent that has its id (two entries with one id would make the written file fail validation and the load would reset the team). A kept persona whose own model points at a provider (or a pool entry) the imported file does not have goes back to the `deep` role's, for the same reason. Neither case is in the plan.
- **Readers of `agents.team` found by the search and not in the plan's class C**, all looked at: lookups of an agent by id (`service.ts:1117,1579,1601`, `executor.ts:186`, `publish.ts:1444`, `ceremonyCommands.ts:25`, `mentions/ceremony.ts:54`, `browser/sessions.ts:694`), the id lists (`publish.ts:328`, `browser/module.ts`), `runner/module.ts:435`, the pool walkers of the wizard (`poolEdit.ts`), `flowFile.ts:65` (agents named by a flow file) and `squadEdit.ts:95-120`. None decides who works, is called or is offered, so none is filtered.
- **CHANGELOG** still waits for commit 10, as the plan has it (nothing is visible yet).

## Commit 3: a call that answers in plain text and streams what it writes, in both engines

Built as planned: `TextSink` and the optional `schema` in `contract.ts` and `AgentCall`; `onPiece`, `onTurnEnd`, `onRestart` in the open loop (a sub-agent's events drop all three, beside `onThought`); `runOpenEngine` feeds the sink and settles the whole text; `runClaudeSdk` asks for partial messages only when a sink is given, reads the text deltas of the call's own turns, restarts on a tool turn, exempts `stream_event` from the thought flush, and accepts a success result with no structured output for a call with no schema; `src/shared/persona.ts` (the event, the client assembly) and `src/main/persona/live.ts` (the store); the tests (`test/persona-live.test.ts`, `test/persona-stream-open.test.ts`, `test/persona-stream-sdk.test.ts`). The module that publishes the event and serves the read is commit 4, as the plan has it.

Deviations and decisions:

- **`restart()` is also called at the start of every model of the pool** (`withPool`, in `runAgent`), and `onRestart` also fires when a model call fails (the `catch` of the loop's `call()`), not only on a pool switch. Both are idempotent in the live store (a restart with nothing written emits nothing); they keep a failed attempt's pieces and a first model's pieces out of the answer whatever the seam.
- **The Claude loop restarts at the `content_block_start` of a top-level `tool_use` as well as at the assistant message that carries it.** The real check showed the stream event arriving about 300 ms before the assistant message of the same block, so the narration leaves the bubble that much earlier. The assistant-message restart stays for a stream that sends no partial event for it.
- **`settle` publishes the whole text at once, unthrottled and without the held-back word.** The plan only says a sink that got no piece "shows it now"; a final text has no unfinished word, and `end` follows at once.
- **`end(thread, to, how)`** takes `done` (publish the complete text, then the end event) or `dropped` (a failure: only the end event); the plan's third parameter was unspecified.
- **`PersonaLive.active()`** is added (any answer being written), for the module of commit 4.
- **`applyRead`** is added beside `applyLive` in `src/shared/persona.ts`: a read is taken only when it is newer than what the device holds.

### The real check of the Claude SDK path (the plan's "real check, outside the suite")

Run on 2026-10-10 with the SDK `0.3.292` and the CLI `2.1.291` in this repository's `node_modules`, using the Claude login of this computer. A throwaway script in the git-ignored `scratch/` (deleted afterwards), run with `env -i HOME="$HOME" PATH="$PATH"` and empty `CERIMONIAS_DATA_DIR` and `CERIMONIAS_SPECS_DIR` folders, `permissionMode: 'dontAsk'`, `settingSources: []`, isolated settings, `includePartialMessages: true`, no `outputFormat`, the persona-like system text, `Read` allowed. Scenarios: a prompt that needs `Read` and then a long answer (three runs, with the default thinking, with `display: 'summarized'` and with `type: 'disabled'`), the same with a sub-agent (`Agent`), a plain long answer, and a prompt that asks for one sentence of narration in the same turn as the tool call.

1. **Do `text_delta` events arrive in several pieces before the assistant message? Yes.** 57 to 76 `text_delta` events per answer of 786 to 1088 characters, all `parent_tool_use_id: null`, all before the `assistant` message holding the text block (`assistant ... blocks=text(786)` after the last delta). **Caveat:** how they are spread in time depends on whether the model thought first. Without thinking the deltas came over the length of the answer (`first 1738 last 4486 spread 2748` ms). When the model thought first (it did in every run that read a file, even with `thinking: disabled`, which this model ignores), the thinking block took 3 to 4 s, delivered as one burst of `thinking_delta` with empty or summarized text, and then all the text deltas arrived within about 8 ms (`first 7058 last 7065 spread 7`). On the Claude engine the bubble therefore grows gradually only for a turn that does not think first; after a thinking pause the text appears at once. The code is right either way (the pieces are in order and the final text is the same); the effect is the API's and the CLI's, not something the app can ask for with the options tried.
2. **Does the text of a tool turn arrive as deltas followed by a `tool_use` block? Yes.** With narration: `content_block_start text` at 2.677 s, `assistant ... text(28)` at 2.857 s, `stream_event content_block_start tool_use` at 2.857 s, `assistant ... tool_use(Read)` at 3.181 s. The result's `result` held only the last turn's text (165 characters) and not the 28 of narration plus it, which is what the app needs.
3. **Does a success result carry `result` without a structured output? Yes.** In every run: `RESULT subtype=success is_error=false resultLen=786..1088 structured_output=absent turns=1..2`, and `result` equal to the text of the last turn.
4. **Does a `stream_event` appear between the blocks of one turn? Yes.** `assistant id=T2dcfb blocks=thinking`, then `stream_event content_block_stop`, `content_block_start text`, and only then `assistant id=T2dcfb blocks=text`: same message id, partial events in between. This is what the `flushThought` exemption is for, and `test/persona-stream-sdk.test.ts` fails without it.
5. **Sub-agents:** with `Agent`, no `stream_event` of the sub-agent was sent at all (its messages arrive as `user`/`assistant` with `parent=toolu_...` and no partial event). The `parent_tool_use_id` guard stays as defence; nothing in the fallback list was needed.

None of the plan's fallbacks was triggered: the Claude engine streams, and ends with a usable success result.
