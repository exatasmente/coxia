# Test environment for stages

A stage of a run — QA first of all — can exercise the app under development with real configuration: a model provider key, a code host token, the URL of an integration, a feature flag. The person keeps, per workspace, a test environment made of plain variables and secret references, chooses which stages receive it, and the values arrive on the computer only: never in the configuration file, an export, a commit, a pull request, the conversation or the log.

## What changes for the person

Today a QA stage has nothing real to test with: the app under test starts without a key and without a way out to any integration, so "executed evidence" of a real flow cannot exist. After this change the person fills, once per workspace, a list of testing values and marks which entries are secrets; from then on, an allowed stage starts with them already in place, its network opens only to the destinations those entries declare, and every stored or shown trace of the stage masks the exact secret value. Workspaces without the list, and stages not allowed, behave exactly as before.

## Rules

1. **The list lives per workspace, with a per-repository overlay.** The workspace specification keeps a `testEnvironment` section: variables (plain values, stored in the workspace configuration only, never under the data folder) and secrets (references into the existing secrets store, resolved on the computer by the main process). A repository of the workspace may add or override entries on top of the workspace list; the merged view is optional and defaults to workspace-level (the per-repository overlay ships after the workspace list, in this order).
2. **Secrets are stored as references, never as values.** The configuration file carries only the reference (`stored`, `command` or `env` source, like every other secret) plus its metadata; the resolved value exists only in memory of the main process, at the moment a stage launches. Secret references for testing live under their own prefix in the secrets store, so the person can manage and delete them as a group.
3. **QA stages receive the environment by default; other kinds opt in.** Each stage of a cycle template declares whether it receives the test environment. A new QA stage defaults to yes; other kinds (and already-saved templates) default to no and keep today's behavior until the person turns it on for that stage.
4. **Delivery is the stage environment, set by the app, not by the agent.** The sandbox stage starts with the entries as environment variables, written by the launcher before the agent runs. The agent can read them as it can read anything in its environment; nothing is delivered through a file the agent writes, and no template-file mechanism (`*.env`, config file) exists in this change. For Coxia under test on the host, the entries reach the tested app the same way, and the tested app is started with a fresh, empty data folder (see rule 9).
5. **Network opens only to declared destinations.** Each entry may declare a list of allowed hosts. A stage that receives a test environment runs in the existing registry mode; the registry allow-list starts from the hosts the person declared on the stage's entries, so the app under test reaches exactly those on 443 through the app's proxy and nothing else. Entries without declared hosts add nothing to the network.
6. **Private addresses are opt-in, per host.** The proxy's refusal of private and loopback addresses extends to the declared list: one of the person-declared hosts is reached only if the person marks it as private on that entry. An integration on a private address the app is testing against (a self-hosted code host, an internal service) is therefore usable, but only by explicit marking; the default stays refused.
7. **Exact-value masking wherever stage text is kept or shown.** Every resolved secret value is masked — raw, URL-encoded and JSON-escaped forms — in command output, the conversation, the audit log, the run file, stage documents (including executed-evidence text) and anything the stage proposes to a pull request, with the same replacement token plugin requests use today. The existing pattern-based redaction stays in force after exact-value masking, as a second layer. The masked forms are computed from the resolved values of everything in the test environment of that stage, before any text leaves the stage.
8. **Images are not masked, and are blocked from leaving.** A screenshot can show a value on screen, and pictures cannot be reliably redacted. The stage prompt of an environment-carrying stage says this up front. A screenshot or any image file a secret-carrying stage produces is refused from anything that leaves the computer — a pull request, an issue comment — with the reason, the same way a commit that would carry a secret value is refused; the person can see it locally at any time.
9. **A host stage testing the app cannot read the person's real data folder.** When a host stage that received the test environment is for the app being tested by the workspace itself, the launcher starts the tested app with its data folder pointed at a fresh empty folder on the computer, and the app's own secrets file stays out of the stage's file view. For other apps (not Coxia), broader file confinement is out of scope; only the network and masking guarantees above apply.
10. **Real side effects are confirmed once, at configuration time.** The person marks each secret in the test environment as test-only (a dedicated project, a low-budget key) or not. A secret not marked test-only requires the person's explicit confirmation screen — listing the entry, its declared hosts and the stages that will receive it — before any stage launches with it, once per entry, and the confirmation is recorded in the audit log. Confirmation is never delegated to the agent.
11. **Refusal with a reason, not silent failure.** A reference that cannot be resolved, a declared host that fails to normalize, an image or commit that would carry a value, a confirmation missing for a non-test-only secret: the stage launches without the entry only if it cannot otherwise run, and every refusal is reported to the person with the entry name and the reason, in the audit log.

## Out of scope

- Delivery by template file (an `.env` or config file written by the app) — the environment is the only channel in this change.
- The host shell receiving arbitrary workspace secrets with file confinement beyond rule 9.
- Automatic detection or redaction of secret values inside images; blocked instead, per rule 8.
- Per-plugin settings (unchanged), the existing global secrets store outside the new test prefix, and any change to `open` network mode for these stages (they run in registry mode only, per rule 5).
- Sharing test environments between workspaces or exporting them.

## Acceptance criteria

1. Open a workspace, add a variable and a secret reference to the test environment, save: the workspace configuration file contains the variable's value and the secret's reference only; no resolved secret value appears in the file, and the app's export of the configuration does not contain it either.
2. Run an allowed QA stage whose entries declare one host: on the computer, the stage's process has the entries as environment variables; the app under test can call the declared host over 443; a command inside the stage that tries any other host is refused and reports the destination; a command that tries a public host of another kind is refused too.
3. Mark a self-hosted integration on a private address in a stage's entries without marking it private: the call to it is refused; mark it private and confirm: the call goes through.
4. Inside a secret-carrying stage, run a command that echoes a secret value: the conversation, the audit log, the run file and the stage document show the masked token in its raw form; repeat with the value URL-encoded (for example inside a URL) and JSON-escaped (inside a JSON body): all masked.
5. Have a stage propose a commit and a pull request carrying a secret value: both are refused, each with a reason naming what was found; run the same stage in a workspace without a test environment: both succeed as today.
6. In a secret-carrying stage, take a screenshot and save it: it exists locally; a flow that would attach it to a pull request or an issue comment is refused with the reason; the same image is viewable in the paired browser.
7. On the host, run an allowed stage of the workspace that tests Coxia: the tested Coxia starts with an empty data folder on the computer (no existing workspace, no secrets file of the person anywhere in its view), and it performs a real model call and a real read from the code host with the delivered values; the executed evidence recorded for the stage shows the integrations working and the exact values nowhere in it.
8. Run a stage kind that does not allow the environment, and a QA stage flipped to no: their commands see no test entry and their sandbox or host shell behaves exactly as before the change.
9. Use a secret not marked test-only for the first time: a confirmation screen shows the entry, its declared hosts and the receiving stages before launch; approve: the stage runs and the audit log records the approval; refuse: the stage runs without that entry, reported to the person.
10. Point a secret reference at a name the store cannot resolve: the launch report names the entry and the reason, in the audit log and to the person, and the stage does not crash into an unclear state.

## Open questions

- Whether the per-repository overlay ships in the same change as the workspace list (rule 1 makes it sequenced, not blocking).
- How the paired browser states environment-carrying stages in its interface (the refusal flows above are defined; the exact placement on screen is design, not specification).
